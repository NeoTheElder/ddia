The Future of Data Systems

If a thing be ordained to another as to its end, its last end cannot consist in the preservation of its being. Hence a captain does not intend as a last end, the preservation of the ship entrusted to him, since a ship is ordained to something else as its end, viz. to navigation. (Often quoted as: If the highest aim of a captain was to preserve his ship, he would keep it in port forever.) — St. Thomas Aquinas, Summa Theologica (1265–1274)

Eleven chapters described data systems as they are. This last one is different in kind: Kleppmann shifts to how things should be, writes in the first person, and says plainly that these are opinions you are welcome to disagree with. It is also the chapter where the whole book converges. The goal stated in Chapter 1←1 — reliable, scalable, maintainable applications — gets its proposed answer here: build applications as dataflows of immutable events through deterministic derivations, get correctness from end-to-end mechanisms rather than by trusting any single layer, and then step back and ask whether the system you built is beneficial to humanity at all.

The chapter runs in four movements. Data integration: no single tool fits all uses of your data, so how do copies in many systems stay in step? Unbundling databases: the parts of a database — indexes, views, replication — re-emerge as separately operated systems glued by logs; what does application design look like then? Aiming for correctness: how asynchronous, coordination-free dataflow can still give hard guarantees. And doing the right thing: the ethics of predictive analytics and of data collection itself.

FEYNMAN · the whole chapter in one idea Every mechanism in this book is a special case of one move: write things down once, in one agreed order, and derive everything else from that record. A B-tree index, a replication follower, a cache, a search index, a data warehouse, a fraud model — all of them are derived data: the output of running a deterministic function over an ordered log of events. Databases do this inside one product (CREATE INDEX scans the table and then follows its changes); the future Kleppmann proposes does the same across products — the "database inside out." Correctness then stops being something you buy from a vendor and becomes an end-to-end property: a request ID minted where the user clicked, checked where the data lands, makes retries harmless without any distributed transaction. And because "derive everything from the record" is also precisely how surveillance works, the chapter ends by asking the engineer's question no tool can answer: should this be recorded at all? Data Integration

A recurring theme of the book: for any problem there are several solutions with different trade-offs — log-structured vs B-tree vs column storage in Chapter 3←3, single-leader vs multi-leader vs leaderless in Chapter 5←5. Every tool, even a "general-purpose" database, is designed for a particular usage pattern. The first challenge is mapping products to circumstances (vendors won't tell you what their software is bad at). The second is harder: in a real application, the same data is used in several different ways, so no single tool suffices and you inevitably compose several. Statements like "99% of people only need X" say more about the speaker's experience than about reality — the need for integration only becomes visible when you zoom out to the dataflows of a whole organization.

Combining Specialized Tools by Deriving Data

combining-specialized-tools-by-deriving-data

The canonical example: an OLTP database plus a full-text search index (PostgreSQL's built-in search is fine for simple cases, but serious retrieval needs a specialist tool — and a search index is a poor system of record, so you need both). Then copies creep into analytics systems, caches, denormalized views, ML pipelines, notification systems. Chapter 11←11 already posed the question this raises: how do all these representations stay consistent?

Reasoning about dataflows

When the same data lives in several systems, be explicit about inputs and outputs: where is data written first, and which representations derive from which sources? Funnel all writes through a single system that decides a total order, and every other representation can be derived by processing that one ordered stream — change data capture←11 or an event log; the principle is what matters, and it is state machine replication via total order broadcast←9. If instead the application writes to the database and the search index directly, you get the Figure 11-4 dual-write race: two systems each choose their own order for two concurrent writes and end up permanently disagreeing. Derivation from a log is also easy to make deterministic and idempotent, so recovering from faults is straightforward.

Derived data versus distributed transactions

The classical way to keep systems consistent is a distributed transaction: 2PC←9 decides the order of writes with locks and makes changes take effect exactly once with atomic commit. Log-based derivation reaches the same goals by different means: a log for ordering, deterministic retry + idempotence for exactly-once. The big functional difference is timing: transaction systems are usually linearizable←9 — you get read-your-writes←5 for free — while derived systems update asynchronously and don't. Kleppmann's judgment: XA←9 has fault-tolerance and performance properties poor enough that log-based derivation is the more promising integration path — but "eventual consistency, suck it up" is not an answer either; the Aiming for Correctness section looks for the middle ground.

The limits of total ordering

A totally ordered event log is feasible for small systems — that is precisely single-leader replication. At scale, limits appear:

  • Throughput greater than one node can handle forces you to partition the log←11 — and the order of events in two different partitions is undefined.
  • Geo-distribution: a leader per datacenter (multi-leader←5) means events originating in different datacenters have no defined order.
  • Microservices deploy each service with its own durable state, no sharing (Chapter 4←4): events born in two services are unordered.
  • Offline-capable clients (Chapter 5←5) update local state immediately and sync later — clients and servers will see events in different orders.

Formally, deciding a total order is total order broadcast, which is equivalent to consensus←9 — and consensus algorithms are designed for single-node throughput. Consensus that scales beyond one node's throughput, in a geo-distributed setting, is an open research problem.

Batch and Stream Processing

batch-and-stream-processing

The goal of data integration, in one sentence: make sure data ends up in the right form in all the right places. Batch and stream processors are the tools that do it — consuming, transforming, joining, filtering, aggregating, training, and writing derived datasets: search indexes, materialized views, recommendations, aggregate metrics (Chapter 10←10, Chapter 11←11). The fundamental difference — bounded vs unbounded input — is real, but the implementations are blurring: Spark does streams on a batch engine (microbatches), Flink does batch on a stream engine.

Maintaining derived state

Batch processing has a functional flavor: deterministic, pure functions, immutable inputs, append-only outputs. Stream processing extends this with managed, fault-tolerant state (Chapter 11←11). Determinism buys fault tolerance and reasoning: think in pipelines that derive one thing from another. Derived views could be maintained synchronously (a relational database updates its secondary indexes in the writing transaction), but asynchrony is what makes log-based systems robust — a fault in one consumer stays local, while a distributed transaction turns any participant's failure into everyone's abort. Cross-partition secondary indexes (Chapter 6←6) are most reliable when maintained asynchronously, too.

Reprocessing data for application evolution

Stream processing keeps derived views fresh with low delay; batch processing can reprocess the entire history to build a new view of an existing dataset. That is the strongest evolution mechanism the book offers: without reprocessing, schema evolution is limited to small additive changes (Chapter 4←4); with it, you can restructure a dataset into a completely different model. And you can do it gradually: keep the old and new schema side by side as two derived views of the same log, shift users over incrementally, drop the old view when done — every stage reversible. The book's non-computer analogy: 19th-century English railways converted track gauges by adding a third rail (mixed gauge) so trains of both gauges ran for years during the migration; expensive, which is why BART still runs a nonstandard gauge today.

The lambda architecture

If batch reprocesses history and streams handle recent events, how do you combine them? The lambda architecture (Marz): record incoming data as immutable events in an always-growing dataset (like event sourcing←11), then run two parallel systems over it — a stream processor (Storm) producing fast approximate views, and a batch processor (Hadoop) later producing corrected exact views. Influential — it popularized deriving views from immutable events and reprocessing — but with practical problems Kleppmann lists bluntly: the same logic maintained in two frameworks; two outputs that must be merged (easy for tumbling-window aggregates, hard for joins and sessionization); and frequent full reprocessing is too expensive, so the batch layer goes incremental, reacquiring exactly the straggler-and-window headaches (Chapter 11←11) it was meant to escape.

Unifying batch and stream processing

Recent systems get lambda's benefits without its downsides by doing both computations in one system. Three requirements, all now widely available: (1) replay of historical events through the same engine that handles recent ones — log-based brokers can replay, and stream processors can read from HDFS; (2) exactly-once semantics — output as if no fault occurred, by discarding partial output of failed tasks (Chapter 11←11); (3) windowing by event time, not processing time, which is meaningless when replaying (Apache Beam expresses such computations; Flink or Google Cloud Dataflow runs them).

Unbundling Databases

At the most abstract level, databases, Hadoop, and operating systems all do the same job: store data, let you process and query it. They just come from opposite philosophies. Unix gives programmers a logical but low-level abstraction over hardware — pipes, and files that are just byte sequences. Relational databases give a high-level abstraction that hides on-disk data structures, concurrency, and crash recovery — SQL and transactions. Both emerged in the early 1970s and the tension is still unresolved; NoSQL can be read as applying the Unix low-level approach to distributed OLTP. This section tries to reconcile the two — and the reconciliation is this chapter's central design idea.

The meta-database of everything

Seen this way, the dataflow across an entire organization looks like one huge database. Every batch, stream, or ETL process that carries data from one place-and-form to another is acting like a database subsystem keeping an index or materialized view up to date; the derived systems themselves are like different index types — one team's search cluster is the organization's full-text index, another's cache is its materialized view. Making unbundling work

Synchronizing writes across heterogeneous systems the traditional way means distributed transactions across them — which Kleppmann argues is the wrong solution (transactions within one system work; across technologies built by different teams, the lack of a standard protocol makes an asynchronous event log with idempotent consumers far more robust). The payoff is loose coupling at two levels. System level: a slow or failed consumer doesn't stop anyone else — the log buffers (Chapter 11←11), the consumer catches up when fixed — whereas distributed transactions escalate local faults into large-scale failures. Human level: teams develop and operate their systems independently, with the event log as an interface strong enough to carry durability and ordering, general enough to carry almost any data.

Unbundled versus integrated systems

Unbundling won't replace databases: stream processors need stores for state, and query results have to be served from somewhere (Chapter 10←10). Running many pieces of infrastructure has real cost — each has a learning curve and operational quirks — and a single integrated product will beat a composed system on the workloads it was designed for. The goal of unbundling is breadth, not depth: good performance across a much wider range of workloads than any single product covers. If one technology satisfies all your requirements, use it; the advantages of composition only appear when no single piece of software does.

What's missing?

The unbundled equivalent of the Unix shell: a high-level declarative language for composing storage and processing systems. Kleppmann's wish: mysql | elasticsearch — the unbundled CREATE INDEX, taking every document in MySQL, indexing it into Elasticsearch, then capturing every subsequent change automatically. Likewise declaratively specified, automatically maintained caches and materialized views — including over recursive graph queries (Chapter 2←2) and arbitrary application logic. He points to differential dataflow as the promising early research.

Designing Applications Around Dataflow

designing-applications-around-dataflow

Composing specialized storage and processing systems with application code is becoming known as the "database inside-out" approach — Kleppmann's own 2014 talk title, though he insists it's a design pattern, not a new architecture, amalgamated from dataflow languages (Oz, Juttle), functional reactive programming (Elm), and logic programming (Bloom); the term unbundling is Jay Kreps's.

FEYNMAN · the spreadsheet test Put =SUM(A1:A9) in a spreadsheet cell and you never think about it again: change any input and the sum is correct, immediately, always. You don't poll the cell, schedule a refresh job, or reconcile it nightly. Now notice that your search index, your cache, and your analytics dashboard are all just formulas over your database — and yet keeping them right is somebody's full-time job. That is the indictment: data systems still haven't caught up with VisiCalc, 1979. The difference is that modern derived data must also be fault-tolerant, scalable, durable, and built by different teams on different technologies — but the goal stands: when a record changes, everything derived from it updates, and you simply trust that it works.

Application code as a derivation function

Derived datasets are outputs of transformation functions: a secondary index is a cookie-cutter derivation (so databases build it in — CREATE INDEX); a full-text index is standard linguistic processing (language detection, stemming, synonyms) feeding an inverted index; an ML model is derived from training data by feature extraction and statistics; a cache holds an aggregation in exactly the shape the UI displays. When the derivation function is not cookie-cutter, you need custom code — and that is where databases struggle: triggers, stored procedures, and UDFs exist but were afterthoughts, fighting the requirements of modern application development.

Separation of application code and state

Databases could in theory be deployment environments for arbitrary application code; in practice they are terrible at it (no dependency management, version control, rolling upgrades, monitoring…). Cluster schedulers — Mesos, YARN, Docker, Kubernetes — specialize in running application code and do it much better. So the trend holds: stateless application logic here, state management there — don't put application logic in the database, don't put persistent state in the application. As the functional-programming joke goes: we believe in the separation of Church and state. In this model the database is a passive, mutable shared variable reached synchronously over the network. And in most languages you cannot subscribe to a mutable variable's changes — you can only read it periodically. Databases inherited that passivity: polling is usually your only option; subscribing to changes is only beginning to appear as a feature.

Dataflow: the interplay of state, state changes, and code

Thinking in dataflow renegotiates that relationship: application code responds to state changes in one place by triggering state changes in another — the database's changelog treated as a subscribable event stream (Chapter 11←11), actors reacting to messages (Chapter 4←4), the 1980s tuple-spaces model of processes observing and reacting. Crucially, maintaining derived data is not ordinary asynchronous job execution — it makes two stringent demands that traditional messaging doesn't meet: stable ordering (several views derived from one log must process events in the same order or they diverge — redelivery reorders, dual writes are out) and fault-tolerant processing (losing one message leaves a derived view permanently out of sync). Modern stream processors provide both at scale, cheaper and more robustly than distributed transactions, and let application code run as operators between the streams.

The reason the derived dataset exists is the read path: work done lazily, only when a user asks. Stateful, offline-capable clients

The client/server model — stateless clients, authoritative servers — is an assumption, not a law. Single-page apps and mobile apps hold real state on the device and work offline; offline-first applications do as much as possible against a local database and sync in the background (Chapter 5←5). Then the on-device state is a cache of state on the server: the pixels on screen are a materialized view onto client-side model objects, which are a replica of state in a datacenter — the write/read-path picture extended one more hop.

Pushing state changes to clients

A loaded web page is a stale snapshot — a read done once, never updated unless you poll (RSS is just polling). Server-sent events (EventSource) and WebSockets keep a TCP connection open so the server can push changes: the write path extended all the way to the end user. Offline devices? Already solved — a consumer of a log-based broker resumes from its offset←11 after disconnection; each device is a small subscriber to a small stream.

End-to-end event streams

Tools like Elm and React/Flux/Redux already manage client state as a stream of events, structured like event sourcing. Extending that pipeline so servers can push state-change events into it gives the picture above: state changes flowing from one device's interaction, through logs and derivations, to another device's UI, with sub-second delay. Building this way means moving from request/response to publish/subscribe dataflow throughout the stack — worth it, Kleppmann argues, for more responsive UIs and real offline support. When designing systems: keep the option of subscribing to changes, not just querying current state.

Reads are events too

Writes go through the log; reads usually go straight to the store — the store being the boundary where the two paths meet. But reads can also be represented as events, routed to the same operator as the writes: the processor responds by emitting the result onto an output stream. Then serving a query is literally a stream-table join between the query stream and the data (Chapter 11←11) — the read event is co-partitioned with the data it reads, just like any join (Chapter 6←6). A one-off read passes through the join and is forgotten; a subscription is a standing join with future events. Recording read events buys causal-dependency tracking — you can reconstruct what the user saw before they acted (the fix the unfriend example needed), e.g. the shipping estimate shown before a purchase — at the cost of extra storage and I/O.

Multi-partition data processing

For single-partition queries, a query stream is overkill. Its payoff is queries that must combine data from many partitions: the stream processor's message routing, partitioning, and joining infrastructure does the distributed execution. Storm's distributed RPC computed "how many people have seen this URL" — the union of the follower sets of everyone who tweeted it; fraud scoring joins a purchase event against differently partitioned reputation databases for IP, email, billing and shipping addresses. MPP databases do this internally (Chapter 10←10) — use one if it fits; streams are the option when applications outgrow off-the-shelf limits.

Aiming for Correctness

Stateless read-only services shrug off bugs — fix, restart, done. Stateful systems remember things forever, so mistakes potentially last forever. And our engineering methods here are surprisingly flaky: transactions' foundations are weaker than they look (witness the confusion of weak isolation levels←7); some systems abandoned transactions entirely for messier semantics (Chapter 5←5); "consistency" is much invoked and poorly defined (Chapter 9←9); and Kyle Kingsbury's Jepsen experiments keep finding daylight between products' claimed guarantees and their behavior under network faults. Serializability and atomic commit are established but costly — single-datacenter, limited scale. This section proposes ways of thinking about correctness for dataflow architectures.

The End-to-End Argument for Databases

the-end-to-end-argument-for-databases

Using a data system with strong safety properties does not make your application correct. If the application writes wrong data or deletes good data, serializable transactions won't save you. (Immutable, append-only data helps you recover from buggy code — Chapter 11←11 — but it is not a cure-all.) A subtler corruption: processing a message twice. Exactly-once semantics (Chapter 11←11) means arranging that the final effect is as if no fault occurred, typically via idempotence — which takes real care: extra metadata (which operation IDs have been applied), plus fencing←8 across failovers. The end-to-end argument

This is an instance of the end-to-end argument (Saltzer, Reed & Clark, 1984): a function like duplicate suppression "can completely and correctly be implemented only with the knowledge and help of the application standing at the endpoints" — a lower layer's version can be a useful performance optimization, never the whole answer. Same for integrity: Ethernet, TCP, and TLS checksums catch network corruption but not bugs at either end or rot on disk — only an end-to-end checksum catches everything. Same for encryption: WiFi passwords stop snooping neighbors, TLS stops network attackers, but only end-to-end encryption protects against the server itself. The low-level features remain worth having (they make higher-level faults rare); they are just not sufficient.

Applying end-to-end thinking in data systems

The uncomfortable conclusion: your application needs its own end-to-end correctness measures, and transactions alone were never enough. Transactions were a beautiful abstraction — collapsing concurrency, constraint violations, crashes, network faults into "commit or abort" — but they are expensive (especially heterogeneous/XA, Chapter 9←9), and when teams refuse them on performance grounds they end up reimplementing fault tolerance in application code — where reasoning about concurrency and partial failure reliably goes wrong. The abstraction that would wrap up end-to-end fault tolerance cheaply — the successor to the transaction — has not been found yet. The rest of this section assembles the best current candidate from parts we already have.

Enforcing Constraints

enforcing-constraints

Uniqueness constraints require consensus

A username must identify one user; a seat sells once; a balance stays non-negative; stock doesn't go below zero; meeting rooms don't double-book — most such constraints reduce to uniqueness-style enforcement. In a distributed setting, enforcing uniqueness requires consensus (Chapter 9←9): several concurrent claims on the same value, one accepted, the rest rejected. The usual implementation is a single leader (funnel everything through one node; if it fails you're back at consensus); it scales out by partitioning by the constrained value — requests for the same username hash to the same partition (Chapter 6←6). Asynchronous multi-leader replication is ruled out: masters that independently accept conflicting writes destroy uniqueness. If you must reject violations immediately, synchronous coordination is unavoidable.

Timeliness and Integrity

timeliness-and-integrity

Notice what the log-based constraint check gave up: the client may have to wait for the outcome to appear on the output stream. Consumers of a log are asynchronous by design. This points at a distinction the word "consistency" conflates — and separating it is the chapter's sharpest conceptual contribution:

Kleppmann's assertion: in most applications integrity is far more important than timeliness. ACID promises both together, so the distinction is invisible there. Event-based dataflow decouples them: no timeliness unless you build waiting in — but integrity is the streaming world's home turf, achieved by combining four mechanisms: (1) the write's content as a single atomically-writable message (event sourcing); (2) all other state derived via deterministic functions (like stored procedures, Chapter 7←7); (3) a client-generated request ID passed through every level for end-to-end idempotence; (4) immutable messages so derived data can be reprocessed after bugs.

Loosely interpreted constraints

Hard uniqueness needs consensus — but does your business actually need hard uniqueness? Often a violated constraint can be repaired afterwards with an apology: two users register the same username — email one to pick another (a compensating transaction); customers buy more than the warehouse holds — order stock, apologize, discount (the same workflow a forklift accident forces anyway); airlines and hotels deliberately overbook and compensate with refunds and upgrades; overdrafts become fees plus a bounded daily-withdrawal risk. The cost of an apology is a business quantity, often low. If it's acceptable, write optimistically, check afterwards — these applications still require integrity (don't lose the reservation) but not timeliness of enforcement. Coordination and constraints reduce apologies for inconsistency but also reduce availability, thereby increasing apologies for outages; the optimum is not zero of either.

Coordination-avoiding data systems

Two observations compose: dataflow systems keep integrity without atomic commit, linearizability, or synchronous cross-partition coordination; and many constraints can be loose. So coordination-avoiding systems can serve real applications with strong integrity but no synchronous coordination — e.g. multi-leader across regions, each datacenter operating independently (Chapter 5←5), weak timeliness (not linearizable) yet no corruption. Serializable transactions still earn their keep — at small scope, maintaining derived state; heterogeneous XA is not required. Coordination becomes a purchase you make only where the business case (apology cost) justifies it.

Trust, but Verify

trust-but-verify

Everything so far assumed a system model←8: crashes and network faults happen; fsync'd data survives, memory doesn't corrupt, the CPU multiplies correctly. Binary "can/cannot happen" is really a spectrum of probabilities. Data rots on disk untouched; corruption evades TCP checksums (Chapter 8←8); at fleet scale, random bit flips in client RAM show up in crash reports; rowhammer flips bits in fault-free memory on purpose. Rare — but not beyond possibility, and therefore deserving attention.

Maintaining integrity in the face of software bugs

Worse than hardware: bugs. MySQL has failed to maintain a uniqueness constraint; PostgreSQL's serializable isolation has exhibited write skew — in two of the most battle-tested databases there are. Application code is far buggier, and frequently misuses even the integrity features databases do offer (many apps skip foreign-key and uniqueness constraints altogether). ACID consistency is built on the assumption that transactions are bug-free; the database cannot save an application that uses it incorrectly.

Don't just blindly trust what they promise — a culture of verification

If corruption is eventually inevitable, you need to find it: checking data integrity is auditing — not just for accountants (though finance is auditable precisely because everyone admits mistakes happen). HDFS and S3 don't fully trust disks: background processes continually re-read files against replicas and rotate them across disks. If you don't read your backups occasionally, you'll learn they're broken only after the data is gone. Most systems, though, run on blind trust — the ACID culture taught us to treat correctness guarantees as absolute, then NoSQL's weaker guarantees and younger storage arrived and the auditing habit still didn't. Mature systems self-validate: trust, but verify.

Designing for auditability

A transaction that mutated several tables doesn't say why after the fact — the invocation that decided it is gone. Event-sourced systems are better: user input is one immutable event; state updates derive from it deterministically and reproducibly — run the same log through the same code and get the same result. Explicit dataflow makes provenance clear: hash the event log to verify storage; re-run (or redundantly run) derivations to verify views; the same determinism gives time-travel debugging. And continuous end-to-end integrity checks work like automated tests for your data: increased confidence means you can move faster (like the evolvability argument of Chapter 1←1).

The end-to-end argument again — and cryptographic tools

The more systems one integrity check spans, the fewer places corruption can hide — an end-to-end checksum over a whole derived-data pipeline implicitly checks every disk, network, and algorithm on the path. The frontier is cryptographic auditing: cryptocurrencies and distributed ledgers are, from a data-systems view, replicated databases whose mutually untrusting replicas continually cross-check integrity. Doing the Right Thing

The book's final section steps back from architecture entirely. Every system is built for a purpose, and its consequences reach beyond that purpose; the engineers who build it share responsibility for those consequences. Many datasets are about people — their behavior, interests, identity — and deserve to be treated with humanity and respect: users are humans too, and human dignity is paramount. Guidelines exist (the ACM's Software Engineering Code of Ethics) but are rarely discussed or enforced, and engineers and product managers sometimes take a cavalier attitude to privacy as a result. A technology isn't good or bad in itself — what matters is how it's used and whom it affects; focusing on the technology and ignoring the consequences is not an option. Reasoning about ethics is hard; it is also too important to skip.

FEYNMAN · the word-swap test Take any proud sentence about your data platform and replace the word data with surveillance: "in our surveillance-driven organization we collect real-time surveillance streams in our surveillance warehouse, and our surveillance scientists derive new insights." If the sentence suddenly sounds sinister, ask what changed — the sentence, or your awareness of what it always described? Kleppmann's own polemic version: the book could be titled Designing Surveillance-Intensive Applications. The test is not a verdict; user-facing features genuinely need some behavioral tracking. It is a probe for the moment the relationship flips — when the tracking stops serving the person being tracked and starts serving whoever funds the tracking.

Predictive Analytics

predictive-analytics

Predicting the weather is one thing; predicting whether a convict reoffends, a borrower defaults, an applicant is worth hiring — those decisions hit individual lives. Organizations rationally prefer false "no" over costly "yes", so an algorithm that labels someone risky — accurately or not — can systematically exclude them from jobs, credit, flights, insurance, housing: an "algorithmic prison" — exclusion from key parts of society without proof of guilt and with little chance of appeal, inverting the presumption of innocence.

Bias and discrimination

Algorithmic decisions aren't automatically fairer than human ones: if the input data carries systematic bias, the model learns and amplifies it. Anti-discrimination law protects traits like ethnicity, age, gender, sexuality, disability, beliefs — but proxies leak: in a segregated city, postal code or IP address predicts race. Believing a model can take biased data and produce fair output is what the satire calls "machine learning is like money laundering for bias." Predictive analytics extrapolates the past; if the past is discriminatory, it codifies discrimination. A better future requires moral imagination, which only humans supply — data and models should be our tools, not our masters.

Responsibility and accountability

Who answers when the algorithm is wrong? A human decision-maker can be held accountable; a self-driving car's accident or a credit model's systematic bias has no clear address, and an opaque model may be unexplainable even under judicial review. Credit bureaus are the old version — but a credit score at least summarizes your own record ("how did you behave?") and errors are correctable in principle; ML scoring uses far broader, more opaque inputs and asks "how did people like you behave?" — stereotyping by construction, unfixable when the input data is wrong. Statistics are true of distributions, not individuals (average life expectancy of 80 says little about your death date); a blind belief in data supremacy over individual cases is not just delusional but dangerous. Analytics can also target the vulnerable — the same models that could focus aid instead sell payday loans and worthless degrees.

Privacy and Tracking

privacy-and-tracking

Beyond decision-making there's the ethics of collection. When a user explicitly entrusts data to a service to have it processed, the service serves the user. When their activity is tracked as a side effect, the relationship blurs: the service acquires interests of its own. Some tracking genuinely serves users — clicked-result ranking, recommendations, A/B tests. But when the service is funded by advertising, the advertisers are the customers and users' interests take second place: tracking grows more detailed, retention longer, profiles richer. The relationship earns a more sinister name: surveillance.

Surveillance

In the rush to make software eat the world we have built the greatest mass surveillance infrastructure in history — internet-connected microphones in every inhabited space (phones, TVs, assistants, baby monitors, children's toys — many with terrible security records), locations and movements tracked by devices carried voluntarily, even enthusiastically. What totalitarian regimes only dreamed of, we opted into — the collector being corporations rather than governments. Why do we accept it? Perhaps you have "nothing to hide" — i.e., you're aligned with existing power structures and needn't fear persecution; not everyone is so fortunate. And "benign personalization" combined with predictive analytics stops looking benign: insurance premiums linked to car trackers, coverage conditional on fitness wearables — and a smartwatch's motion sensor can reconstruct what you type, passwords included.

Consent and freedom of choice

"Users agreed to the terms" fails on inspection. Users can't know what data they feed in or what it becomes — privacy policies obscure more than they illuminate — so meaningful consent is impossible; one user's data also describes non-users who agreed to nothing; the derived datasets of this book's third part are precisely the kind of thing no user can meaningfully understand. The exchange is one-way — terms set by the service, no negotiation. And declining is not free: when a service is "regarded by most people as essential for basic social participation," opting out has real social and professional costs — a freedom available only to the privileged. For everyone else, surveillance becomes inescapable.

Privacy and use of data

"Privacy is dead" misunderstands the word. Privacy is not secrecy; it is a decision right — the freedom to choose what to reveal, to whom, in each situation. Surveillance doesn't erode that right so much as transfer it: the company now decides what stays secret (mostly its own conclusions about you, revealed only as ad-targeting categories) and what gets used. Privacy settings return crumbs of control against other users, while the service itself keeps unfettered internal access. A person targeted in the bucket "suffers from illness X" has lost agency over an intimate disclosure even if never individually reidentified. This transfer of privacy rights from individuals to corporations, at scale, is historically unprecedented — surveillance used to be expensive and manual; trust-based data relationships (doctor, attorney) used to come with ethical and legal constraints that internet services shed.

Data as assets and power

"Data exhaust" gets the economics backwards: if targeted advertising pays for the service, then behavioral data is the core asset and the app is bait for the extraction machine — startups are literally valued by "eyeballs." Because the data is valuable, everyone wants it: companies collect it, governments obtain it by secret deal, compulsion, or theft; bankruptcy sells it; breaches leak it disconcertingly often. Hence the critics' terms: data as a "toxic asset," at best "hazardous material." When deciding to collect, weigh not just today's government but all future ones: "it is poor civic hygiene to install technologies that could someday facilitate a police state." Knowledge is power, and scrutinizing others while avoiding scrutiny is one of power's most important forms.

Remembering the Industrial Revolution

Kleppmann's closing analogy: the information age as a second Industrial Revolution. The first brought sustained growth and dreadful pollution, dangerous factories, child labor; safeguards (environmental regulation, workplace safety, food inspection) took a long time and raised the cost of business — and society was hugely better for them. Bruce Schneier's formulation: "Data is the pollution problem of the information age, and protecting privacy is the environmental challenge… our grandchildren will look back at us and judge us on how we addressed the challenge of data collection and misuse." We should try to make them proud.

Legislation and self-regulation

The 1995 European Data Protection Directive already demanded purpose-limited, "adequate, relevant and not excessive" collection — philosophically the exact opposite of Big Data (maximize collection, combine datasets, use for unforeseen purposes). Kleppmann doubted 1995-era law's effectiveness and noted updated regulation in development; he calls over-regulation a real risk too (medical-data analysis could save lives). But the deeper ask is a culture shift: treat users as humans, not metrics to optimize; self-regulate to maintain trust; educate users about what happens to their data; purge data when no longer needed rather than retaining it forever (deletion vs immutability is solvable — Chapter 11←11); enforce access control cryptographically rather than merely by policy. Individual control over data is like a natural environment: unprotected, it suffers the tragedy of the commons. Ubiquitous surveillance is not inevitable — we are still able to stop it.

Core takeaways

  • No single tool fits all uses of your data — integration is inevitable, and the sane architecture is derived data: designate systems of record, funnel writes into one ordered log (CDC or event sourcing), and let every other representation — index, cache, warehouse, model — be a deterministic, idempotent consumer. Dual writes race and diverge; a log cannot disagree with itself.
  • Total ordering is the scarce resource: it's equivalent to consensus, so it doesn't scale across partitions, datacenters, microservices, or offline clients. Most events don't need it — but causal dependencies (unfriend-then-vent) can span logs, and a lost dependency plus an external side effect (a sent notification) is unrepairable. Scalable causality capture is an open problem; logging what the user saw ("reads are events") is a starting point.
  • Batch reprocesses history, streams keep views fresh — evolution's killer feature is deriving a new view beside the old (railway-style gradual, reversible migration). The lambda architecture proved the principle and paid twice for it; unified engines (replay + exactly-once + event-time windows) keep the principle and drop the duplicate logic.
  • CREATE INDEX is a dataflow system in miniature: snapshot, catch up, follow — the same shape as setting up a replica or bootstrapping CDC. An organization's dataflow is one huge database: federation unifies its reads (polystores), unbundling unifies its writes (logs + idempotence), Unix-style: small tools, the log as the pipe. Missing: the shell — a declarative language over composed systems.
  • Unbundle only when needed: breadth, not depth. If one product satisfies your requirements, use it; composition wins only where no single product covers the workload span.
  • Design applications as dataflow: application code as derivation functions between state and derived state (the database inside-out); stateless services + state stores, but with subscription replacing polling. Derived-data maintenance is not generic async messaging — it demands stable ordering and fault-tolerant, non-lossy processing. Dataflow beats RPC where a synchronous lookup can become a local, subscribed copy (stream-table join).
  • Write path meets read path at the derived dataset: indexes, caches, and materialized views shift work between the two (grep ↔ precompute-everything; Twitter's fan-out is the canonical middle). The write path can extend to end-user devices — offline-first clients as followers, offsets for reconnection, sub-second end-to-end streams — if we build for publish/subscribe rather than request/response.
  • Correctness must be end-to-end: TCP, 2PC, and exactly-once stream semantics each dedupe within a scope, and a user's retry outlives every scope. A client-minted operation ID enforced by a uniqueness constraint gives exactly-once through arbitrary layers — the end-to-end argument applied to databases; low layers are optimizations, not guarantees.
  • Constraints without coordination: uniqueness needs consensus — a partitioned log provides exactly that (route conflicting claims to one partition, decide sequentially). Multi-partition operations decompose into one atomic append plus deterministic derived instructions deduped by request ID: atomic-commit correctness at partition-independent throughput.
  • Timeliness ≠ integrity: violated timeliness is temporary ("eventual consistency"); violated integrity is permanent ("perpetual inconsistency"). Integrity matters far more, and dataflow systems preserve it without coordination. Many business constraints are loose anyway — apologize and compensate (overbooking, overdrafts) — so buy coordination only where the apology is too expensive.
  • Trust, but verify: hardware lies rarely and software regularly; even MySQL and PostgreSQL have shipped integrity bugs. Audit continuously and end-to-end — event sourcing makes derivations reproducible, hashes make logs tamper-evident, Merkle trees (certificate transparency) make inclusion provable — and read your backups.
  • Engineers carry ethical responsibility: predictive analytics can build algorithmic prisons, launder bias, and spin feedback loops; tracking-funded services drift into surveillance; consent without understanding is not consent; privacy is a decision right that surveillance transfers to the collector. Data is the pollution problem of the information age — minimize collection, purge aggressively, and build the world you want to live in.
  • 2nd-edition arc: the chapter splits — the technical program becomes Ch 13 "A Philosophy of Streaming Systems" (the future arrived: composable data systems, OLEP/sagas, IVM products, local-first/CRDTs), and the ethics section is promoted to Ch 14 "Doing the Right Thing" in a new "Data and Society" part, with GDPR as enacted law and a decade of AI-ethics developments folded in.

Q1 — b. Same goals, different means: logs order, idempotent retry gives exactly-once effect. The honest cost is timing — derived systems are asynchronous, so no read-your-writes by default, which is why (a) is wrong. (c) is false (2PC orders via locks); (d) is false — total order still is consensus, just localized per partition.
Q2 — c. The causal dependency crossed two independently ordered logs. Nothing was redelivered (a); no LWW was involved (b); and (d) misses the point — even perfect clocks wouldn't help, because the notifier's friend-list state lagged, regardless of timestamps.
Q3 — d. Immutable event storage is the part of lambda Kleppmann praises — it's the architecture's lasting contribution. (a), (b), (c) are his three criticisms verbatim.
Q4 — a. Replay, exactly-once, event-time windows — each neutralizes one reason for having a separate batch layer. (b) are implementation details of particular streamers; (c) is the coordination stack this chapter argues around; (d) is Chapter 3's analytics toolkit.
Q5 — c. Snapshot → catch-up → follow, three times over: index build, follower setup (ch 5), CDC bootstrap (ch 11). The parallel is the section's evidence that a database is internally a dataflow system, so its features can be unbundled.
Q6 — b. Reads vs writes is exactly the split, with the traditions deliberately assigned (federation = relational elegance, unbundling = Unix composition). (a) swaps them; (d) is backwards — unbundling exists to avoid heterogeneous distributed transactions, using logs + idempotence instead.
Q7 — d. Subscribe ahead of time, join locally: "the fastest and most reliable network request is no network request at all." (b) keeps the synchronous hop; (a) reinvents stale caches; note the honest caveat either way — the join is time-dependent under reprocessing (SCD, ch 11).
Q8 — a. The boundary-shifting view unifies all three mechanisms — and retroactively explains Chapter 1's Twitter fan-out (precompute timelines at write time, except celebrities at read time). (d) is half the story (they make writes more expensive); (b) and (c) are wrong outright.
Q9 — c. A logged read is a durable fact ("the user was shown X at t") that later events can causally reference — e.g., the shipping estimate that preceded a purchase. The cost is storage/I-O, an open optimization problem. (a), (b), (d) are inventions.
Q10 — b. Scope is everything: TCP dedupes packets within a connection, 2PC ties up one transaction's fate, exactly-once holds within a framework — the user's intention spans all of them. Only an end-to-end operation ID travels the whole path. This is the Saltzer/Reed/Clark end-to-end argument applied to databases.
Q11 — d. UNIQUE(request_id) turns a duplicate into an abort — and uniqueness constraints hold even at weak isolation, where check-then-insert would race (write skew, ch 7). The bonus insight: the requests table is an event log, and the balance writes are derivable — the door to event sourcing.
Q12 — a. Partition-by-constrained-value + sequential single-threaded consumption = consensus via total order broadcast (ch 9's linearizable-storage algorithm). No leases (b), no wall clocks (c) — the append order itself is the decision. (d) ascribes application logic to the broker.
Q13 — c. Determinism + end-to-end IDs: replay produces identical instructions, and appliers keep a seen-set per request ID. (a) is the exactly-once myth — brokers redeliver; (b) checkpoints don't prevent reprocessing, they bound it; (d) would destroy the parallelism that is the whole point.
Q14 — b. The slogan pair: eventual consistency vs perpetual inconsistency. ACID bundles both guarantees, which is why the distinction stays invisible until you unbundle. The credit-card statement is the book's example: lag is fine; sums that don't balance are catastrophic.
Q15 — d. Compensating transactions and apology workflows already exist in the business (forklifts, weather, strikes), so linearizable enforcement is often paying for timeliness nobody needs. Integrity is still required throughout. (c) overstates FLP — consensus is practical (ch 9); the argument is economic, not impossibility.
Q16 — a. "Trust, but verify": HDFS/S3 re-read replicas continually; event-sourced derivations re-run deterministically; hash the log. Merkle trees prove inclusion in log(n) hashes and already secure the TLS certificate ecosystem via certificate transparency — the useful residue of the ledger hype, minus proof-of-work (c), which Kleppmann calls extraordinarily wasteful.
