Storage and Retrieval

Wer Ordnung hält, ist nur zu faul zum Suchen.
(If you keep things tidily ordered, you're just too lazy to go searching.) — German proverb

A database has exactly two jobs: when you give it data, it stores the data; when you ask later, it gives the data back. This chapter is about how it does those two things — not because you'll write a storage engine, but because you have to choose one and tune it, and you can't do either without a rough model of what's happening under the hood. In Chapter 2←2 we looked at data from the application's point of view; now we flip to the database's point of view.

The single most important fork in the road: storage engines optimized for transactional workloads (OLTP) look completely different from engines optimized for analytics (OLAP). The first two thirds of this chapter live in the OLTP world, where two schools of thought compete — log-structured engines (append-only files) and update-in-place engines (B-trees). The final third crosses over into analytics and column-oriented storage.

FEYNMAN · the whole chapter in one idea Every storage engine is a bargain between the cost of writing and the cost of reading. A pile of papers on your desk is instant to add to (drop it on top) and miserable to search. A perfectly organized filing cabinet is instant to search and miserable to add to (find the right folder, make space, reshuffle). Every structure in this chapter — hash indexes, LSM-trees, B-trees, column files — is just a different point on that trade-off curve. Throughout this page, ember means the write path and cyan means the read path.

Data Structures That Power Your Database

Kleppmann opens with the world's simplest database — two shell functions:

#!/bin/bash
db_set () {
    echo "$1,$2" >> database
}
db_get () {
    grep "^$1," database | sed -e "s/^$1,//" | tail -n 1
}

db_set key value appends a line to a file. db_get key greps the whole file and keeps the last match — because updates never overwrite anything, they just append a newer line, so the latest value for a key is the last occurrence in the file. This file is a log: an append-only sequence of records. Not a log as in "application log output" — in this book, log always means the general thing: an append-only sequence of records, human-readable or not. Logs will come back again and again — they're the backbone of replication→5 and of stream processing→11.

Here's the asymmetry that drives the whole chapter: db_set is fast — appending to a file is about the cheapest write there is. db_get is terrible — O(n), a full scan per lookup; double your data, double your lookup time. To read efficiently you need an index: extra metadata on the side that acts as a signpost to where data lives. And indexes are not free:

FEYNMAN · the fundamental trade-off of indexing An index is a derived structure — a cheat-sheet built from your data. Every cheat-sheet must be kept up to date, so every index makes writes slower, because each write now has to update the data and the cheat-sheet. Well-chosen indexes speed up reads; all indexes slow down writes. That's why databases make you choose indexes instead of indexing everything: you know your query patterns, the database doesn't.

Hash Indexes

hash-indexes

The simplest real index: keep the append-only log exactly as it is, and hold an in-memory hash map from every key to the byte offset where that key's latest value lives in the file. On every write, append to the file and update the map. On every read, consult the map, seek() to the offset, read the value — one disk seek at most, zero if the file section is already in the OS page cache. Step through it:

This design (essentially Bitcask) shines when the value for each key is updated frequently: think key = cat-video URL, value = play count. Tons of writes, but few distinct keys — so all keys fit comfortably in memory while the values churn.

Segments, compaction, and merging

One problem: we only ever append, so the file grows forever. The fix: break the log into segments — close a segment file when it reaches a size limit and write on into a fresh one. Frozen segments are then compacted: throw away duplicate keys, keep only the most recent update for each. Since compaction shrinks segments, several segments can also be merged into one in the same pass. Crucially, all of this happens in a background thread against immutable files, while reads and writes continue against the old segments; when the merged segment is ready, reads atomically switch over and the old files are deleted.

FEYNMAN · compaction Imagine a scoreboard where you only ever append score updates: "alice 10", "bob 3", "alice 12", "alice 15". Compaction is rewriting that list as just "alice 15, bob 3" — same information, way less paper. And because the old sheets are never edited (only replaced wholesale), someone can keep reading the old sheet while you prepare the new one.

What a real implementation worries about

  • File format — not CSV; a binary format (length prefix, then raw bytes) is faster and needs no escaping.
  • Deletes — you can't remove from an append-only file, so you append a tombstone: a special deletion record telling the merge process to discard all previous values for that key.
  • Crash recovery — the in-memory hash maps die with the process. Rebuilding them by rescanning every segment is slow, so Bitcask snapshots each segment's hash map to disk.
  • Partially written records — a crash mid-append leaves a torn record; checksums detect and skip the corrupted tail.
  • Concurrency — one writer thread (writes are strictly sequential anyway); segments are immutable, so any number of concurrent readers.

Why append-only beats update-in-place

  1. Appending and merging are sequential writes — vastly faster than random writes on spinning disks, and still preferable on SSDs.
  2. Crash recovery and concurrency are simple: you never have to reason about a file that's half old value, half new value.
  3. Merging periodically rewrites the data, so files never fragment over time.

And the two hard limits of hash indexes

  1. All keys must fit in RAM. An on-disk hash map performs badly: random I/O everywhere, expensive to grow, fiddly collision handling.
  2. No efficient range queries. You can't scan kitty00000 through kitty99999 — every single key would be a separate hash lookup.

Both limits fall to the next structure — which only asks one small thing of the segment file: keep it sorted.

SSTables and LSM-Trees

sstables-and-lsm-trees

Take the segment files from before and add one requirement: key-value pairs are sorted by key, and each key appears only once per segment (compaction already guarantees that). This format is called a Sorted String Table — SSTable. Sorting looks like it breaks the append-only trick (writes arrive in any order!), but hold that thought — the fix is coming. First, what sorting buys you:

1. Merging becomes mergesort. Even for files far bigger than RAM: read the inputs side by side, copy the lowest key, repeat. When the same key appears in several inputs, the value from the newest segment wins — every value in a newer segment is more recent than everything in an older one.

2. The in-memory index can be sparse. To find a key you no longer need every key in memory. Know the offsets of a few keys, and sorting tells you which gap your key must be in — jump there and scan a few kilobytes:

Constructing and maintaining SSTables — the LSM-tree

Now the held thought: writes arrive in any order, so how does data get sorted? Answer: sort it in memory first. Maintaining a sorted structure in RAM is easy — any balanced tree (red-black, AVL) takes inserts in random order and reads them back sorted. The full recipe, which is what LevelDB, RocksDB, Cassandra, and HBase run (the design descends from Google's Bigtable paper, which coined SSTable and memtable, and was first described academically as the Log-Structured Merge-Tree by Patrick O'Neil et al.):

FEYNMAN · the LSM-tree A chef takes orders on a whiteboard (memtable) — fast to scribble, kept tidy and sorted. When the whiteboard fills up, she photographs it into a binder page (SSTable flush) and wipes it. Every night, someone staples related binder pages together and throws away superseded orders (compaction). And because whiteboards get erased by accident, every order is also jotted instantly on a carbon-copy pad nobody sorts or reads — unless the whiteboard is lost, in which case the pad recreates it (WAL). Fast writes, sorted reads, crash safety: pick three.

Performance details worth knowing

  • Lucene does the same trick for text. The term dictionary of Lucene (inside Elasticsearch and Solr) maps term → postings list (word → IDs of documents containing it), stored in SSTable-like sorted files merged in the background.
  • Compaction strategies differ. Size-tiered: newer, smaller SSTables get merged into older, larger ones (HBase; Cassandra supports it). Leveled: the key range is split into smaller SSTables and older data moves into separate levels, letting compaction proceed incrementally with less disk (LevelDB — hence the name — and RocksDB; Cassandra supports both).
  • The core strengths: data is sorted, so range queries work; disk writes are sequential, so write throughput is remarkably high; the working set need not fit in RAM.
2ND EDITION · storage engines in the cloud era The 2nd edition (where this material is Chapter 4) treats RocksDB as the modern LSM workhorse — it's the embedded engine inside many newer databases. New coverage reflects hardware and deployment shifts: NVMe/SSD-aware designs like WiscKey (separating keys from values to cut write amplification), and storage engines built over object storage (S3) — the compute/storage separation behind systems like Snowflake and Aurora. The RUM conjecture — you can't simultaneously optimize Read overhead, Update overhead, and Memory/space overhead — gives the B-tree-vs-LSM trade-off a formal frame.

B-Trees

b-trees

Log-structured indexes are the insurgents; the incumbent — the standard index in almost every relational database and many non-relational ones — is the B-tree, introduced in 1970 and called "ubiquitous" within a decade. Like SSTables, B-trees keep key-value pairs sorted by key (efficient lookups and range queries), but the design philosophy is the opposite. Log-structured engines deal in variable-size segments (megabytes, written sequentially, never modified). B-trees break the database into fixed-size pages — traditionally 4 KB, mirroring the disk's own block structure — and read or write one page at a time, in place. Pages reference each other by on-disk address (a pointer, but on disk), forming a tree:

Updating an existing key is easy: find the leaf, change the value, overwrite the page in place — references to it stay valid since its address doesn't change. Adding a key is easy until the target page is full — then it must split:

FEYNMAN · B-tree A B-tree is the library's signage system: the lobby sign sends you to a floor (root), the floor sign to an aisle, the aisle sign to a shelf where books sit in order (leaf). Nobody ever moves the shelves — they relabel them in place. And when a shelf overflows, the librarian splits its contents across two shelves and fixes the aisle sign. The signage guarantees any book is 3–4 signs away, whether the library holds a thousand books or a billion.

Making B-trees reliable

Overwriting a page is a real hardware act — on a spinning disk, moving the head and rewriting a sector; on SSDs, erasing and rewriting a large block. Three protections matter: the WAL for crash recovery (above); some engines also write each page twice to survive torn pages from power loss mid-write; and latches (lightweight locks) protect the tree from concurrent threads seeing it mid-surgery. Log-structured engines dodge the concurrency problem entirely — merging happens in the background on immutable files, swapped in atomically.

B-tree optimizations, briefly

  • Copy-on-write instead of WAL (LMDB): a modified page is written to a new location with new parent versions pointing at it — which, bonus, is exactly what snapshot isolation→7 wants.
  • Key abbreviation: interior pages only need enough of each key to mark range boundaries — packing more keys per page raises the branching factor and lowers the depth (this variant is the ubiquitous B+-tree).
  • Sequential leaf layout: engines try to place leaf pages in key order on disk so range scans don't seek per page — hard to maintain as the tree grows, and a place where LSM-trees (which rewrite big runs anyway) have it easier.
  • Sibling pointers: leaf pages referencing their left/right neighbors make in-order scans cheap without climbing back up.
  • Fractal trees borrow log-structured buffering to cut seeks (no fractals involved).

Comparing B-Trees and LSM-Trees

comparing-b-trees-and-lsm-trees

Rule of thumb: LSM-trees are typically faster for writes; B-trees are thought to be faster for reads (an LSM read may check the memtable plus several SSTables at different compaction stages). But benchmarks are workload-sensitive and often inconclusive — test with your workload. What follows is the checklist of what to weigh.

LSM-tree advantagesB-tree advantages
WritesHigher sustained throughput: often lower write amplification, and compact SSTables are written sequentially — a huge win on spinning disks, still relevant on SSDs.Predictable: no background compaction competing for the disk.
SpaceCompresses better; periodic rewriting removes fragmentation (especially with leveled compaction).Pages keep unused gaps from splits — some space is always wasted.
Read latency—More predictable tail latency: compaction bursts can push LSM high-percentile response times←1 way up while the disk is busy.
Under pressure—LSM failure mode: at high write rates, compaction can fall behind — unmerged segments pile up until the disk fills, and reads slow down. Engines typically don't throttle incoming writes when this happens; you need monitoring to catch it.
Transactions—Each key lives in exactly one place (LSM may hold copies across segments) — so range locks for transaction isolation attach directly to the tree. More in Chapter 7→7.

B-trees are deeply ingrained and consistently good; log-structured indexes keep winning ground in new datastores. There's no shortcut rule — measure.

Other Indexing Structures

other-indexing-structures

Everything so far was a primary key index: key uniquely identifies one row/document/vertex. Just as common are secondary indexes (CREATE INDEX …), often crucial for joins — e.g. an index on user_id to find all rows belonging to a user, referencing Chapter 2's example schema←2. The twist: secondary keys aren't unique. Two solutions: make each index value a list of matching row IDs (like a postings list), or make each key unique by appending the row ID. Either way, both B-trees and LSM-trees work fine as secondary indexes.

Where does the value live? Heap, clustered, covering

Multi-column and multi-dimensional indexes

A concatenated index glues fields into one key — like a phone book sorted by (lastname, firstname): great for "all Smiths" and "Smith, Jane", useless for "everyone named Jane". For genuinely multi-dimensional queries — the classic being geospatial:

SELECT * FROM restaurants WHERE latitude  > 51.4946 AND latitude  < 51.5079
                            AND longitude > -0.1162 AND longitude < -0.1004;

— a single B-tree or LSM index can give you a latitude stripe or a longitude stripe, but not the rectangle. Options: map 2D into 1D with a space-filling curve and use a normal B-tree, or use a purpose-built spatial index — R-trees (PostGIS, via PostgreSQL's GiST). And dimensions needn't be geographic: (red, green, blue) for color search, (date, temperature) for weather queries — a 2D index narrows both at once where a 1D index must scan one dimension entirely.

Full-text search and fuzzy indexes

Everything above assumes exact keys or exact ranges. Searching for similar keys — misspellings, synonyms, grammatical variants, nearby words — needs different machinery. Lucene can search within an edit distance (edit distance 1 = one letter added/removed/replaced): its in-memory index over the term dictionary isn't a sparse key list but a finite state automaton over the keys' characters (trie-like), which can be transformed into a Levenshtein automaton that walks all terms within a given edit distance efficiently. Beyond that lies document classification and machine learning — information-retrieval textbook territory.

Keeping everything in memory

Every structure in this chapter is an answer to the awkwardness of disks. Disks earn it two ways: durability, and a lower cost per gigabyte than RAM. But RAM keeps getting cheaper, and many datasets simply aren't that big — hence in-memory databases: Memcached (cache-only, loss acceptable), and durable ones — VoltDB, MemSQL, Oracle TimesTen (relational), RAMCloud (durable in-memory KV), Redis and Couchbase (weak durability via async disk writes). Durability comes from a change log on disk, periodic snapshots, replication, or battery-backed RAM — but reads never touch disk.

FEYNMAN · the counterintuitive part The speed win of in-memory databases is not "no disk reads" — a disk-based engine with enough RAM also never reads disk, because the OS caches everything anyway. The win is skipping the work of encoding in-memory structures into a disk-writable format at all. That's also why they can offer data models that are awkward on disk — Redis serves priority queues and sets database-style precisely because everything lives in memory.

Research pushes further: anti-caching evicts least-recently-used records to disk and pulls them back on access — like OS swapping, but at record granularity instead of page granularity, which the database can manage far better than the OS. (Indexes must still fit in memory, Bitcask-style.) And if non-volatile memory (NVM) matures, storage engine design shifts again — an open research frontier as of the 1st edition.

2ND EDITION · a brand-new index family + embedded engines The biggest addition to this chapter's territory (2nd-ed Ch 4): vector indexes for semantic search over embeddings — where the query is "nearest neighbors in a high-dimensional space," which no B-tree can answer. Coverage spans approximate-nearest-neighbor structures like HNSW (navigable small-world graphs) and IVF, with pgvector as the working example — the storage layer under RAG and semantic search. Also new: embedded/in-process databases (DuckDB, SQLite — including Bluesky's single-tenant-SQLite architecture), fuller full-text internals (Lucene, Postgres GIN), and modern spatial indexing (Uber's H3, bkd-trees).

Transaction Processing or Analytics?

The word transaction is a fossil: early databases recorded commercial transactions (sales, orders, salaries), and the name stuck for any group of reads and writes forming a logical unit — money or not. A transaction here does not imply ACID; it just means low-latency reads and writes, as opposed to batch jobs that run periodically. (ACID proper is Chapter 7→7; batch is Chapter 10→10.)

Two access patterns pulled databases apart. OLTP (online transaction processing): an interactive app looks up a handful of records by key via an index, inserts or updates from user input. OLAP (online analytic processing): a business analyst's query scans millions of records, reads only a few columns per record, and computes aggregates — total revenue per store in January; how many extra bananas did the promotion sell; which brand of baby food is bought with brand-X diapers. The workloads differ in every dimension:

propertyOLTPOLAP

column-oriented-storage

Column-Oriented Storage

Trillions of rows, petabytes of facts — how do you query that? Note what a typical warehouse query actually touches: a fact table 100+ columns wide, but only 4 or 5 columns per query. The book's running example — "do people buy more fresh fruit or candy, by weekday?" — reads exactly three columns of fact_sales:

SELECT dim_date.weekday, dim_product.category, SUM(fact_sales.quantity)
FROM fact_sales
  JOIN dim_date    ON fact_sales.date_key   = dim_date.date_key
  JOIN dim_product ON fact_sales.product_sk = dim_product.product_sk
WHERE dim_date.year = 2013 AND dim_product.category IN ('Fresh fruit','Candy')
GROUP BY dim_date.weekday, dim_product.category;

Column storage isn't inherently relational — Parquet is a columnar format for a document data model, based on Google's Dremel. (Beware a naming trap: Cassandra/HBase "column families," inherited from Bigtable, store each row's columns together with a row key and don't compress columns — mostly row-oriented, despite the name.)

Column Compression

column-compression

Look down a single column and you see repetition — few distinct values, long runs. That's compression fuel. The warehouse favorite is bitmap encoding:

FEYNMAN · bitmaps An attendance register: one row of checkboxes per student across all class dates. "Which dates had Alice or Bob?" is just laying Alice's row over Bob's and OR-ing the checkmarks — no reading names, no scanning records, pure bit arithmetic that CPUs eat for breakfast.

Memory bandwidth and vectorized processing. Disk-to-memory bandwidth isn't the only bottleneck — analytical engines also fight for memory-to-CPU-cache bandwidth, dodge branch mispredictions, and exploit SIMD. Column layout helps here too: a chunk of compressed column data fits in L1 cache and can be processed in a tight, call-free loop; operators like those bitwise AND/ORs work on compressed chunks directly. This is vectorized processing.

2ND EDITION · the columnar ecosystem grew up What the 1st edition sketched became an industry (2nd-ed Ch 4 + a dataframes thread in later chapters): Parquet everywhere on disk, Apache Arrow as the in-memory columnar standard (plus newer formats like Lance and Nimble), "composable" query engines built from these parts, and the query-execution debate refined into vectorized vs. compiled execution (the MonetDB/X100 lineage). DuckDB — an embedded, in-process columnar OLAP engine — is the era's emblem: warehouse techniques in a library you import. Real-time OLAP (ClickHouse-class) and dataframes as an analytics interface get first-class treatment.

Sort Order in Column Storage

sort-order-in-column-storage

Rows can be stored in insert order — appending a row just appends to each column file. But choosing a sort order (SSTable-style) helps twice. It's an indexing mechanism: sort by date_key first and queries over "last month" scan a narrow slice instead of everything; a second sort key (product_sk) groups same-product sales within each date for grouping/filtering. And it's a compression multiplier: the first sort key gets long runs of repeated values — run-length encoding can crush a billion-row column to kilobytes. (Later sort keys are progressively more jumbled; the win concentrates in the first.) Remember the constraint: you can't sort each column independently — position is identity, so the rows sort as units, stored columnwise.

Several sort orders at once? C-Store's trick, adopted by Vertica: you're replicating data across machines for fault tolerance anyway — store each replica sorted differently and route each query to the version that fits it best. It rhymes with secondary indexes on a row store, with one deep difference: a row store keeps one authoritative row location plus pointers; a column store has no pointers at all — only columns of values in some order.

Writing to Column-Oriented Storage

writing-to-column-oriented-storage

All these read optimizations make writes awkward: update-in-place à la B-tree is impossible against compressed, sorted columns — inserting one row mid-sort would rewrite every column file to keep positions consistent. The answer is an old friend: the LSM pattern. Writes accumulate in a sorted in-memory store (row- or column-oriented, doesn't matter); when enough pile up, they're merged with the on-disk column files and written as new files in bulk — essentially what Vertica does. Queries transparently combine disk columns with recent in-memory writes; analysts never see the seam.

FEYNMAN · one trick, twice Notice what just happened: the chapter's two halves reunited. The write side of a "read-optimized" column store is an LSM-tree. Sorted immutable files + in-memory buffer + background merge isn't an OLTP trick — it's the general answer to "writes arrive randomly, reads want order."

Aggregation: Data Cubes and Materialized Views

aggregation-data-cubes-and-materialized-views

Warehouse queries lean on aggregates (COUNT, SUM, AVG, MIN, MAX). If many queries recompute the same aggregates, cache them: a materialized view is a view whose results are physically written to disk — unlike a virtual view, which is just a saved query expanded on the fly. When underlying data changes, the materialized copy must be refreshed, which taxes writes — fine in a read-heavy warehouse, rarely worth it in OLTP.

Core takeaways

  • Every storage engine trades write cost against read cost. An index is derived metadata: it speeds targeted reads and taxes every write. Nothing in this chapter escapes that bargain.
  • Two OLTP schools. Log-structured (append-only, immutable segments: Bitcask, SSTables/LSM — LevelDB, RocksDB, Cassandra, HBase, Lucene) vs update-in-place (fixed-size pages: B-trees, in every major relational database).
  • The LSM recipe: WAL for durability → sorted memtable in RAM → flush to immutable SSTables → background mergesort compaction → reads check memtable then segments newest-first, with Bloom filters skipping segments that definitely lack the key.
  • The B-tree recipe: fixed 4 KB pages in a balanced tree, O(log n) page reads to any key (3–4 levels in practice), pages overwritten in place, page splits on overflow, WAL + latches for crash safety and concurrency.
  • Rules of thumb: LSM sustains higher write throughput (sequential I/O, often lower write amplification, better compression); B-trees give steadier read latency (no compaction bursts) and each key one canonical location — which transactional range-locking loves. Benchmarks are workload-sensitive: measure your own.
  • Write amplification — one logical write becoming many physical writes — is the shared currency for comparing engines, and it matters most on SSDs and write-heavy workloads.
  • Secondary indexes are key-value indexes with non-unique keys; values live in a heap file (indexes point), a clustered index (row inside the index), or a covering index (some columns inside).
  • OLTP ≠ OLAP. Few-records-by-key vs millions-scanned-few-columns; seek-time-bound vs bandwidth-bound. The warehouse (fed by ETL, shaped as a star schema: fact table + dimensions) exists so analysts can't hurt production.
  • Column storage wins analytics: read only the columns the query touches; compress aggressively (bitmaps + run-length encoding, multiplied by sort order); process vectorized, cache-friendly chunks. Writes come back around to the LSM pattern.
  • Materialized views and data cubes precompute aggregates: instant answers for anticipated shapes, no flexibility beyond them — keep raw data, cube as accelerant.
  • 2nd-edition arc: same physics, new hardware and deployment — RocksDB as workhorse, NVMe-aware designs, storage over object stores (Snowflake/Delta Lake), Parquet/Arrow standardization, DuckDB-style embedded OLAP, and one genuinely new index family: vector indexes (HNSW) for embeddings.

Answer key with explanations
Q1 — c. The index is a derived structure that must be updated on every write; that's overhead no index escapes. The payoff is targeted read speed — which is why databases let you pick indexes based on query patterns rather than indexing everything.
Q2 — b. Bitcask's constraint is that all keys live in an in-memory hash map (values may exceed RAM). Lots of writes across few distinct keys — the cat-video play counter — fits perfectly. (a) fails because hash maps can't range-scan; (c) fails the keys-in-RAM constraint.
Q3 — a. Nothing in an append-only file is ever modified, so deletion is itself an append: a tombstone. Compaction/merging sees it and drops all earlier values for the key. The hash-map trick in (c) would leak disk space forever and break after the map is rebuilt from the log.
Q4 — d. Sequential writes (a), simple crash recovery (b), and no fragmentation (c) are the book's three stated advantages. Indexes are still needed — the hash map, sparse SSTable index, etc. Append-only changes how you write, not whether you need read signposts.
Q5 — d. Sorting enables all three: mergesort-style merging with only a cursor per input in memory; a sparse index because sorting bounds where a key can be; and block compression because reads scan ranges anyway. This trio is the whole case for SSTables over raw hash-indexed logs.
Q6 — b. The WAL is the unsorted on-disk safety copy, written before the in-memory tree. It has exactly one job (rebuild the memtable after a crash) and is discarded at each flush. (d) describes what happens without a WAL.
Q7 — c. A Bloom filter is a probabilistic set summary with one-sided error: "maybe present" or "definitely absent." The painful LSM read is a key that doesn't exist (check memtable + every segment); Bloom filters eliminate most of those disk touches. It stores no values (a) and can't pinpoint segments (b).
Q8 — a. 500⁴ leaf references × 4 KB ≈ 256 TB in four levels. Balance guarantees O(log n) depth; the huge branching factor is what makes the log base so friendly. This is why "3–4 page reads per lookup" covers essentially all real databases.
Q9 — d. Update-in-place means partial multi-page operations are visible after a crash — a split writes two leaves plus the parent, and stopping midway orphans a page. Logging every modification first makes the pages reconstructible. LSM avoids the problem by never modifying files (its WAL protects only the memtable).
Q10 — b. B-trees amplify via WAL + whole-page overwrites (+ splits, + torn-page double writes); LSM amplifies via WAL + flush + a rewrite per compaction pass. On SSDs, blocks tolerate limited overwrites (wear); on write-heavy systems, amplification directly eats the disk bandwidth budget that determines writes/second.
Q11 — a. Flushes and compaction share finite disk bandwidth with foreground writes; the bigger the database, the more compaction needs. Falling behind is silent by default — segments pile up, disk fills, reads check ever more files. B-trees also see compaction-free, steadier tail latencies (no background bursts to queue behind).
Q12 — c. Isolation in many relational databases is implemented with locks on key ranges; those locks attach directly to a B-tree because the tree holds each key exactly once. An LSM engine may have the same key in memtable + several SSTables at once. Details in Chapter 7.
Q13 — b. OLTP: many independent small lookups → dominated by positioning the read (seek). OLAP: few queries, each scanning millions of rows → dominated by how many bytes/second you can pull (bandwidth). This split is why the two worlds diverged into different engines — and it's the bridge to column storage: fewer bytes read per query.
Q14 — a. Both halves matter: I/O proportional to columns-used-not-table-width, and compression (bitmaps, RLE, sort-order runs) shrinking what's left — which also feeds CPU-cache-friendly vectorized processing. (b) is the classic trap: columns can NEVER be sorted independently — position is identity; rows sort as units.
Q15 — d. Each distinct value's bitmap has one bit per row, all files share row order, so set membership per row is pure bitwise OR (AND for conjunctions). This is why bitmap encoding isn't just compression — it's an execution strategy.
Q16 — c. A cube precomputes aggregates over chosen dimensions; anything outside them is unanswerable from the cube. Fast for anticipated queries, rigid for exploration — so warehouses keep raw events and treat cubes (like all materialized views) as a cache, accepting the write-time refresh cost.
