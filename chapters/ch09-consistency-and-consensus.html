Consistency and Consensus

Is it better to be alive and wrong or right and dead? — Jay Kreps, A Few Notes on Kafka and Jepsen (2013)

Chapter 8←8 was the list of everything that can go wrong. The lazy response is to let the whole service fail and show an error. If that's unacceptable, you need fault tolerance: keep working correctly while parts are broken. This chapter is about the algorithms that do that, assuming the worst — packets lost, reordered, duplicated, or delayed; clocks approximate; nodes pausing or crashing at any time.

The strategy is the one that worked for transactions in Chapter 7←7: find general-purpose abstractions with useful guarantees, implement them once, and let applications lean on them. The central abstraction here is consensus — getting all nodes to agree on something — which turns out to be surprisingly hard to do reliably, and surprisingly widely useful once you have it (electing a single leader so there's no split brain, for one). Before tackling it head-on, the chapter maps the space of guarantees: what is possible, what isn't, and what it costs.

FEYNMAN · the whole chapter in one idea Three questions, each harder than it looks, and by the end they turn out to be the same question. Can we make many copies behave like one? That's linearizability — and it is expensive precisely when the network is slow or broken. Can we at least agree on what happened before what? Causality gives a partial order for free; a total order (every event numbered) needs a leader or Lamport timestamps — but knowing the order isn't enough when you must decide right now whether this username is taken, because a lower-numbered claim might still be in flight. Can several machines agree on one irrevocable decision, even as some of them die? That's consensus. And the punchline: a linearizable compare-and-set, a total-order log, atomic commit across nodes, a lock, a uniqueness constraint, and leader election are all equivalent — solve one and you've solved them all. Two-phase commit solves it badly (one coordinator, no fault tolerance); Paxos/Raft/Zab solve it well (majority votes, epochs); ZooKeeper packages the solution so you never have to. Colors as always: ember = writes / proposals, cyan = reads / responses.
consistency-guarantees

Consistency Guarantees

Look at two replicas at the same instant and you'll likely see different data — writes reach different nodes at different times, whatever the replication scheme (Chapter 5←5). Most replicated databases promise at least eventual consistency: stop writing, wait some unspecified time, and all reads return the same value — better named convergence. It is a very weak guarantee. It says nothing about when; until then reads may return anything. Write a value and read it back and you may not see it (Chapter 5←5). That is hard for developers because it's nothing like a variable in a single-threaded program, which a database superficially resembles; and the bugs hide until a network fault or high concurrency.

This chapter explores stronger models. They cost performance or fault tolerance but are easier to use correctly. There is a family resemblance to transaction isolation levels (Chapter 7←7), but they're mostly separate concerns: isolation is about race conditions between concurrent transactions; distributed consistency is about coordinating replicas under delay and failure. Three movements, deeply linked: linearizability, the strongest common model; ordering, causality and total order; and distributed transactions and consensus.

linearizability

Linearizability

Ask two replicas the same question and get two answers — confusing. Wouldn't it be simpler if the database gave the illusion of a single copy? That is linearizability (also atomic consistency, strong, immediate, or external consistency): appear as if there were only one copy of the data, and every operation on it were atomic. As soon as one client's write completes, every client's read must see that value — not a stale cache or lagging replica. Linearizability is a recency guarantee.

What Makes a System Linearizable?

what-makes-a-system-linearizable

"A single copy of the data" needs care to pin down. The book's Figures 9-2 to 9-4 use a register x (one key, one row, one document) and draw each client request as a bar from send to response; a client knows only that its request was processed somewhere in that bar. Operations: read(x) ⇒ v, write(x, v) ⇒ r, and later cas(x, vold, vnew) ⇒ r (compare-and-set). Rules: a read that finishes before a write starts returns the old value; a read that starts after the write completes returns the new value; a read that overlaps the write may return either. But that alone would let readers see the value flip back and forth during the write (a regular register). Linearizability adds one more constraint: there is a single instant at which the value atomically flips, so once any read has returned the new value, every later read must too — even if the write hasn't finished yet.

FEYNMAN · linearizability vs serializability Two words that both sound like "can be put in a line," and they are about different things. Serializability (Chapter 7←7) is an isolation property of transactions touching many objects: the outcome equals some serial order — not necessarily the real-time one. Linearizability is a recency guarantee on a single register: no transactions, no grouping, so it doesn't prevent write skew. Both together is strict serializability (strong one-copy serializability). 2PL and actual serial execution are typically linearizable; SSI←7 is serializable but not linearizable, because it reads from a snapshot that by design excludes recent writes.

Relying on Linearizability

relying-on-linearizability

A stale football score is harmless. Three situations aren't. Locking and leader election: single-leader replication needs exactly one leader; one way is a lock every starting node tries to acquire, and that lock must be linearizable — all nodes must agree who holds it. ZooKeeper and etcd implement such linearizable operations via consensus (with the caveat that their default reads may be stale unless you ask for a quorum read / sync()); Apache Curator adds recipes on top; Oracle RAC uses a linearizable lock per disk page on a dedicated interconnect. Constraints and uniqueness: enforcing "one user per username" or "one file per path" at write time — so one of two concurrent creators gets an error — requires linearizability; it's a lock on the name, or a compare-and-set. Likewise non-negative balances, stock levels, unbooked seats: each needs a single up-to-date value all nodes agree on. (Loosely enforced constraints — overbook and compensate — don't; see Chapter 12→12. Foreign-key and attribute constraints don't either.) Cross-channel timing dependencies: a web server writes a photo to file storage, then puts a "resize this" message on a queue; the resizer fetches the photo. If storage isn't linearizable, the queue can outrun storage's internal replication and the resizer reads an old version or nothing — full-size and thumbnail permanently inconsistent. Two channels (storage + queue), just like replication + Alice's voice. Linearizability is the simplest fix; if you control the second channel, read-your-writes techniques can substitute, with more complexity.

Implementing Linearizable Systems

implementing-linearizable-systems

"Behave as if there's one copy" — the simplest implementation is literally one copy, which isn't fault-tolerant. So: replication. How do Chapter 5's schemes fare? Single-leader (potentially linearizable): reads from the leader or from synchronously updated followers can be linearizable (partitioning doesn't hurt — it's a single-object guarantee), but not every such database is, by design (snapshot isolation) or by bug; and reading from "the leader" assumes you know who the leader is — a deluded ex-leader serving requests breaks linearizability (Chapter 8←8), and asynchronous failover can lose committed writes. Consensus algorithms (linearizable): like single-leader replication plus the machinery that prevents split brain and stale replicas — ZooKeeper and etcd. Multi-leader (not linearizable): concurrent writes on several nodes, asynchronously replicated, produce conflicts — the very symptom of not having a single copy. The Cost of Linearizability

the-cost-of-linearizability

Multi-leader replication suits multi-datacenter deployments (Chapter 5←5). Cut the link between two datacenters, with clients still able to reach each one. Multi-leader: each datacenter keeps working; writes queue and exchange when the link returns. Single-leader: the leader is in one datacenter, and every write and every linearizable read must go to it — so clients attached to the follower datacenter can't write or read linearizably until the link is repaired. They can read stale data or get an error; either way, if the application needs linearizability, it is unavailable in that datacenter.

The CAP theorem

That trade-off — linearizable and unavailable under partition, or available and not linearizable — is the CAP theorem, named by Eric Brewer in 2000 though known since the 1970s. It started as a rule of thumb without precise definitions, meant to push database designers beyond linearizable shared-storage clusters toward shared-nothing systems suited to web scale — and it deserves credit for the NoSQL culture shift. But the book calls it unhelpful. "Pick 2 of 3" is misleading: partitions are a fault, not a choice; they will happen. When the network works you get both consistency and availability; when it faults you choose — so a better name is "either Consistent or Available when Partitioned." Definitions of availability in CAP discussions contradict each other, and many fault-tolerant "highly available" systems don't meet CAP's idiosyncratic one. Formally it covers one consistency model (linearizability) and one fault (network partitions among live nodes), saying nothing about delays, dead nodes, or other trade-offs. Influential historically; little practical value now, superseded by more precise impossibility results. The CP/AP labels are best avoided.

Linearizability and network delays

Surprisingly few systems are actually linearizable — not even RAM on a multi-core CPU: a write on one core isn't guaranteed visible to a read on another core shortly after, without a memory barrier, because each core has its own cache and store buffer, asynchronously flushed to main memory. Several copies, asynchronously updated: linearizability lost. CAP can't explain that choice — we assume reliable communication inside one machine — the reason is performance. The same holds for most databases that skip linearizability: performance, not fault tolerance; and it's slow all the time, not just during faults. Could a cleverer algorithm fix that? No: Attiya and Welch proved linearizable read/write response time is at least proportional to the uncertainty in network delay (Chapter 8←8). On real networks that is inevitably high. Weaker models can be much faster, which is why Chapter 12→12 looks for correctness without linearizability.

FEYNMAN · why "one copy" must be slow Pretending there is one copy means that before answering any read you must be sure no write anywhere else has completed that you haven't heard about. On a network whose delay is uncertain by u, being sure costs you on the order of u every time — not sometimes, always. It's the same reason your CPU cores don't share one perfectly coherent memory: waiting for every other core before every read would throw away most of the speed. Linearizability isn't a feature you lose when the network breaks; it's a tax you pay whenever the network is merely uncertain, which is always.

ordering-guarantees

Ordering Guarantees

A linearizable register acts as if every operation takes effect atomically at one point in time — which implies a well-defined order of operations. Ordering has been everywhere in this book: the leader's job in single-leader replication is to fix the order of writes in the log (no leader ⇒ conflicts, Chapter 5←5); serializability is about transactions behaving as if run in some order (Chapter 7←7); and timestamps were an attempt to impose order on a disorderly world (Chapter 8←8). There are deep connections between ordering, linearizability, and consensus, and this section — the most abstract in the book — draws them.

Ordering and Causality

ordering-and-causality

Ordering keeps coming up because it preserves causality. The book's back-catalogue of examples: seeing an answer before its question (consistent prefix reads←5); an update overtaking the insert of the row it updates in multi-leader replication; the happened-before relation of Chapter 5←5 (A before B, B before A, or concurrent — no causal link either way); a consistent snapshot meaning consistent with causality — if it has the answer it has the question, and read skew is a causality violation; write skew in the on-call example, where going off call depends causally on who was observed on call, and SSI catches it by tracking those dependencies; and Alice's exclamation, causally downstream of the score, which Bob's stale read contradicted. Cause precedes effect; a message is sent before it is received; chains of read-then-write define the causal order. A system that obeys it is causally consistent — snapshot isolation is an example.

The causal order is not a total order

A total order lets any two elements be compared (natural numbers: 13 > 5). Sets are only partially ordered: {a, b} vs {b, c} is incomparable. Consistency models mirror this. Linearizability gives a total order — a single copy, atomic operations, so any two operations can be ranked; a single timeline, no concurrency at all. Causality gives a partial order: causally related events are ordered; concurrent ones are incomparable. Concurrency means the timeline branches and merges — like Chapter 5's version graphs, or a Git history with its straight runs, branches, and merge commits.

Linearizability is stronger than causal consistency

Linearizability implies causality: any linearizable system preserves causal order automatically, even across multiple communication channels, with no timestamps passed around — that's what makes it simple and appealing. But it costs performance and availability, especially with large network delays, so some systems abandon it. The middle ground: causal consistency without linearizability. Causal consistency is the strongest model that doesn't slow down under network delay and stays available under network faults — CAP doesn't apply. Many systems that seem to need linearizability really only need causal consistency, and research databases exploring this (with eventual-consistency-like performance) are a promising direction, though little has reached production.

Capturing causal dependencies

To preserve causality a replica must process an operation only after everything that happened before it; if a predecessor is missing, the operation waits. Determining "happened before" means describing a node's knowledge — "did the node know X when it wrote Y?" — the kind of question asked in a fraud investigation. The techniques generalize version vectors←5 from a single key to the whole database: the application tells the database which version it read (as Chapter 5's client did on every write), just as SSI records which data each transaction read so it can check at commit whether it's still current.

Sequence Number Ordering

sequence-number-ordering

Tracking every causal dependency is impractical — clients read a lot before writing, and it's unclear which reads the write depends on. Instead, order events with sequence numbers or timestamps from a logical clock: not a quartz oscillator but a counter incremented per operation. They are compact and give a total order; and we can make that total order consistent with causality — if A happened before B, A gets the smaller number; concurrent operations are ordered arbitrarily. (A random UUID per operation is also a total order, and useless: it says nothing about what happened first.) In single-leader replication the replication log is exactly this: the leader increments a counter per write, and a follower applying the log in order is always causally consistent, even when lagging.

Noncausal sequence number generators

Without a single leader — multi-leader, leaderless, or partitioned — how do you generate them? Three common ways, all faster and more scalable than a single counter, and all inconsistent with causality. Independent per-node counters (odd/even, or node-ID bits): nodes process different rates, so one counter lags and an odd number can't be compared causally with an even one. Physical-clock timestamps: clock skew, as in Figure 8-3, gives a causally later write a lower timestamp (Spanner's commit wait fixes this, but needs an uncertainty metric most clocks lack). Preallocated blocks (A gets 1–1,000, B gets 1,001–2,000): a causally later operation can land in the lower block.

Lamport timestamps

There is a simple generator that is consistent with causality: Lamport timestamps (Lamport, 1978 — one of the most-cited papers in the field). Each node has a unique ID and a counter of operations processed; the timestamp is the pair (counter, node ID), made unique by the ID and totally ordered — bigger counter wins, ties broken by node ID. That alone is the odd/even scheme. The key idea: every node and every client tracks the maximum counter it has seen and sends it with every request; a node receiving a bigger maximum jumps its own counter forward to it. Every causal dependency thus produces a larger timestamp.

Timestamp ordering is not sufficient

Lamport timestamps totally order operations causally — yet they can't solve the unique username problem. After the fact it works: collect all creation attempts, the lowest timestamp wins. But a node that has just received a request must decide now, and it doesn't know whether another node is concurrently creating the same username with a lower timestamp. To be sure it would have to ask every other node — and if one is down or unreachable, everything halts. Not fault-tolerant. The problem: the total order only emerges once all operations are collected; unknown operations from other nodes may still need inserting earlier in the order. To enforce uniqueness you must also know when the order is finalized — that no one can still slip a claim in ahead of yours. That is the job of total order broadcast.

Total Order Broadcast

total-order-broadcast

On one CPU core a total order is trivial — execution order. Across nodes, getting everyone to agree on one total order is the hard part. Single-leader replication does it by funnelling all operations through one node; the challenges are scaling beyond one leader's throughput and failover when the leader dies (Chapter 5←5). The distributed-systems name for this problem is total order broadcast or atomic broadcast (nothing to do with ACID atomicity). It is a message protocol with two safety properties that must hold even under node and network faults: reliable delivery — a message delivered to one node is delivered to all; and totally ordered delivery — every node receives the messages in the same order. Messages won't flow during a network interruption, but the algorithm retries until they do, and still in order. (Partitioned databases with a leader per partition typically order only within a partition; total order across partitions needs extra coordination.)

Using total order broadcast

ZooKeeper and etcd implement total order broadcast — a hint of its link to consensus. It is exactly what replication needs: each message a write, every replica applying the same writes in the same order — state machine replication (Chapter 11→11). It implements serializable transactions too: each message a deterministic stored procedure, every partition and replica executing them in the same order (Chapter 7←7). Crucially, the order is fixed at delivery: no message may be retroactively inserted earlier once later ones have been delivered — that's what makes it stronger than timestamp ordering. Another view: total order broadcast is a log (replication log, transaction log, WAL); delivering a message is appending to it, and every node reads the same sequence. Hence also a lock service with fencing tokens: each acquire request is a log entry, its sequence number the monotonically increasing token (ZooKeeper's zxid).

Implementing linearizable storage using total order broadcast

Linearizability has a total order; is it the same thing as total order broadcast? Not quite. Total order broadcast is asynchronous — messages arrive reliably in a fixed order, but with no promise about when, so a recipient may lag; linearizability is a recency guarantee. But you can build linearizable storage on top of it. Implementing total order broadcast using linearizable storage

And the other direction: given a linearizable register with atomic increment-and-get (or CAS), build total order broadcast — for each message, increment-and-get, attach the result as a sequence number, send to all nodes (resending losses), and have recipients deliver in sequence-number order. Unlike Lamport timestamps these numbers have no gaps: a node holding message 4 that receives message 6 knows it must wait for 5. That gaplessness is the difference between total order broadcast and timestamp ordering. How hard is a linearizable increment-and-get? Trivial without faults — a variable on one node. Handling that node's network interruptions and failures inevitably leads you to a consensus algorithm. Indeed, it can be proved that a linearizable CAS/increment register, total order broadcast, and consensus are all equivalent — a solution to any one transforms into a solution to the others.

FEYNMAN · a total order, and knowing it's final Two people mail applications for the same license plate. Sorting the applications by postmark gives a total order — but the clerk can't issue the plate to the earlier postmark until they're sure no envelope with an earlier postmark is still in the mail. Lamport timestamps are postmarks: they order everything correctly and tell you nothing about what's still in transit. Total order broadcast is a numbered ticket dispenser at the counter: you get ticket 44, you watch the screen until 44 is called, and by then you know 43 was called first and nothing can ever be called between them. The ticket dispenser that keeps working when the counter staff keep collapsing is consensus.

Distributed Transactions and Consensus

Consensus — getting several nodes to agree on something — is one of the most fundamental problems in distributed computing and looks easy; many broken systems were built by people who believed that. It arrives this late because it needs everything before it: replication, transactions, system models, linearizability, total order broadcast. Two headline uses: leader election (all nodes must agree who the leader is, or split brain diverges the data), and atomic commit (a transaction spanning nodes must commit everywhere or abort everywhere — formally slightly different from consensus, since it may only commit if all vote yes, but reducible to it).

FEYNMAN · the impossibility of consensus (and why we do it anyway) The FLP result (Fischer, Lynch, Paterson) proves no algorithm can always reach consensus if a node might crash. Since nodes do crash, consensus is impossible — and yet this section is full of consensus algorithms. The catch: FLP is proved in the asynchronous model (Chapter 8←8), for deterministic algorithms with no clocks or timeouts. Allow timeouts — even unreliable suspicion of crashed nodes — or just random numbers, and consensus becomes solvable. FLP is deep theory; in practice, consensus is achieved routinely.

Atomic Commit and Two-Phase Commit (2PC)

atomic-commit-and-two-phase-commit-2pc

Atomicity (Chapter 7←7) keeps failed transactions from littering the database with half-done state — vital for multi-object transactions and for secondary indexes, which must stay consistent with the primary data. On a single node the storage engine does it: write the data durably (WAL), then append a commit record; on crash recovery, a transaction with a commit record on disk is committed, otherwise rolled back. The deciding instant is when the disk finishes writing that record — one device makes the commit atomic. Across nodes — a multi-object transaction in a partitioned database, or a term-partitioned index (Chapter 6←6) — simply sending "commit" to everyone fails: one node hits a constraint violation while another commits; one request is lost and times out; one node crashes before its commit record is complete. Nodes diverge, and a commit on one node can't be retracted because it's already visible to other transactions (the basis of read committed←7). A node may commit only once it is certain all others will too. Commit is irrevocable (compensating transactions are a separate, application-level matter).

Introduction to two-phase commit

2PC achieves atomic commit across nodes: all commit or all abort. A classic algorithm, used inside some databases and exposed to applications as XA transactions (Java Transaction API) or WS-AtomicTransaction. It is not two-phase locking — 2PL is about serializable isolation (Chapter 7←7); think of them as unrelated. 2PC adds a component: the coordinator (transaction manager), often a library inside the application process (a Java EE container), sometimes a separate service (Narayana, JOTM, BTM, MSDTC). The application reads and writes on several participant nodes as usual; at commit time the coordinator runs phase 1 — a prepare request to every participant ("can you commit?") — and then phase 2: if all said yes, commit to all; if any said no, abort to all. The book's analogy is a wedding: the minister asks each party "do you?", and only after both "I do"s pronounces them married.

Three-phase commit

Because it can block on a crashed coordinator, 2PC is a blocking atomic commit protocol. A nonblocking alternative, 3PC, exists in theory but assumes bounded network delay and response times; with unbounded delays and pauses it can't guarantee atomicity. Nonblocking atomic commit needs a perfect failure detector, and on an unbounded-delay network a timeout isn't one — a request can time out with no node crashed. So 2PC endures despite the coordinator problem.

Distributed Transactions in Practice

distributed-transactions-in-practice

Distributed transactions have a mixed reputation: an important safety guarantee, but also operational trouble, killed performance, and overpromising; many cloud services skip them. MySQL's distributed transactions are reported over 10× slower than single-node ones, mostly from the extra fsyncs for crash recovery and the extra round trips. Two very different things get conflated. Database-internal distributed transactions — all participants run the same database (VoltDB, MySQL Cluster NDB) — can use any protocol and optimizations, and often work well. Heterogeneous distributed transactions — two vendors' databases, or a database plus a message broker — must achieve atomic commit across unrelated systems, and that is far harder.

Exactly-once message processing

Heterogeneous transactions integrate systems powerfully: acknowledge a message from a queue if and only if the database transaction that processed it committed, by committing the ack and the writes atomically. If either fails, both abort and the broker redelivers; the message is effectively processed exactly once, retries and all (Chapter 11→11). It only works if every affected system speaks the same atomic commit protocol — an email server that doesn't do 2PC may send the email twice.

XA transactions

X/Open XA (1991) is the standard for 2PC across heterogeneous technologies, supported by PostgreSQL, MySQL, DB2, SQL Server, Oracle, and brokers like ActiveMQ, HornetQ, MSMQ, IBM MQ. It is not a network protocol — it's a C API for talking to a transaction coordinator (Java's JTA, via JDBC and JMS drivers). An XA-aware driver asks the coordinator whether an operation belongs to a distributed transaction and exposes callbacks for prepare/commit/abort. The coordinator is usually a library inside the application process, tracking participants and logging decisions to local disk. If the application process or its machine dies, the coordinator dies with it, prepared transactions are stuck in doubt, and recovery requires restarting that server so the library can read its log and drive the callbacks — the database can't contact the coordinator itself.

Holding locks while in doubt

Why care about in-doubt transactions? Locks. Participants hold row-level exclusive locks on modified rows (and, under 2PL, shared locks on read rows) until commit or abort. An in-doubt transaction holds them for as long as it's in doubt — 20 minutes if the coordinator takes 20 minutes to restart, forever if its log is lost until an administrator intervenes. Other transactions can't write those rows (maybe can't read them), so large parts of the application can become unavailable.

Recovering from coordinator failure

In theory a restarted coordinator recovers cleanly from its log. In practice orphaned in-doubt transactions happen — log lost or corrupted by a bug — and they sit forever holding locks; even rebooting the database won't release them, since a correct 2PC must preserve in-doubt locks across restarts. An administrator must examine each participant, find which have already committed or aborted, and apply the same outcome to the rest — manual, stressful work during a production outage. Many XA implementations offer heuristic decisions: a participant unilaterally commits or aborts an in-doubt transaction. "Heuristic" is a euphemism for probably breaking atomicity; it's for catastrophes only.

Limitations of distributed transactions

The key realization: the coordinator is itself a database (it stores transaction outcomes) and deserves the same care. Yet many coordinators aren't replicated — a single point of failure for the whole system. Application servers meant to be stateless become stateful when the coordinator's log lives on their disk — the log is now durable system state as important as the databases. XA is a lowest common denominator: it can't detect deadlocks across systems and doesn't work with SSI, since both would need cross-system protocols. Even database-internal 2PC (which can do distributed SSI) needs all participants to respond, so any broken part fails the transaction: distributed transactions amplify failures, the opposite of fault tolerance. Alternatives that keep systems consistent without heterogeneous 2PC come in Chapters 11 and 12→12.

FEYNMAN · 2PC is consensus with a dictator Two-phase commit does reach agreement: everyone ends up with the same decision. But look who decides — one coordinator, and if that coordinator is unavailable, nobody can decide anything, ever, while holding locks on the rows in question. That is the shape of a consensus algorithm that satisfies agreement, integrity, and validity but not termination: a dictatorship. The section that follows is about replacing the dictator with an elected leader who can be replaced when they stop answering — which requires that the electorate, not the leader, be the source of truth.

Fault-Tolerant Consensus

fault-tolerant-consensus

Formally: one or more nodes propose values, and the algorithm decides one of them — several customers grab the last seat, each node proposes its customer, the decision names the winner. A consensus algorithm must satisfy four properties:

PropertyStatementKindWhat it rules out
Uniform agreementNo two nodes decide differentlysafetysplit brain — the core idea
IntegrityNo node decides twicesafetychanging your mind after deciding
ValidityIf a node decides v, some node proposed vsafetythe trivial "always decide null" algorithm
TerminationEvery non-crashed node eventually decideslivenesssitting around forever; i.e. this is fault tolerance

Without fault tolerance the first three are easy: hardcode a dictator. That is 2PC — coordinator down, in-doubt participants can't decide. Termination says the algorithm must make progress even when nodes fail — and in the consensus model a crashed node is gone forever (buried under 30 feet of mud), so any algorithm that waits for a node to recover fails termination; 2PC does. Of course, if all nodes crash nothing can decide; it can be proved that consensus needs at least a majority of nodes working to guarantee termination — that majority forms a quorum. Most implementations still uphold the safety properties even when a majority is down or the network is severed: an outage can stop decisions, never corrupt them. And most assume no Byzantine faults (Chapter 8←8); Byzantine-tolerant consensus exists for fewer than one-third faulty nodes.

Consensus algorithms and total order broadcast

The best-known fault-tolerant algorithms: Viewstamped Replication, Paxos, Raft, and Zab — similar in spirit, not identical, and hard to implement (don't roll your own). Most don't decide single values; they decide a sequence — i.e. they are total order broadcast algorithms. Total order broadcast is equivalent to repeated rounds of consensus, one decision per message: agreement ⇒ same messages in the same order; integrity ⇒ no duplicates; validity ⇒ nothing fabricated; termination ⇒ nothing lost. VSR, Raft, and Zab implement total order broadcast directly since that's more efficient than one-value-at-a-time; Paxos's version is Multi-Paxos.

Single-leader replication and consensus

Isn't single-leader replication total order broadcast? Why didn't Chapter 5 need consensus? Because of how the leader is chosen. A leader configured by humans is a dictatorship: only it decides write order, and if it dies, no writes until operators pick another — fine in practice, but it fails termination (progress needs a human). Automatic failover gets closer — but all nodes must agree who the leader is, so you need consensus to elect a leader; and if consensus algorithms are total order broadcast, and total order broadcast is single-leader replication, and single-leader replication needs a leader… to elect a leader we need a leader; to solve consensus we must first solve consensus.

Epoch numbering and quorums

The way out: the protocols use a leader but don't guarantee it is unique — only unique within an epoch. The epoch number (ballot in Paxos, view in VSR, term in Raft) is incremented every time the leader is suspected dead and a vote elects a new one; epochs are totally ordered, and if two leaders from different epochs conflict, the higher epoch wins. Before deciding anything, a leader must check it hasn't been ousted by a higher-epoch leader — and, per Chapter 8←8, it can't trust its own belief. So for every decision it sends the proposal to the others and waits for a quorum (usually a majority) to vote in favor; a node votes yes only if it knows of no higher epoch. Two rounds of voting — elect a leader, then approve each proposal — and the key insight is that the two quorums must overlap: if a proposal passes, at least one voter also took part in the most recent election, so if no voter reports a higher epoch, the leader knows no newer election has happened and may safely decide.

Limitations of consensus

Consensus is a breakthrough — concrete safety in an uncertain world, while still making progress with a majority up — and it yields total order broadcast and therefore fault-tolerant linearizable operations. But it isn't used everywhere, because: voting on every proposal is a form of synchronous replication (Chapter 5←5), and many databases prefer asynchronous speed at the risk of losing committed data on failover; a strict majority is required — 3 nodes to survive 1 failure, 5 for 2 — and the minority side of a network split is blocked; most algorithms assume a fixed membership, and dynamic membership extensions are less well understood; failure detection by timeouts means that on high-latency or geo-distributed networks nodes falsely suspect the leader, and frequent elections can leave the system electing more than working; and some algorithms are fragile in specific ways — Raft has been shown to bounce leadership endlessly or force the leader to resign repeatedly when a single link is flaky. Robustness to unreliable networks is still an open research problem.

Membership and Coordination Services

ZooKeeper and etcd are described as "distributed key-value stores" or "coordination and configuration services," and their API looks like a database — read and write keys, iterate. So why the elaborate consensus machinery? You rarely use ZooKeeper directly — it's a poor general-purpose database — but HBase, Hadoop YARN, OpenStack Nova, and Kafka all rely on it. It holds a small amount of data, in memory (written to disk for durability), replicated to every node by fault-tolerant total order broadcast. Modeled on Google's Chubby lock service, it adds a set of features that together make distributed coordination tractable:

Allocating work to nodes

Two textbook uses. Choosing a leader or primary among several instances of a service — single-leader databases, but also job schedulers and other stateful systems — with automatic takeover when it fails. Assigning partitions to nodes for any partitioned resource (database, message streams, file storage, actor system): rebalance onto new nodes as they join (Chapter 6←6), take over work when nodes fail. Done with atomic operations, ephemeral nodes, and notifications, the application recovers from faults without human intervention. It isn't easy even with Apache Curator's recipes, but it beats implementing consensus from scratch, which has a poor track record. Note the scale trick: an application may grow to thousands of nodes, and majority votes across thousands would be hopeless; ZooKeeper runs on a fixed 3 or 5 nodes, votes among those, and serves many clients — outsourced consensus, ordering, and failure detection. Its data changes slowly ("10.1.1.23 leads partition 7" — minutes or hours), not thousands of times per second; replicating fast-changing application state is a job for other tools (Apache BookKeeper).

Service discovery

ZooKeeper, etcd, and Consul are also used for service discovery — which IP serves this service? — because in the cloud VMs come and go and services register their endpoints on startup. But discovery doesn't obviously need consensus: DNS, the traditional answer, is heavily cached, absolutely not linearizable, and nobody minds slightly stale results — what matters is that it stays available and robust to interruptions. Leader election, however, does need consensus, and if the consensus system already knows the leader, it can help other services find it; some offer read-only caching replicas that receive the decision log asynchronously without voting, serving reads that don't need to be linearizable.

Membership services

ZooKeeper sits in a long line of research on membership services, back to the 1980s and air-traffic-control systems: determine which nodes are currently live members of the cluster. Unbounded delays make failure detection unreliable (Chapter 8←8), but coupling it with consensus lets nodes agree on who's alive. A live node may still be wrongly declared dead — yet agreement on membership is invaluable: "the leader is the lowest-numbered member" only works if everyone agrees who the members are.

FEYNMAN · why ZooKeeper is a database that isn't for your data ZooKeeper is a notary's office with three or five notaries who vote on every stamp. You would never keep your inventory there — each stamp costs a round of voting. But you go there for the handful of facts that must be agreed rather than merely stored: who is in charge of partition 7, who holds this lock, who is still alive. The notaries also keep a numbered ledger (fencing tokens), notice when a client stops showing up (sessions and ephemeral nodes), and call you when a fact you care about changes (watches). Everything else in your system can then be fast and sloppy, because the few decisions that have to be right are outsourced to the office that's slow and right.

Core takeaways

  • Eventual consistency (convergence) is the weakest useful guarantee: no bound on when, and reads may return anything meanwhile. Stronger models cost performance or fault tolerance but are easier to use correctly. Consistency models (replica coordination) and isolation levels (concurrent-transaction races) are related but distinct.
  • Linearizability = the illusion of a single copy with atomic operations: a recency guarantee. Once any read returns a new value, all later reads must; every operation takes effect at one instant inside its request/response window, and joining those instants gives a valid history that never moves backward in time. Testable from recorded timings.
  • Linearizability ≠ serializability: the latter orders multi-object transactions in some order; the former is per-register recency. Both = strict serializability. 2PL and serial execution are linearizable; SSI is not (snapshot reads).
  • Where it's required: locks and leader election (ZooKeeper/etcd), hard uniqueness constraints (one up-to-date value everyone agrees on), and cross-channel dependencies (file storage + message queue racing).
  • Implementations: single-leader can be linearizable (leader or sync-follower reads, if you really know the leader); consensus systems are; multi-leader isn't; Dynamo-style quorums aren't even with w + r > n (a reader can see the new value while a later reader sees the old) unless read repair is synchronous — and CAS needs consensus regardless.
  • The cost: under a network fault, a linearizable system must make cut-off replicas unavailable; a non-linearizable one can keep every replica serving. That is CAP — better said "Consistent or Available when Partitioned"; the book calls "pick 2 of 3" misleading and CAP largely unhelpful. Beyond faults, linearizability is slow always: response time ∝ network-delay uncertainty (Attiya–Welch), the same reason multi-core RAM isn't linearizable.
  • Causality is a partial order (branches and merges; concurrent ops incomparable); linearizability is a total order (one timeline). Linearizability implies causal consistency; causal consistency is the strongest model that stays fast and available under network problems, and often all you actually need.
  • Sequence numbers from a logical clock give a compact total order. Per-node counters, wall-clock timestamps, and block allocation are not causally consistent; Lamport timestamps (counter, node ID) are, by carrying the max counter seen on every message and jumping forward — but they can't distinguish concurrent from dependent (version vectors can).
  • Timestamps aren't enough for uniqueness: the total order only emerges after all operations are known; you must know when it's final. That is total order broadcast: reliable, same-order delivery to all nodes, order fixed at delivery — i.e. a replicated log. It gives state machine replication, serializable deterministic transactions, and fencing tokens.
  • Log ⇄ linearizable storage: CAS via the log (append a claim, wait for it to come back, first claim wins); linearizable reads by sequencing through the log, syncing to the latest position, or sync replicas. Conversely, increment-and-get builds a gapless log. Linearizable CAS, total order broadcast, and consensus are equivalent.
  • 2PC: prepare (participants fsync and promise) → coordinator logs the decision (commit point) → commit/abort to all, retried forever. Two points of no return. A crashed coordinator leaves participants in doubt, holding locks; 3PC needs a perfect failure detector, so 2PC persists. Not 2PL.
  • XA in practice: heterogeneous 2PC (exactly-once queue + DB processing) via a C API and a coordinator library on the app server; slow (fsyncs, round trips), coordinator is an unreplicated single point of failure and makes "stateless" servers stateful, orphaned in-doubt transactions need manual or heuristic (atomicity-breaking) resolution, and it amplifies failures. Database-internal distributed transactions fare better.
  • Consensus = uniform agreement, integrity, validity (safety) + termination (liveness, needs a majority alive). FLP forbids it only in the pure asynchronous model. VSR, Paxos, Raft, Zab decide sequences (total order broadcast). They use a leader but guarantee uniqueness only per epoch; every decision needs a quorum that must overlap the election quorum, so a stale leader is always discovered. Unlike 2PC: elected leader, majority not unanimity, recovery process.
  • Limits: synchronous-replication cost; strict majority (3 for 1 failure, 5 for 2); mostly fixed membership; timeout-based detection causes leadership churn on flaky networks (Raft's known edge cases).
  • ZooKeeper/etcd: small in-memory data replicated by total order broadcast, plus linearizable CAS (locks/leases), zxid ordering (fencing), session-based failure detection (ephemeral nodes), and watches — outsourced consensus for leader election and work assignment among 3–5 voters serving thousands of clients. Service discovery doesn't need consensus (DNS is fine); membership agreement does.
  • 2nd-edition arc (Ch 10, significantly expanded): Raft covered properly (etcd alongside ZooKeeper); shared-log architectures (CORFU, Tango, Delos) and Calvin-style deterministic transactions; distributed ID generation (Snowflake, ULID) tied to logical clocks; CAP further retired in favour of strict serializability / external consistency as documented by Spanner and CockroachDB; isolation vs consistency hierarchies clearly layered.
