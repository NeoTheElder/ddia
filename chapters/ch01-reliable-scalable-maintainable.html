Reliable, Scalable, and Maintainable Applications

The Internet was done so well that most people think of it as a natural resource like the Pacific Ocean, rather than something that was man-made. When was the last time a technology with a scale like that was so error-free? — Alan Kay, in interview with Dr Dobb's Journal (2012)

Most applications today are data-intensive, not compute-intensive: raw CPU is rarely the limit — the amount of data, its complexity, and how fast it changes are. And such applications are assembled from a handful of standard building blocks: databases (store data, find it later), caches (remember expensive results), search indexes (keyword search and filtering), stream processing (send a message to another process, handled asynchronously), batch processing (periodically crunch accumulated data). That list sounds painfully obvious precisely because these abstractions are so successful — nobody writes a storage engine from scratch when a database will do.

But there are many databases with different characteristics because applications have different requirements; many ways to cache, many ways to index. You still have to choose, and combining tools when no single one does the job is hard. This chapter names the three things every choice is trying to achieve — reliability, scalability, maintainability — and gives you precise ways to think about each, so the rest of the book's techniques have something to aim at.

FEYNMAN · the whole chapter in one idea Three questions, asked of any system: Does it keep working when things break? (reliability). Does it keep working when it gets 10× bigger? (scalability). Can the people who inherit it keep working on it? (maintainability). Everyone nods at these words; the chapter's real content is turning each vague word into things you can measure and design for — faults vs failures, load parameters and percentiles, operability/simplicity/evolvability. As in the whole book: ember marks the write path, cyan the read path.

Thinking About Data Systems

Why lump databases, queues, and caches together as "data systems" when they're such different tools? Two reasons. First, the categories have blurred: Redis is a datastore also used as a message queue; Kafka is a message queue with database-like durability. New tools no longer fit the old boxes. Second, one tool is often not enough: demanding applications break their work into tasks each handled by a specialized tool, stitched together by application code — and then the application code owns the job of keeping them consistent:

Many things shape a design — the team's skills, legacy dependencies, delivery timescales, risk tolerance, regulation. The book fixes on three concerns that matter for most systems:

  • Reliability — the system keeps working correctly (right function, at the desired performance) even in adversity: hardware or software faults, even human error.
  • Scalability — as the system grows (data volume, traffic, complexity), there are reasonable ways to deal with the growth.
  • Maintainability — over time many different people (engineering and operations) will work on it, maintaining current behavior and adapting to new cases, and all of them should be able to work productively.

reliability

Reliability

Intuitively, reliable software: does what the user expected; tolerates the user making mistakes or using it in unexpected ways; performs well enough for the expected load and data; prevents unauthorized access and abuse. If all that is "working correctly," then reliability is continuing to work correctly even when things go wrong.

The things that go wrong are faults; systems that anticipate and cope with them are fault-tolerant or resilient. "Fault-tolerant" slightly oversells it — no system tolerates every fault (if Earth is swallowed by a black hole, tolerance requires hosting in space; good luck with that budget line). You tolerate certain types of faults.

FEYNMAN · why you should break your own system on purpose Counterintuitively, fault-tolerant systems benefit from raising the fault rate deliberately — randomly killing processes without warning, à la Netflix's Chaos Monkey. Most critical production bugs are actually bad error handling: code paths that only run when something has already gone wrong, and therefore never get exercised. Killing things on purpose keeps the fault-tolerance machinery continually tested, so you can trust it when faults arrive on their own. It's a fire drill: nobody learns the exits during a real fire.

One caveat: prevention beats cure where no cure exists — security, above all. Once an attacker has read sensitive data, that can't be undone. This book mostly deals with faults that can be cured, in three families:

Hardware Faults

hardware-faults

Disks crash, RAM goes bad, the grid blacks out, someone unplugs the wrong cable. At scale these aren't rare events, they're weather: hard disks have a mean time to failure of roughly 10–50 years, so a cluster of 10,000 disks loses about one disk per day. The first response is hardware redundancy — RAID, dual power supplies, hot-swappable CPUs, batteries and diesel generators — which makes total failure of a single machine rare, and for most applications restoring a backup onto a new machine quickly was good enough. Only the rare high-availability application needed multi-machine redundancy.

Two shifts changed that. Data volumes pushed applications onto many machines, multiplying the fault rate proportionally; and cloud platforms like AWS routinely make VM instances vanish without warning, prioritizing elasticity over single-machine reliability. Hence the move to software fault-tolerance — systems that tolerate the loss of whole machines — in preference to or on top of hardware redundancy. It has an operational bonus too: a single-server system needs planned downtime to reboot for a security patch; a machine-loss-tolerant system patches one node at a time with no downtime — a rolling upgrade, which Chapter 4→4 shows has consequences for how you encode data.

Software Errors

software-errors

Hardware faults are mostly random and independent — one disk dying says little about the next (weak correlations aside, like a hot rack). Software faults are the opposite: systematic errors, correlated across nodes, and therefore far more likely to cause outright failures. Examples: a bug that crashes every application server given one bad input (the 2012 leap second hung many services simultaneously via a Linux kernel bug); a runaway process eating a shared resource — CPU, memory, disk, bandwidth; a dependency that slows down, hangs, or starts returning corrupted responses; and cascading failures, where a small fault triggers another, and another.

These bugs lie dormant until an unusual set of circumstances reveals a hidden assumption about the environment — usually true, until one day it isn't. There's no quick fix, only many small things: think carefully about assumptions and interactions; test thoroughly; isolate processes; let processes crash and restart; measure, monitor, analyze production behavior; and when a system promises a guarantee (a queue's messages-in equals messages-out), have it check itself continuously and alert on discrepancy.

2ND EDITION · what a decade of production taught us about faults The 2nd edition deepens this section with post-2017 production research: metastable failures (a system pushed into a bad state that sustains itself even after the trigger is gone — retry storms are the classic), backoff with jitter, circuit breakers and load shedding as the standard defenses against cascades; and on the hardware side, fail-slow hardware (degraded but not dead — worse than a clean crash), silent data corruption from CPUs that miscompute ("Cores That Don't Count"), and SSD/DRAM field-failure studies.

Human Errors

human-errors

Humans design, build, and operate the systems, and humans — with the best intentions — are unreliable. One study of large internet services found operator configuration errors were the leading cause of outages, with hardware faults involved in only 10–25%. Reliability despite unreliable humans comes from combining approaches:

  • Minimize opportunities for error — abstractions, APIs, and admin interfaces that make the right thing easy and the wrong thing awkward. Too restrictive, though, and people work around them, negating the benefit; the balance is delicate.
  • Decouple where mistakes happen from where they cause failures — full-featured non-production sandboxes with real data, where people can explore safely.
  • Test at every level — unit through whole-system integration and manual tests; automated tests earn their keep on corner cases that rarely arise normally.
  • Make recovery quick and easy — fast config rollback, gradual code rollout so bugs hit few users, tools to recompute data when the old computation was wrong.
  • Detailed, clear monitoring — performance metrics and error rates; in other engineering fields, telemetry. Once the rocket has left the ground, telemetry is how you know what's happening — early warning of violated assumptions, and the evidence for diagnosis afterward.
  • Good management and training — important, and beyond the book's scope.

How Important Is Reliability?

how-important-is-reliability

Not just nuclear plants and air traffic control. Business-application bugs cost productivity (and legal risk when figures are misreported); e-commerce outages cost revenue and reputation. Even in "noncritical" apps there's a duty to users: picture a parent who keeps every photo and video of their children in your photo app — and the database is suddenly corrupted. Would they even know how to restore a backup? Sometimes you consciously trade reliability for development cost (a prototype for an unproven market) or operational cost (razor-thin margins) — but be very conscious of when you're cutting the corner.

scalability

Scalability

Reliable today doesn't mean reliable tomorrow — the common cause of degradation is increased load: 10k concurrent users become 100k, 1M become 10M; data volumes balloon. Scalability is a system's ability to cope with increased load. But — and this is the chapter's most-quoted point — it is not a one-dimensional label. "X is scalable" and "Y doesn't scale" are meaningless. The real questions: If the system grows in a particular way, what are our options for coping? and How can we add computing resources to handle the additional load? Answering them takes two things: a way to describe load, and a way to describe performance.

Describing Load

describing-load

Load is described by a few numbers — load parameters — and the right ones depend on your architecture: requests per second to a web server; read/write ratio in a database; simultaneously active users in a chat room; cache hit rate. Maybe the average case matters; maybe a handful of extreme cases dominate your bottleneck. The book's worked example is Twitter, using data it published in November 2012:

FEYNMAN · read-time vs write-time work A newsletter can be delivered two ways. Pull: every reader walks to every author's house each morning and asks "anything new?" — cheap for authors, brutal for readers. Push: each author photocopies their letter and drops it in every subscriber's mailbox — readers just open one box. Push wins when reading is far more common than writing… until one author has thirty million subscribers, and the photocopier melts. So: push for everyone normal, pull for the handful of superstars.
2ND EDITION · the case study, updated The 2nd edition keeps this case study, reframed generically as a social-network home timeline rather than "Twitter," and folds in newer material such as Bluesky's deliberately lossy timelines — accepting that not every follower's feed must receive every post — as another point on the same trade-off curve.

Describing Performance

describing-performance

With load described, ask what happens when it grows — two ways: increase a load parameter with resources fixed, how does performance change? Or: increase a load parameter, how much more resource keeps performance unchanged? Both need performance numbers. For batch systems like Hadoop the number is throughput — records per second, or total job time on a dataset of a given size (see Chapter 10→10). For online systems it's response time — from the client sending a request to receiving the response.

FEYNMAN · latency vs response time — not synonyms Response time is what the client experiences: the actual processing (service time) plus network delays plus queueing delays. Latency is strictly the time a request spends waiting to be handled — during which it is latent, awaiting service. People use them interchangeably; the book doesn't.

Even the identical request, repeated, gets a different response time every try; in a real mix of requests it varies a lot — so response time is not a number but a distribution. Some slow requests are intrinsically expensive (more data). But even when every request "should" take the same time, randomness intrudes: a context switch to a background process, a lost packet and TCP retransmit, a garbage-collection pause, a page fault forcing a disk read, even mechanical vibration in the rack.

Percentiles in practice

To put percentiles on a dashboard you need them continuously — say, over a rolling 10-minute window, recomputed every minute. The naive way (keep every response time, sort each minute) may be too costly; approximation algorithms such as forward decay, t-digest, and HdrHistogram compute good percentiles at minimal CPU and memory. One trap: averaging percentiles — to coarsen time resolution or combine machines — is mathematically meaningless. Aggregate response-time data by adding the histograms.

2ND EDITION · SLOs as a discipline The 2nd edition expands the percentile treatment into a fuller account of tail latency and SLOs as an operating discipline, and updates the sketch toolbox (HdrHistogram, t-digest, and newer DDSketch-style mergeable histograms) — all in the service of the same rule: describe performance as a distribution, and add histograms, never average percentiles.

Approaches for Coping with Load

approaches-for-coping-with-load

An architecture right for one load level is unlikely to cope with 10× that load: a fast-growing service rethinks its architecture at every order of magnitude — or more often. The usual dichotomy is scaling up (vertical: a more powerful machine) versus scaling out (horizontal: many smaller machines — a shared-nothing architecture):

Distributing stateless services is straightforward; taking a stateful data system from one node to many adds a lot of complexity. So the common wisdom (as of the 1st edition) was: keep the database on a single node — scale up — until cost or high-availability needs force distribution. As distributed tooling improves that wisdom may flip, and distributed data systems may become the default even for modest workloads — the rest of the book judges them on ease of use and maintainability, not scalability alone.

There is no magic scaling sauce — no generic, one-size-fits-all scalable architecture. The problem may be read volume, write volume, data volume, data complexity, response-time requirements, access patterns, or (usually) a mix. A system handling 100,000 requests/s of 1 kB each looks nothing like one handling 3 requests/minute of 2 GB each — same data throughput. A scalable architecture is built on assumptions about which operations are common and which rare — the load parameters — and if those assumptions are wrong, the scaling effort is wasted at best, counterproductive at worst. In an early-stage startup, iterating on product usually matters more than scaling to a hypothetical future load. Still, scalable architectures are assembled from general-purpose building blocks in familiar patterns — those blocks and patterns are what this book is about.

maintainability

Maintainability

The majority of software cost is not initial development but ongoing maintenance: fixing bugs, keeping systems running, investigating failures, adapting to new platforms and use cases, repaying technical debt, adding features. Yet many engineers dislike maintaining "legacy" systems — other people's mistakes, outdated platforms, systems bent to purposes never intended. Every legacy system is unpleasant in its own way, so instead of general advice on living with them, the book asks how to avoid creating legacy software: design for three principles from the start.

  • Operability — make it easy for operations to keep the system running smoothly.
  • Simplicity — make it easy for new engineers to understand the system by removing as much complexity as possible (not the same as a simple user interface).
  • Evolvability — make it easy to change the system in future, adapting to unanticipated use cases as requirements change. Also called extensibility, modifiability, plasticity.

Operability: Making Life Easy for Operations

operability-making-life-easy-for-operations

"Good operations can often work around the limitations of bad (or incomplete) software, but good software cannot run reliably with bad operations." Automation helps, but humans set up the automation and verify it. A good operations team monitors health and restores service fast; tracks down causes of failures and degradation; keeps software and platforms patched; watches how systems affect each other so a problematic change is caught before it does damage; anticipates problems (capacity planning); establishes deployment and configuration practices and tools; performs complex maintenance like platform migrations; maintains security through configuration changes; defines processes that keep production predictable; and preserves the organization's knowledge of the system as individuals come and go.

Good operability means making routine tasks easy, freeing the team for high-value work. Concretely, a data system can: expose its runtime behavior and internals through good monitoring; support automation and standard tools; avoid dependence on individual machines (so one can be taken down while the whole keeps running); provide good documentation and an easy-to-understand operational model ("if I do X, Y will happen"); offer good defaults while letting administrators override them; self-heal where appropriate while leaving manual control available; and behave predictably, minimizing surprises.

Simplicity: Managing Complexity

simplicity-managing-complexity

Small projects can be delightfully simple; large ones tend toward a big ball of mud. Symptoms of complexity: explosion of the state space, tight coupling, tangled dependencies, inconsistent naming, performance hacks, special-casing to paper over problems elsewhere. Complexity slows everyone down, blows budgets and schedules, and breeds bugs — hidden assumptions, unintended consequences, and unexpected interactions are easier to miss when the system is hard to reason about. Reducing complexity greatly improves maintainability, so simplicity should be a key goal.

FEYNMAN · accidental complexity and the power of abstraction Simplifying does not mean removing features. Moseley and Marks call complexity accidental when it isn't inherent in the problem the users see but arises only from the implementation. The best tool against it is abstraction: hide a mass of implementation detail behind a clean façade that many applications can reuse — and reuse means every quality improvement to the abstraction benefits every user of it. High-level languages hide machine code, registers, and syscalls. SQL hides on-disk and in-memory data structures, concurrent requests from other clients, and inconsistencies after crashes — you're still using machine code underneath, you just never have to think about it. The hard part is finding good abstractions: distributed systems has many good algorithms but far less clarity about how to package them into abstractions that keep complexity manageable — a search the book keeps up throughout.

Evolvability: Making Change Easy

evolvability-making-change-easy

Requirements never stay fixed: new facts, unanticipated use cases, shifting business priorities, feature requests, platform changes, legal and regulatory change, growth forcing architectural change. Organizationally, Agile patterns provide a framework for adapting, and the Agile community's technical tools — test-driven development, refactoring — help when software changes often. But those discussions work at a small scale: a few source files in one application. This book asks the same question at the scale of a whole data system of several applications and services: how would you "refactor" Twitter's timeline architecture from approach 1 to approach 2? Ease of modifying a data system tracks closely with its simplicity and its abstractions — simple systems are easier to change — and because the idea matters so much at this scale, it gets its own name: evolvability. Chapter 4→4 makes it concrete: how data formats evolve while old and new code coexist.

Core takeaways

  • Applications have functional requirements (what it should do) and nonfunctional requirements (security, reliability, compliance, scalability, compatibility, maintainability). This chapter — and the whole book — is about three of the nonfunctional ones.
  • Data-intensive apps are composites of standard building blocks (databases, caches, search indexes, stream and batch processing) glued by application code — and that glue owns the guarantees. You're a data system designer whether you meant to be or not.
  • Reliability = working correctly when things go wrong. Fault ≠ failure: a fault is a component deviating from spec; a failure is the system failing its users. Design fault-tolerance to stop faults becoming failures; you can't drive fault probability to zero.
  • Three fault families: hardware (random, uncorrelated — 10k disks ⇒ ~1 dead per day; answered by redundancy and, increasingly, software fault tolerance), software (systematic, correlated, dormant until an assumption breaks — no quick fix, many small disciplines), human (the leading cause of outages — minimize error opportunities, sandbox, test, make recovery fast, monitor, train).
  • Deliberately inject faults (Chaos Monkey): error-handling code is the least-exercised, most-buggy code you have.
  • Scalability is not a label. Ask "if load grows this way, what are our options?" Describe load with load parameters chosen for your architecture — and beware distributions hiding behind averages (Twitter's 75-follower mean vs 30M-follower celebrities).
  • Trade read-time work against write-time work according to their ratio: Twitter moved from compute-on-read to fan-out-on-write, then to a hybrid that exempts celebrities.
  • Performance is a distribution. Use percentiles, not means: p50 for typical experience, p95/p99/p999 for the tail that hurts your most valuable users. Tail latency amplifies across parallel backend calls; queueing (head-of-line blocking) dominates the tail, so measure client-side and load-test without waiting on responses. Add histograms; never average percentiles.
  • Coping with load: rethink architecture per order of magnitude; scale up vs scale out (shared-nothing) is a pragmatic mix, not a religion; elastic vs manual is a trade-off; stateless is easy, stateful is hard; there is no magic scaling sauce — only building blocks arranged around your load parameters.
  • Maintainability = operability (make routine ops easy: visibility, automation, no single-machine dependence, predictable behavior), simplicity (remove accidental complexity via good abstractions — SQL is the model), evolvability (make change easy; simplicity and abstraction are what make it possible).
  • 2nd-edition arc: this chapter split into "Trade-Offs in Data Systems Architecture" (cloud vs self-hosting, cloud-native architectures, serverless, OLTP/OLAP up front) and "Defining Nonfunctional Requirements" (this chapter's core, deepened with metastable failures, circuit breakers, load shedding, fail-slow hardware, and SLO discipline).

Answer key with explanations
Q1 — b. Two reasons in the text: tools no longer fit neat categories (Redis, Kafka), and demanding applications compose several specialized tools, with application code keeping them in sync. Not (c): they have very different access patterns and implementations — that's precisely why you combine them.
Q2 — c. The disk deviating from spec is a fault; because replication (a fault-tolerance mechanism) absorbed it, the system never stopped serving users, so there was no failure. (a) misuses "failure" for the component event; (d) cascading failure is a fault triggering further faults.
Q3 — d. The book's argument: many critical bugs are poor error handling, and error paths are the least exercised code. Deliberately inducing faults keeps them tested, raising confidence for the natural case. It's a testing discipline, not cost-cutting.
Q4 — a. Hardware faults are (mostly) independent — one disk's death doesn't imply another's. A software bug hits every instance at once (leap-second kernel bug, 2012), a runaway process starves shared resources, cascades propagate. Correlation is what turns faults into failures.
Q5 — c. The cited study found operator configuration errors were the leading cause; hardware played a role in only 10–25%. Hence the whole section on designing for unreliable humans — sandboxes, gradual rollout, fast rollback, telemetry.
Q6 — b. The book is emphatic: "X is scalable" is meaningless. Scalability is a set of options for coping with specific kinds of growth, described via load parameters and performance metrics. Multi-machine, low latency, or elasticity are neither necessary nor sufficient.
Q7 — d. Tweets are ~2 orders of magnitude rarer than timeline reads, so fan-out on write shifts work to the cheap side. The average of 75 followers hides a huge tail; celebrity fan-out (30M writes per tweet within 5 s) forced the hybrid: fan-out for most, read-time merge for celebrities.
Q8 — a. Tweet rate alone (12k/s peak) would be easy; the follower distribution determines fan-out cost and is what makes the problem hard. Choosing the right load parameter is the first act of scalability engineering.
Q9 — c. Straight from the book's sidebar: response time includes service time, network delays, and queueing; latency is the waiting ("latent") period. (d) is a tempting mix-up — the book says to measure response time on the client, but that's a measurement practice, not the definition.
Q10 — b. The mean doesn't say how many users saw a given delay; high percentiles do, and Amazon's slowest requests come from its heaviest, most valuable customers. Also cited: 100 ms slower ⇒ ~1% fewer sales. Yet Amazon stopped at p999 — p9999 was too costly for the benefit.
Q11 — d. Three practices, all from the "Describing Performance" section: client-side measurement (because of head-of-line blocking at the server), open-loop load generation (closed-loop clients shorten queues artificially), and histogram addition (averaging percentiles is mathematically meaningless).
Q12 — a. Even with parallel calls, the user waits for the slowest. With p per-call slowness and n calls, P(at least one slow) = 1 − (1−p)ⁿ — 1% and 100 calls ≈ 63%. This is why backend services need tight high percentiles.
Q13 — c. The book refuses the dichotomy: good architectures mix approaches; a few powerful machines can beat many small VMs; stateful distribution is genuinely hard; and scalable architectures are application-specific — built around the load parameters — with no generic recipe.
Q14 — b. Explicitly not UI simplicity (a). Moseley and Marks' accidental complexity is the target; abstraction is the tool; SQL and high-level languages are the exemplars. Simpler systems are also easier to change — linking simplicity to evolvability.
