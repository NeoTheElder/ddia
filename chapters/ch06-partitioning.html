Partitioning

Clearly, we must break away from the sequential and not limit the computers. We must state definitions and provide for priorities and descriptions of data. We must state relationships, not procedures. — Grace Murray Hopper, Management and the Computer of the Future (1962)

Chapter 5←5 kept a full copy of the database on every node. That stops working when the dataset outgrows one disk or the query load outgrows one machine's CPUs. The remedy is to break the database into pieces — partitions, also called shards — and put different pieces on different nodes. Each record, row, or document belongs to exactly one partition, so each partition is a small database of its own, and a shared-nothing cluster can spread the data over many disks and the query load over many processors. Single-partition queries scale by adding nodes; big queries can be parallelized across nodes, which is harder.

The vocabulary is a mess and the book warns you up front. A partition here is a shard in MongoDB, Elasticsearch, and SolrCloud; a region in HBase; a tablet in Bigtable; a vnode in Cassandra and Riak; a vBucket in Couchbase. And it has nothing to do with network partitions (netsplits), the fault studied in Chapter 8→8. Partitioned databases were pioneered in the 1980s (Teradata, Tandem NonStop SQL), then rediscovered by NoSQL stores and Hadoop-based warehouses; the OLTP/analytics split from Chapter 3←3 changes the tuning, not the fundamentals.

The chapter asks four questions in order: how do you decide which record goes where (key-value partitioning)? What happens to secondary indexes, which don't map neatly onto partitions? How do you rebalance when nodes join or leave? And when a client has a key in hand, how does it find the right node (request routing)?

FEYNMAN · the whole chapter in one idea A library outgrows one room, so the books are spread across many rooms. Every question in this chapter is a librarian's question. Which room does each book go in? By first letter of title (key range — browsing a shelf is easy, but every new bestseller starting with "The" lands in one room) or by a scrambled number stamped on the spine (hash — rooms fill evenly, but "all titles from Ha to Hu" is now a tour of every room). Where does the card catalog live? A catalog per room (fast to update, but "every red book" means visiting every room) or one alphabetized catalog split across rooms (one visit to read, but shelving a book means updating cards in several rooms). What happens when you open a new room? Move whole shelves, not individual books, and never renumber everything. How does a visitor know which room? Ask any librarian, ask the front desk, or carry your own map — and someone has to keep the map current. Colors as always: ember = writes, cyan = reads.

Partitioning and Replication

Partitioning is almost always combined with replication: each partition's data is copied onto several nodes for fault tolerance. So a record belongs to exactly one partition, yet lives on several nodes. Under the leader–follower model of Chapter 5←5, each partition has its own leader on one node and followers on others — and each node is leader for some partitions and follower for others. That is the book's Figure 6-1:

FEYNMAN · two orthogonal knobs Replication answers "how many copies?"; partitioning answers "how many pieces?". A node is just a shelf that happens to hold the master copy of some pieces and photocopies of others. You can turn either knob without touching the other — which is exactly why the book can study them in separate chapters. The one place they meet is failure: when a node dies you lose one leader and a couple of followers of different partitions, so failover (Chapter 5) has to happen per partition.

The structure survives (key-value sharding, secondary indexes, rebalancing, request routing) and a new section on sharding for multitenancy is listed (one shard per customer as an isolation and data-residency tool). Kleppmann has also softened the need to shard: with much bigger machines and managed cloud services, most teams no longer must shard early, and the chapter reads more as "when you eventually have to." partitioning-of-key-value-data

Partitioning of Key-Value Data

You have a lot of data and want to spread it. Which records go on which nodes? The goal is to spread both the data and the query load evenly: with a fair split, 10 nodes should hold 10× the data and serve 10× the throughput of one. If the split is unfair — some partitions hold more data or take more queries — it is skewed, and skew wrecks the whole point: in the extreme, all the load lands on one partition, 9 of 10 nodes idle, and the busy node is your ceiling. A partition with disproportionately high load is a hot spot.

The naive fix for hot spots is to assign records to nodes at random. That spreads data beautifully and destroys reads: to find a particular item you'd have no idea where it is, so you'd have to ask every node in parallel. We can do better, and the rest of this section assumes the simplest data model — a key-value store where every record is accessed by primary key, like an encyclopedia entry looked up by its title.

FEYNMAN · the encyclopedia on the shelf A paper encyclopedia is a partitioned database. Twelve volumes, each covering a range of titles, spines labeled "A–B", "C–D", … "T–Z". You know which book to pull because the ranges are printed on the spines (the partition boundaries), and inside each volume entries are alphabetical so "everything between Hopper and Hornet" is a single flip of pages. Notice the spines are not evenly spaced: "T–Z" covers six letters because those letters are rarer. The whole art of key-range partitioning is choosing the spine labels so every volume is roughly the same thickness.

Partitioning by Key Range

partitioning-by-key-range

Assign each partition a continuous range of keys, from some minimum to some maximum. Knowing the boundaries tells you which partition holds a key; knowing which node holds which partition lets you go straight to it — pick the right volume off the shelf. Because real keys aren't uniformly distributed, the boundaries must adapt to the data (one volume per two letters would make some volumes huge). They may be set by an administrator or chosen automatically by the database (see Rebalancing). Bigtable, its open-source equivalent HBase, RethinkDB, and MongoDB before 2.4 partition this way.

Two things to keep from the stepper: sorted keys within a partition (the SSTable←3 idea from Chapter 3) make range scans cheap and let the key act as a concatenated index←3; and access patterns, not data volume, are what create hot spots — timestamp keys are the textbook case (the Google App Engine advice "monotonically increasing values are bad" is the cited source).

Partitioning by Hash of Key

partitioning-by-hash-of-key

Because of that skew risk, many distributed stores put a hash function between the key and the partition. A good hash takes skewed input and produces uniformly distributed output: a 32-bit hash maps any string to a seemingly random number in 0…2³²−1, and near-identical strings land far apart. It need not be cryptographic — Cassandra and MongoDB use MD5, Voldemort uses Fowler–Noll–Vo — but it must be stable across processes: Java's Object.hashCode() and Ruby's Object#hash can give the same key different values in different processes, which would scatter one key across partitions (Kleppmann's own "Java's hashCode is not safe for distributed systems" is the reference). With a suitable hash, each partition owns a range of hashes instead of a range of keys.

Consistent hashing — the confusing term

When hash-range boundaries are chosen pseudorandomly the scheme is sometimes called consistent hashing. The term comes from Karger et al. (1997), who designed it for internet-scale caches like a CDN: random boundaries avoid the need for central control or distributed consensus. Consistent here has nothing to do with replica consistency (Chapter 5) or ACID consistency (Chapter 7→7); it just names a particular approach to rebalancing. The book's verdict: that approach doesn't work well for databases (we'll see why under Strategies for Rebalancing), it is rarely used, and database docs that say "consistent hashing" are often inaccurate — so avoid the term and say hash partitioning.

2ND EDITION · newer hashing algorithms The 2nd edition treats consistent hashing more generously, covering the newer algorithms that achieve the "move as little as possible when N changes" property with far less metadata than a ring of random boundaries: Google's jump consistent hash (Lamping & Veach — the 1st edition's reference [8]) and random slicing. The 1st edition's advice to say "hash partitioning" stands; what changes is that the low-metadata algorithms are now first-class rebalancing options rather than a footnote. Skewed Workloads and Relieving Hot Spots

skewed-workloads-and-relieving-hot-spots

Hashing spreads different keys. It does nothing for the case where every request is for the same key: the hash of one ID is one number, so all of that key's traffic lands on one partition. Unusual, but real — a celebrity with millions of followers does something, and a storm of writes hits their user ID or the ID of the post being commented on (the reference is "3% of Twitter's servers dedicated to Justin Bieber"). partitioning-and-secondary-indexes

Partitioning and Secondary Indexes

Everything so far assumed records are reached only by primary key, so the key alone routes every read and write. Secondary indexes break that assumption. A secondary index (recall Chapter 3←3) usually doesn't identify a record uniquely — it finds occurrences of a value: all actions by user 123, all articles containing "hogwash", all red cars. They are the bread and butter of relational databases, common in document databases, the whole reason search servers like Solr and Elasticsearch exist — and some key-value stores (HBase, Voldemort) avoided them because of the implementation complexity, while others (Riak) added them because they're so useful. The trouble is that a secondary index doesn't map neatly onto partitions: the value you're searching by has no relationship to the key that decided where the record lives. There are two ways to partition an index: by document and by term.

Footnote worth keeping: if your store only offers key-value access, you may be tempted to build a secondary index yourself as a value→IDs mapping in application code. Do that and you own its consistency — race conditions and partial write failures will happily desynchronize it from the data, which is one of the reasons multi-object transactions→7 exist.

FEYNMAN · where does the card catalog live? The books are already spread across rooms by ID. Now readers want "all the red books." Option one: each room keeps its own catalog of the books in that room. Shelving a book means updating one catalog — the one in its room. But finding all red books means walking into every room and checking every catalog. Option two: one catalog for the whole library, itself split alphabetically across rooms (colors A–R in room 0, S–Z in room 1). Now "red" is one visit. But shelving a book means running to the "color" catalog room and the "make" catalog room to add cards — and if a runner is slow, the catalog lags behind the shelves. Local index: cheap writes, expensive reads. Global index: expensive writes, cheap reads.

Partitioning Secondary Indexes by Document

partitioning-secondary-indexes-by-document

The book's example: a used-car website. Each listing has a unique document ID, and the database is partitioned by it (IDs 0–499 in partition 0, 500–999 in partition 1, …). Users filter by color and make, so those fields are indexed. In the document-partitioned approach, each partition keeps its own secondary indexes covering only its own documents — it neither knows nor cares what other partitions hold. Whenever a red car is added to partition 0, that partition appends its ID to its own color:red list. The stepper walks both approaches on the same data:

Because a document-partitioned index lives with its documents, it's also called a local index; the term-partitioned one is a global index. The local approach makes writes trivially single-partition and reads expensive: scatter/gather, with the tail latency amplification of Chapter 1←1. Widely used regardless: MongoDB, Riak, Cassandra, Elasticsearch, SolrCloud, VoltDB.

Partitioning Secondary Indexes by Term

partitioning-secondary-indexes-by-term

The global index flips the trade. It covers data in all partitions but is partitioned differently from the primary key — by the term being looked up (color:red), either by the term's own value (enables range scans, e.g. asking price) or by its hash (even load). Reads become efficient: the client asks only the index partition that owns the term. Writes become slower and more complicated: a single document's terms may scatter across several index partitions on several nodes, and an always-up-to-date global index would need a distributed transaction across all affected partitions — Chapter 9→9 territory, and not supported everywhere. So in practice global secondary indexes are asynchronous: Amazon DynamoDB documents that its global secondary indexes usually update within a fraction of a second but can lag under infrastructure faults. Riak's search feature and Oracle's data warehouse (which lets you choose local or global indexing) are other users; the book returns to building term-partitioned indexes as derived data in Chapter 12→12.

rebalancing-partitions

Rebalancing Partitions

Databases change: query throughput grows (more CPUs), the dataset grows (more disks and RAM), a machine dies (others must take over). All three mean moving data and requests between nodes — rebalancing. Whatever the partitioning scheme, rebalancing has minimum requirements: afterwards, load (storage, reads, writes) should be shared fairly; during it, the database must keep accepting reads and writes; and no more data than necessary should move, because rebalancing is expensive network and disk I/O.

FEYNMAN · move shelves, don't renumber books Opening a new room in the library, the worst thing you can do is re-derive every book's room from scratch — that's "hash mod N", and it reshuffles almost the entire collection. The good strategies all share one trick: the unit that moves is a whole shelf (a partition), never an individual book, and a book's shelf never changes. Only the shelf's room changes. Whether you start with far more shelves than rooms (fixed number of partitions), saw a shelf in half when it gets too full (dynamic partitioning), or give each room a fixed number of shelves (proportional to nodes) is the rest of this section.

Strategies for Rebalancing

strategies-for-rebalancing

How not to do it: hash mod N

We said hash partitioning assigns each partition a range of hashes. Why not just hash(key) mod N with N nodes — it returns 0…N−1, a node number, done? Because when N changes, almost every key changes node:

Fixed number of partitions

The simple, common answer: create many more partitions than nodes from the start and give each node several. A 10-node cluster might be split into 1,000 partitions, ~100 per node. When a node joins, it steals a few partitions from every existing node until things are fair again; when a node leaves, the reverse. Only entire partitions move. The number of partitions never changes and neither does the assignment of keys to partitions — the only thing that changes is the assignment of partitions to nodes. That reassignment takes time (bulk network transfer), so the old assignment keeps serving reads and writes while the transfer is in flight.

Dynamic partitioning

For key-range partitioning, a fixed set of partitions with fixed boundaries would be a disaster: guess the boundaries wrong and all the data lands in one partition while the others sit empty, and fixing boundaries by hand is tedious. So key-range stores like HBase and RethinkDB create partitions dynamically: when a partition exceeds a configured size (HBase default: 10 GB), it is split into two halves; when deletes shrink one below a threshold, it is merged with a neighbor — exactly what happens at the top level of a B-tree←3. Each partition lives on one node, a node holds many partitions, and after a split one half can be shipped to another node to balance load (HBase moves the files via HDFS).

Partitioning proportionally to nodes

Fixed-count partitions grow with the dataset; dynamic partitions keep a bounded size and their count grows with the dataset. In both, the partition count is independent of the node count. Cassandra and Ketama take a third route: a fixed number of partitions per node (Cassandra: 256 by default). Partition size grows with the dataset while nodes stay fixed, but adding nodes makes partitions smaller again — and since more data usually means more nodes anyway, partition size stays roughly stable. When a node joins it randomly picks a fixed number of existing partitions to split and takes one half of each. Randomization can produce unfair splits, but averaged over 256 partitions the newcomer ends up with a fair share; Cassandra 3.0 added a token-allocation algorithm that avoids unfair splits. Picking boundaries randomly requires hash partitioning — which makes this the scheme that most closely matches the original definition of consistent hashing, and newer hash functions (jump hash) get a similar effect with less metadata.

Operations: Automatic or Manual Rebalancing

operations-automatic-or-manual-rebalancing

One question the strategies gloss over: who decides to rebalance? There's a gradient from fully automatic (the system moves partitions on its own, no administrator involved) to fully manual (an administrator sets the partition→node assignment and it changes only when they say so). Couchbase, Riak, and Voldemort sit in between: they generate a suggested assignment automatically but require an administrator to commit it. Automation is convenient — less routine work — but unpredictable. Rebalancing reroutes requests and moves large amounts of data, and done carelessly it saturates the network or the nodes and degrades everything else while it runs.

This is the failure-detection problem from Chapter 5's failover←5, generalized: a timeout cannot distinguish a dead node from a slow one, and Chapter 8→8 shows there is no better detector available. Hence the book's preference for a human in the rebalancing loop.

2ND EDITION · shard management services The 2nd edition adds the machinery big operators built to make automatic rebalancing safe: Facebook's Shard Manager (a general shard-placement service with load-aware, rate-limited migrations), ScyllaDB's Raft-based topology changes (cluster membership and token ownership go through consensus instead of gossip, making concurrent node joins safe), and DynamoDB's adaptive capacity for hot partitions. The 1st edition's gradient from manual to automatic still frames the discussion, but the modern default in managed services has shifted toward automation with strong guardrails. request-routing

Request Routing

The data is partitioned across nodes on many machines. When a client wants to read or write the key "foo", which IP address and port does it connect to? Rebalancing keeps changing partition→node assignments, so somebody has to stay on top of the changes. This is an instance of service discovery, a problem for anything highly available over a network, and many companies have built and open-sourced their own tools for it. There are three broad shapes, and one shared hard problem:

FEYNMAN · the map and the mapmaker Three ways to find a room in the library: ask any librarian (they all carry the map and will walk your request over), ask the front desk (a dedicated desk that only gives directions), or carry your own map. The design question isn't which of those you pick — it's who prints the map and how everyone gets the new edition when a shelf moves. ZooKeeper is the print shop: every room reports what it holds, and every subscriber gets the update pushed. Cassandra and Riak instead have the librarians whisper changes to each other until everyone has heard (gossip). Either way, the routing layer is only as correct as its map is current — and agreeing on one current map is the consensus problem Chapter 9→9 finally solves.

Parallel Query Execution

parallel-query-execution

Everything so far routes simple queries — read or write one key, plus scatter/gather for document-partitioned indexes — and that is about the level most NoSQL distributed stores support. Massively parallel processing (MPP) relational databases, used for analytics, are far more ambitious. A typical warehouse query has joins, filters, grouping, and aggregation; the MPP query optimizer breaks it into execution stages and partitions, many of which run in parallel on different nodes. Queries that scan large parts of the dataset benefit most. This is a specialized, commercially important topic; the book revisits parallel execution techniques in Chapter 10→10.

FEYNMAN · the chapter's closing warning By design every partition operates mostly independently — that independence is what lets a partitioned database scale across machines. The price shows up the moment an operation needs to write to several partitions: what if the write to one succeeds and the write to another fails? The chapter ends on that question and hands it to Chapter 7→7 (transactions) and Chapter 9→9 (atomic commit across nodes).

Core takeaways

  • Why partition: when the dataset or query load exceeds one machine. Each record belongs to exactly one partition (shard / region / tablet / vnode / vBucket); partitions are spread over a shared-nothing cluster and usually each replicated, with every node leading some partitions and following others. Partitioning and replication are orthogonal choices.
  • Goal = even spread of data AND load; unevenness is skew, a disproportionately loaded partition a hot spot. Random placement spreads perfectly but makes reads ask every node.
  • Key-range partitioning (Bigtable, HBase, RethinkDB, early MongoDB): contiguous sorted ranges with data-adapted boundaries; cheap routing and efficient range scans (the key is a concatenated index), but sequential access patterns — timestamp keys — create hot spots; fix by putting a spreading component first in the key at the cost of one range query per prefix.
  • Hash partitioning (Cassandra, MongoDB hashed, Riak, Voldemort): a stable, process-independent hash maps skewed keys uniformly onto hash ranges; balances load but destroys key order, so range queries hit all partitions. Cassandra's compound key hashes the first column and sorts by the rest — one-to-many data (user, timestamp) on one partition. "Consistent hashing" is a rebalancing approach that works poorly for databases; say "hash partitioning."
  • Same-key hot spots (celebrities) defeat hashing; the application must salt the key (random 2-digit suffix → 100 keys), paying with 100-way reads and bookkeeping of which keys are split.
  • Secondary indexes don't map to partitions. Document-partitioned (local): each partition indexes its own docs; writes touch one partition, reads scatter/gather with tail-latency amplification (MongoDB, Riak, Cassandra, Elasticsearch, SolrCloud, VoltDB). Term-partitioned (global): one index split by term (value or hash); reads hit one index partition, writes fan out to several nodes and are therefore usually asynchronous (DynamoDB GSIs, Riak search, Oracle).
  • Rebalancing must leave load fair, keep serving reads and writes meanwhile, and move no more than necessary. hash mod N fails the last test catastrophically (nearly everything moves when N changes).
  • Strategies that work: fixed number of partitions ≫ nodes, move whole partitions on join/leave (Riak, Elasticsearch, Couchbase, Voldemort; the count caps node count and partitions grow with data); dynamic split/merge at a size threshold, B-tree style (HBase, RethinkDB, MongoDB ≥ 2.4; cold start on one partition unless pre-split); fixed partitions per node with random splits on join (Cassandra 256 vnodes, Ketama — the closest thing to real consistent hashing).
  • Automatic vs manual: automation is convenient but unpredictable and, combined with timeout-based failure detection, can cascade (slow node declared dead → rebalance adds load → slower). Couchbase/Riak/Voldemort propose, a human commits.
  • Request routing is service discovery: any node forwards (Cassandra, Riak via gossip), a routing tier (Espresso/Helix, mongos, moxi), or a partition-aware client. All need an agreed, current partition→node map — a consensus problem usually delegated to ZooKeeper (HBase, SolrCloud, Kafka); DNS suffices for the slowly changing node IPs.
  • Parallel query execution: NoSQL stores route single-key and scatter/gather queries; MPP warehouses break joins/aggregations into parallel stages across nodes (Chapter 10).
  • 2nd-edition arc: chapter renamed Sharding; sharding for multitenancy added; the need to shard softened (bigger machines, managed services); shard management services (Facebook Shard Manager, ScyllaDB Raft topology, DynamoDB adaptive capacity, S3) join the Cassandra/Riak-era examples; jump hash and random slicing give consistent hashing a second look.
