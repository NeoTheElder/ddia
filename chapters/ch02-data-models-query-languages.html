Data Models and Query Languages

The limits of my language mean the limits of my world. — Ludwig Wittgenstein, Tractatus Logico-Philosophicus (1922)

Data models may be the most important part of developing software: they shape not only how the code is written but how you think about the problem. Every application stacks data models in layers, and at each layer the question is the same — how is this represented in terms of the layer below?

FEYNMAN · the whole chapter in one idea Every data model is a bet about what shape your relationships have. If your data is a tree — one thing owning many sub-things, always loaded together — the document model fits like a glove. If many things point at many other things and you need to slice them from any angle, the relational model's joins are the tool. If everything may relate to everything, you want a graph. Pick the wrong shape and you'll spend your life writing code to fight the model. And the second theme: declarative query languages ("what I want") beat imperative ones ("how to get it") because they leave the database free to get smarter without changing your queries. Book-wide colors: ember = writes, cyan = reads.
relational-model-versus-document-model

Relational Model Versus Document Model

The best-known model is SQL's, built on Edgar Codd's 1970 relational model: data is organized into relations (tables), each an unordered collection of tuples (rows). It began as a theoretical proposal many doubted could be implemented efficiently; by the mid-1980s RDBMSes and SQL were the default for anything with regular structure — a dominance lasting 25–30 years, an eternity in computing. Its roots are mundane 1960s–70s mainframe business processing: transaction processing (sales, banking, airline reservations, stock-keeping) and batch processing (invoicing, payroll, reporting). Its purpose was radical for the time: other databases made developers think hard about the internal representation of data; the relational model hid that behind a cleaner interface.

Challengers came and went — the network and hierarchical models (1970s–80s), object databases (late 80s–early 90s), XML databases (early 2000s, niche). Each generated hype; none lasted. Meanwhile relational databases generalized astonishingly well beyond business data to power most of the web: publishing, discussion, social networking, e-commerce, games, SaaS.

The Birth of NoSQL

the-birth-of-nosql

The 2010s challenger. The name is an accident — a catchy Twitter hashtag for a 2009 meetup on open source, distributed, nonrelational databases — retroactively reinterpreted as Not Only SQL. The driving forces: a need for greater scalability than relational databases easily offer (very large datasets, very high write throughput); a preference for free and open source software over commercial products; specialized query operations the relational model supports poorly; and frustration with restrictive schemas, wanting a more dynamic, expressive model. Since requirements differ, the likely future is relational databases used alongside a variety of nonrelational stores — polyglot persistence.

Many-to-One and Many-to-Many Relationships

many-to-one-and-many-to-many-relationships

The stepper's steps 4–6 are this section's argument in pictures; the principle in words: whether you store an ID or a string is a question of duplication. An ID has no human meaning and therefore never needs to change; the meaningful text lives in exactly one place. Anything humans care about may need to change someday — and if it's duplicated, every copy must be updated: write overhead, plus the risk that some copies get missed and the data goes inconsistent. Removing that duplication is normalization. (The literature distinguishes several normal forms; the practical rule: if you're duplicating values that could live in one place, you're not normalized.) DBAs and developers love arguing normalization vs denormalization; the book suspends judgment until Part III→12 treats caching, denormalization, and derived data systematically.

Are Document Databases Repeating History?

are-document-databases-repeating-history

NoSQL reopened a debate that is older than most programmers: how to represent many-to-many relationships. The 1970s' best-selling business database — IBM's IMS, built for Apollo-program stock-keeping, released 1968, still running on mainframes today — used a hierarchical model remarkably like JSON: all data a tree of records nested in records. Like document databases, it handled one-to-many well, struggled with many-to-many, and had no joins; developers chose between duplicating data and manually resolving references. Two rival fixes were proposed, and "the great debate" between them consumed the 1970s:

FEYNMAN · why the optimizer was the real invention CODASYL asked every programmer to be a navigator, memorizing routes through the data. The relational model hired one professional navigator — the query optimizer — and gave it a map (indexes, statistics). Hand-picking a route for one trip is easier than building a navigator; but you make a million trips, and the roads keep changing. The general-purpose navigator wins in the long run, and everyone gets it for free.

Relational Versus Document Databases Today

relational-versus-document-databases-today

Beyond data models, the two families also differ in fault tolerance (Chapter 5→5) and concurrency (Chapter 7→7); here, data model only. The document model's case: schema flexibility, locality, closeness to application data structures. The relational case: joins, many-to-one and many-to-many.

Which model gives simpler application code?

If your data is document-shaped — a tree of one-to-many relationships, typically loaded whole — the document model is probably right; shredding it across tables makes cumbersome schemas and complicated code. The document model's own limits: you can't point directly at a nested item ("the second position of user 251" — an access path in miniature), tolerable while nesting is shallow; and weak joins may not matter (an analytics app logging events may never need many-to-many). But if you do have many-to-many relationships, documents get ugly: denormalize and keep copies consistent in application code, or emulate joins with multiple requests — more complex code and worse performance than a database join. No general answer exists; it depends on the relationships in your data. For highly interconnected data: document awkward, relational acceptable, graph most natural.

Schema flexibility in the document model

Document databases (and JSON columns) enforce no schema; anything can be written, and readers get no guarantees about fields. "Schemaless" is misleading — the code that reads the data assumes a structure, so there's an implicit schema the database doesn't enforce. Better terms: schema-on-read (structure implicit, interpreted when read) vs schema-on-write (explicit schema, enforced on every write). The analogy: dynamic vs static type checking — and equally contentious, with no right answer.

Data locality for queries

A document is stored as one continuous string (JSON, XML, or a binary variant like BSON). If you usually need the whole document — rendering a page — that locality wins: multi-table data requires several index lookups and disk seeks. But locality only pays if you need most of the document: the database loads all of it even for a small piece, and updates usually rewrite the whole thing — only same-size changes can happen in place. Hence the advice: keep documents small, avoid writes that grow them. Note that locality isn't document-exclusive: Spanner interleaves child rows within a parent table in a relational schema; Oracle has multi-table index cluster tables; Bigtable's column families (Cassandra, HBase) serve the same purpose — see Chapter 3→3.

Schema-on-read vs schema-on-write remains the framing, now paired with modern online schema-migration tooling (gh-ost, pgroll) that removes much of the old "schema changes need downtime" fear.

Query Languages for Data

The relational model brought not just a new data model but a new way of asking: SQL is declarative, where IMS and CODASYL were queried with imperative code. Imperative code tells the computer which operations to perform in which order; a declarative query states the pattern of the data you want — conditions, transformations (sort, group, aggregate) — and leaves the how to the optimizer:

Declarative Queries on the Web

declarative-queries-on-the-web

The same advantage shows up far from databases. In a web page about ocean animals, the currently selected navigation item is marked <li class="selected">; you want its title <p> highlighted blue. CSS says it declaratively — li.selected > p { background-color: blue; } — a pattern: every <p> whose direct parent is an <li> with class selected. XSL does the same with an XPath pattern (li[@class='selected']/p). The imperative alternative — JavaScript walking getElementsByTagName("li"), checking classes, walking child nodes, calling setAttribute("style", …) — is longer, harder to read, and has real bugs: when the selected class moves, the blue stays (CSS removes it automatically the moment the rule stops matching); and if a faster API appears (getElementsByClassName, document.evaluate()), you must rewrite the code — whereas browser vendors speed up CSS and XPath under you without breaking anything. Declarative CSS beats imperative DOM manipulation for exactly the reasons SQL beat CODASYL's COBOL cursors.

MapReduce Querying

mapreduce-querying

MapReduce is Google's programming model for bulk processing across many machines (the full story is Chapter 10→10); MongoDB and CouchDB support a limited form for read-only queries across documents. It sits between declarative and imperative: the query logic is snippets of code the framework calls repeatedly — the map (collect) and reduce (fold/inject) functions from functional programming. The example: a marine biologist logs sightings and wants sharks seen per month.

2ND EDITION · MapReduce querying is gone; GraphQL arrives Consistent with the book-wide demotion of MapReduce, the 2nd edition drops this MongoDB MapReduce section — the aggregation pipeline is the story now. In its place among query languages: GraphQL, treated as a query language for the application/API layer, with its critiques.

Graph-Like Data Models

Mostly one-to-many (trees) or no relationships? Document model. Many-to-many everywhere? The relational model handles the simple cases, but as connections get complex it becomes natural to model data as a graph: vertices (nodes, entities) and edges (relationships, arcs). Homogeneous examples: social graphs (people, who-knows-whom), the web graph (pages, links — PageRank), road and rail networks (junctions, roads — shortest path). But graphs are equally powerful for heterogeneous data in one store: Facebook's single graph holds people, locations, events, checkins, comments, with edges for friendship, checkin-at-location, commented-on, attended.

The book's example graph: Lucy from Idaho and Alain from Beaune, France — married, living in London. Two related models (property graph: Neo4j, Titan, InfiniteGraph; triple-store: Datomic, AllegroGraph) and three declarative query languages (Cypher, SPARQL, Datalog); imperative graph languages (Gremlin) and graph processing frameworks (Pregel, Chapter 10→10) exist too.

Property Graphs

property-graphs

Each vertex: a unique ID, outgoing edges, incoming edges, and properties (key–value pairs). Each edge: a unique ID, the tail vertex (start), the head vertex (end), a label naming the relationship, and properties. You can picture the whole store as two relational tables:

CREATE TABLE vertices (vertex_id integer PRIMARY KEY, properties json);
CREATE TABLE edges (
    edge_id     integer PRIMARY KEY,
    tail_vertex integer REFERENCES vertices (vertex_id),
    head_vertex integer REFERENCES vertices (vertex_id),
    label       text,
    properties  json
);
CREATE INDEX edges_tails ON edges (tail_vertex);
CREATE INDEX edges_heads ON edges (head_vertex);

Three properties make the model flexible: (1) any vertex may connect to any other — no schema restricts what associates with what; (2) given a vertex you can efficiently find incoming and outgoing edges and so traverse forward and backward (hence indexes on both columns); (3) labels let one graph hold many kinds of relationship cleanly. The example graph shows what a relational schema would strain at: different regional structures per country (France's départements and régions vs US counties and states), a country within a country, and varying granularity (Lucy lives in a city but was born "in Idaho"). Add allergens as vertices and food-contains edges, and "what can each person safely eat" is a query. Graphs are good for evolvability — new features extend the graph without restructuring it.

The Cypher Query Language

the-cypher-query-language

Cypher is Neo4j's declarative language for property graphs (named for a Matrix character, nothing to do with ciphers). Creating data uses an arrow notation: (Idaho) -[:WITHIN]-> (USA) makes a WITHIN edge from tail Idaho to head USA. Querying uses the same arrows as patterns in a MATCH clause. The book's question: find everyone who emigrated from the United States to Europe.

Graph Queries in SQL

graph-queries-in-sql

Graph data fits in relational tables — can SQL query it? Yes, with difficulty. In a relational query you normally know in advance which joins you need; a graph traversal may cross a variable number of edges — a LIVES_IN edge may point at a street, city, region, or country, each nested WITHIN others to different depths. Cypher's :WITHIN*0.. says "zero or more" in six characters. Since SQL:1999 the same idea is expressible via recursive common table expressions (WITH RECURSIVE): build the set in_usa starting from the vertex named "United States" and repeatedly adding the tail vertices of incoming within edges until nothing new appears; likewise in_europe; then born_in_usa and lives_in_europe by following the incoming born_in/lives_in edges; finally join the two people-sets. Supported in PostgreSQL, DB2, Oracle, SQL Server — and about 29 lines to Cypher's 4. The lesson isn't that SQL loses; it's that a data model suited to your application saves you from fighting the language.

2ND EDITION · graph querying got a standard Graph query languages are converging on standards the 1st edition predates: GQL, the ISO graph query language, and SQL/PGQ (property-graph queries inside SQL, closing much of the 29-lines-vs-4 gap). Example systems modernize too: Facebook's TAO, LinkedIn's LIquid, embedded KùzuDB, Amazon Neptune, and knowledge graphs as a use case.

Triple-Stores and SPARQL

triple-stores-and-sparql

The triple-store model is mostly the property graph in different words, worth knowing for its tools. Everything is a three-part statement (subject, predicate, object): (Jim, likes, bananas). The subject is a vertex. The object is either a primitive value — then predicate + object are a property: (lucy, age, 33) ≈ vertex lucy with {"age": 33} — or another vertex — then the predicate is an edge label, subject the tail, object the head: (lucy, marriedTo, alain).

The semantic web (briefly)

Triple-stores are independent of the semantic web — Datomic is a triple-store (technically 5-tuples, with versioning metadata) with no such ambitions — but the two are entangled in people's minds. The idea is reasonable: sites publish text for humans; why not machine-readable data too? RDF (Resource Description Framework) was to be the consistent format, letting data from many sites combine into an internet-wide "database of everything." Overhyped in the early 2000s, never realized, drowned in acronyms and hubris — yet good work came out of it, and triples are a fine internal data model even if you publish nothing. RDF's quirk: subjects, predicates, and objects are often URIs (<http://my-company.com/namespace#within>) so that your within and someone else's don't collide when data is combined; the URL needn't resolve — it's a namespace, declared once with a @prefix and then forgotten.

SPARQL

SPARQL ("sparkle": SPARQL Protocol and RDF Query Language) queries RDF triple-stores and predates Cypher — Cypher's pattern matching is borrowed from it, so they look alike. The emigration query is even shorter:

PREFIX : <urn:example:>
SELECT ?personName WHERE {
  ?person :name ?personName.
  ?person :bornIn  / :within* / :name "United States".
  ?person :livesIn / :within* / :name "Europe".
}

Variables start with ?; :bornIn / :within* is a property path equal to Cypher's -[:BORN_IN]-> () -[:WITHIN*0..]->. And because RDF doesn't distinguish properties from edges — both are predicates — the same syntax matches properties: ?usa :name "United States". ≈ Cypher's (usa {name:'United States'}). A nice language, semantic web or no.

Graph databases compared to the network model

Is the graph model CODASYL's second coming? No — four differences:

CODASYL (network model)graph databases
SchemaSpecified which record types could nest within whichNone: any vertex may have an edge to any other — flexibility for changing requirements
Reaching a recordOnly by traversing an access pathDirectly by unique ID, or via an index on a property value
OrderingChildren were an ordered set; storage had to maintain it and inserts had to place recordsVertices and edges are unordered; sort only in query results
QueriesAll imperative, hard to write, broken by schema changesImperative traversal possible, but high-level declarative languages (Cypher, SPARQL) are the norm

The Foundation: Datalog

the-foundation-datalog

Datalog is far older — studied intensively by academics in the 1980s — and less known to engineers, but it's the foundation later query languages build on. In practice it powers Datomic's query language and Cascalog (Datalog over Hadoop). Its data model generalizes triples: instead of (subject, predicate, object) write predicate(subject, object): name(lucy, 'Lucy'), born_in(lucy, idaho), within(idaho, usa). Where Cypher and SPARQL jump straight to SELECT, Datalog takes small steps: you define rules that derive new predicates from existing facts and other rules — and rules can call each other, even recursively, like functions.

FEYNMAN · Datalog is "define your own verbs" Cypher and SPARQL hand you a fixed vocabulary of arrows and let you draw a pattern. Datalog lets you invent new verbs — within_recursive, migrated — by saying what they mean in terms of verbs you already have, including themselves. Once defined, a verb is reusable in any later question, like a function in a library. Small steps, big compounding.

Core takeaways

  • Data models are layered (application objects → general-purpose model → bytes → hardware), and each layer's clean abstraction is what lets teams cooperate. The model you choose shapes how you think about the problem.
  • Relational (Codd, 1970): relations of unordered tuples, all data in the open, joins on foreign keys, an automatic query optimizer choosing the access path. It hid storage details and generalized far beyond business processing; it has out-lasted every challenger for 25–30 years.
  • NoSQL (a 2009 hashtag): driven by scalability, open source, specialized queries, and schema frustration; expect polyglot persistence, not replacement.
  • Document model: JSON-shaped trees. Wins on schema flexibility, locality (one read, one write), and closeness to application objects — when the data is a self-contained tree loaded whole. Weak joins make many-to-one and many-to-many painful: work moves into application code.
  • Normalization is about duplication: store human-meaningful text once and refer to it by an ID that never has to change. Reference, don't copy, anything that may change.
  • History rhymes: IMS's hierarchical model (1968) ≈ documents; CODASYL's network model solved many-to-many with pointer access paths the programmer navigated by hand; the relational model won by making the optimizer navigate. Document databases nest one-to-many like IMS but reference by ID like relational — they are not CODASYL. The two families are converging (JSON in SQL; joins in document stores).
  • Schema-on-read vs schema-on-write — not "schemaless": the reading code always assumes a structure. Like dynamic vs static typing: no universal answer; on-read for heterogeneous or externally-dictated data, on-write when records share structure.
  • Locality pays only when you need most of the document; documents are loaded and rewritten whole, so keep them small and avoid growth. Relational systems (Spanner interleaving, Oracle cluster tables, Bigtable column families) offer locality too.
  • Declarative beats imperative: state the pattern, not the steps. It's more concise, it hides implementation so the engine can optimize and reorganize without breaking queries, and it parallelizes. CSS vs DOM-walking JavaScript is the same lesson outside databases.
  • MapReduce querying (map emits key–values; group; reduce folds) sits between declarative and imperative; the functions must be pure. Two coordinated functions are harder than one query and optimize worse — so MongoDB reinvented SQL as the aggregation pipeline.
  • Graphs for many-to-many-everywhere: property graphs (vertices, labeled edges, properties on both) and triple-stores (subject–predicate–object) are the same idea in two vocabularies; declarative languages Cypher, SPARQL, and Datalog express variable-length traversal in a few lines where SQL needs WITH RECURSIVE. Graph DBs beat CODASYL on schema freedom, direct access by ID/index, no forced ordering, and declarative queries.
  • Datalog is the foundation: rules derive new predicates from facts and other rules, recursively; harder for one-offs, powerful for complex data because rules compose and reuse.
  • 2nd-edition arc: relational-vs-NoSQL treated as settled convergence ("What Goes Around Comes Around… And Around", 2024); GraphQL added, MapReduce querying removed; dataframes/arrays as a data model; GQL and SQL/PGQ standardize graph querying; online schema migration (gh-ost, pgroll) defuses the schema-change fear.

Answer key with explanations
Q1 — c. The chapter's framing: other 1960s–70s databases made developers think about internal representation; Codd's goal was a cleaner interface hiding those details. Distributed execution (d) and OO support (b) came decades later and weren't the motivation.
Q2 — d. The book lists five benefits of standardized lists, then generalizes: an ID vs text is a question of duplication. IDs have no human meaning so they never change; duplicated meaningful text must be updated everywhere (write overhead, inconsistency risk). That's normalization's core idea.
Q3 — b. Documents excel at one-to-many trees (a is backwards) and are schema-flexible (c is backwards). Their weakness is joins: many-to-one and many-to-many require denormalizing (and keeping copies consistent) or emulating joins with multiple round-trips — complexity and slowness the book explicitly warns about.
Q4 — a. CODASYL's "programmer as navigator" tracked access paths by hand; the relational model's key insight was to build the optimizer once so every application benefits — declare a new index and queries use it unchanged. (d) inverts the two: CODASYL used pointers, relational uses foreign keys resolved at query time.
Q5 — c. One aspect reverted (nesting one-to-many inside the parent record); for many-to-one/many-to-many, document references work like foreign keys, resolved at read time. The book states plainly that document databases "have not followed the path of CODASYL."
Q6 — d. No schema is enforced, but the application code assumes one — an implicit schema. The accurate terms are schema-on-read vs schema-on-write, with the dynamic-vs-static typing analogy and the same "no right answer" verdict.
Q7 — b. Locality wins when the whole document is needed (rendering a page). The database loads the entire document regardless, and updates rewrite it unless the encoded size is unchanged — so large documents and growing writes are costly. Hence the advice to keep documents small.
Q8 — a. The book's example: reclaiming disk space moves records and changes their order. SQL guarantees no order, so it's safe; imperative code might rely on order and the database can't know. SQL's limited functionality is precisely what buys automatic optimization.
Q9 — c. Two concrete problems with the imperative DOM code: the highlight persists after the class is removed (CSS un-applies automatically), and adopting a faster API means rewriting code (CSS/XPath get faster for free). Same reasons SQL beat CODASYL's cursors.
Q10 — d. Purity — input-only, no additional queries, no side effects — is what lets the framework run the functions anywhere, in any order, and rerun them on failure. Within those limits they're still powerful (parsing, library calls, calculations).
Q11 — b. The usability problem (two coordinated functions) plus the optimizer argument led to $match/$group/$sum — a subset of SQL's expressiveness in JSON syntax. The book's moral: a NoSQL system may accidentally reinvent SQL in disguise.
Q12 — a. A LIVES_IN edge may point at any level of the location hierarchy, so the traversal depth is unknown — like a regex *. SQL:1999's WITH RECURSIVE builds the closure iteratively; the book's version is 29 lines vs Cypher's 4, illustrating fit-to-purpose, not superiority.
Q13 — c. (lucy, age, 33) is a property because 33 is a literal; (lucy, marriedTo, alain) is an edge because alain is a vertex. RDF doesn't distinguish the two — both are predicates — which is why SPARQL uses one syntax for both.
Q14 — d. The four real differences are schema freedom, direct access by ID/index, no maintained ordering, and declarative query languages. Triples vs tables is not among them — property graphs (the model compared) aren't triple-stores, and CODASYL wasn't tabular either.
