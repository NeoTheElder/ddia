Batch Processing

A system cannot be successful if it is too strongly influenced by a single person. Once the initial design is complete and fairly robust, the real test begins as people with many different viewpoints undertake their own experiments. — Donald Knuth

Part III opens here. Parts I and II assumed one database. Real applications combine several datastores, indexes, caches, and analytics systems, and must move data between them. The book's organizing distinction for Part III: systems of record (the source of truth — new data is written here first, each fact represented once) versus derived data (the result of transforming data from another system — caches, indexes, materialized views, denormalized copies, recommendation summaries — redundant, recreatable from the source, and essential for read performance). A database is neither by nature; the distinction is in how you use it, and being explicit about which data derives from which brings clarity to a confusing architecture. Chapter 10 covers batch dataflow, Chapter 11→11 applies the same ideas to streams, and Chapter 12→12 builds applications from them.

Parts I and II were about requests and responses: you ask, the system answers, a human waits, so response time matters (Chapter 1←1). That isn't the only style. Three kinds of system: services (online — handle each request fast; response time and availability rule), batch processing (offline — take a large input, run a job for minutes to days, produce an output; nobody waits; throughput is the measure; typically scheduled), and stream processing (near-real-time — consume inputs and produce outputs like batch, but on events shortly after they happen). MapReduce (2004) — "the algorithm that makes Google so massively scalable," implemented in Hadoop, CouchDB, MongoDB — is low-level compared to the parallel data warehouses that preceded it, and its importance is declining, but it gives a clear picture of why batch processing is useful. It is also very old: Hollerith punch-card tabulators computed the 1890 US Census in batch, and MapReduce uncannily resembles the IBM card-sorting machines of the 1940s–50s.

FEYNMAN · the whole chapter in one idea Everything here descends from one shell command: cat log | awk | sort | uniq -c | sort -rn | head. Small tools that each do one thing, joined by a uniform interface (a stream of bytes), inputs never modified, outputs completely replaced, so you can rerun and tinker fearlessly. MapReduce is that pipeline spread across a thousand machines: the mapper is awk, the shuffle is sort, the reducer is uniq -c, and HDFS is the pipe — except the pipe is a file that gets written to disk between every stage. Joins and grouping are the same trick: give related records the same key and the sort puts them side by side. The rest of the chapter is what people fixed about the pipe: dataflow engines (Spark, Flink) stream between stages like real Unix pipes; Pregel lets a computation loop; declarative APIs let an optimizer pick the join. Colors as always: ember = writes / output, cyan = reads / input.
batch-processing-with-unix-tools

Batch Processing with Unix Tools

A web server appends one line per request to its log (nginx's default format): remote address, user, timestamp, request line, status, bytes, referer, user agent. One line tells you that on 27 Feb 2015 at 17:55:11 UTC, 216.58.210.78 fetched /css/typography.css, got a 200 and 3,377 bytes, using Chrome 40, referred from the site's front page.

Simple Log Analysis

simple-log-analysis

Find the five most popular pages with nothing but the shell:

cat /var/log/nginx/access.log |
  awk '{print $7}' |      # the requested URL
  sort             |      # identical URLs become adjacent
  uniq -c          |      # count adjacent duplicates
  sort -r -n       |      # most requested first
  head -n 5

Obscure-looking, incredibly powerful: it chews through gigabytes in seconds and is trivially adapted — drop CSS files with '$7 !~ /\.css$/ {print $7}', count client IPs with '{print $1}'. A surprising amount of analysis fits in awk, sed, grep, sort, uniq, and xargs, and it performs.

Chain of commands versus custom program

You could write the same thing in Ruby: a hash table from URL to count, incremented per line, then sorted and truncated. Less concise, arguably more readable, and a matter of taste — but the execution differs. Sorting versus in-memory aggregation: the Ruby script's working set is the number of distinct URLs (a million hits on one URL cost one hash entry), so for most sites it fits in memory and works fine on a laptop. When the working set exceeds memory, the sort approach wins because it uses disks efficiently: sort chunks in memory, write sorted segments, mergesort them — the sequential-I/O principle from Chapter 3←3. GNU coreutils' sort does that automatically and parallelizes across cores.

The Unix Philosophy

the-unix-philosophy

It's no accident that a chain of commands solved this — it was a design idea of Unix that remains astonishingly relevant. Doug McIlroy described pipes in 1964 as a garden hose: "screw in another segment when it becomes necessary to massage data in another way." The Unix philosophy as stated in 1978: (1) make each program do one thing well — build afresh rather than complicate old programs with features; (2) expect every program's output to become the input to another, unknown program — don't clutter output, avoid rigid or binary formats, don't insist on interactive input; (3) design and build software to be tried early, and throw away the clumsy parts; (4) use tools to lighten programming tasks, even if you must build the tools and discard them afterwards. Automation, rapid prototyping, incremental iteration, experimentation, small manageable pieces — it sounds like Agile and DevOps, four decades early. sort is the exemplar: a better sort than most standard libraries (it spills to disk, it uses threads), useless alone, powerful with uniq. What lets programs written by different people compose so well?

A uniform interface

If one program's output is another's input, they need a compatible format — and to connect any output to any input, everyone needs the same interface. In Unix that's a file (a file descriptor): an ordered sequence of bytes. So simple that a filesystem file, a pipe, stdin/stdout, a device driver, and a TCP socket all share it and can all be plugged together. (URLs and HTTP are the same idea on the web: any page can link to any other, unlike BBS-era systems with their own phone numbers and baud rates.) By convention most tools treat the bytes as ASCII text with \n as record separator — arbitrary (the ASCII record separator 0x1E was made for this) but universal, so tools interoperate. Parsing within a record is vaguer (whitespace, tabs, CSV, pipes; xargs has half a dozen options). And {print $7} is not beautiful — {print $request_url} would be nicer; the chapter returns to that. Imperfect as it is, the uniform interface is still remarkable: you can't pipe your email and shopping history through an analysis tool into a spreadsheet and onto a wiki. Even databases with the same data model rarely move data between each other easily — the Balkanization of data.

Separation of logic and wiring

Programs use stdin and stdout and don't care where the bytes come from or go. The shell user wires inputs and outputs — from files, to files, through pipes (a small in-memory buffer, no intermediate file on disk). That's loose coupling, late binding, inversion of control: separating wiring from logic makes small tools composable into big systems, and your own program can join the pipeline just by reading stdin and writing stdout — a user-agent translator, an IP-to-country lookup. Limits: multiple inputs/outputs are awkward, you can't pipe into a network connection (BSD sockets broke the everything-is-a-file idea; Plan 9 kept it), and a program that opens its own files, subprocesses, or connections has taken the wiring into its own hands.

Transparency and experimentation

Unix tools make it easy to see what's happening: inputs are immutable, so you can rerun with different options without damage; you can stop the pipeline anywhere and pipe into less to inspect; you can write a stage's output to a file and restart from there without redoing earlier work. Blunt compared to a query optimizer, yet superb for experimentation. Their one big limitation: they run on a single machine. Enter Hadoop.

FEYNMAN · why a stream of bytes beats a clever API The genius of the Unix interface is how dumb it is. A richer interface — typed records, method calls — would let two programs cooperate better, but only the two programs that agreed on it. "A sequence of bytes, newline-separated" lets a program written in 1975 feed one written yesterday, by someone who never heard of it. The trade is real: $7 instead of $request_url, and every tool re-parses text. Hadoop keeps the philosophy and fixes the trade by using structured, schema-carrying formats — the Avro and Parquet of Chapter 4←4 — as its "bytes."
mapreduce-and-distributed-filesystems

MapReduce and Distributed Filesystems

MapReduce is Unix tools distributed over thousands of machines: blunt, brute-force, surprisingly effective. One job is like one Unix process — inputs in, outputs out, input unmodified, no side effects, output files written once sequentially. Where Unix uses stdin/stdout, MapReduce reads and writes a distributed filesystem: in Hadoop, HDFS, an open-source reimplementation of the Google File System (others: GlusterFS, QFS; object stores like S3, Azure Blob, Swift are similar — though they separate storage from compute, forfeiting the run-the-task-where-the-data-is locality that HDFS offers, which erasure coding forfeits anyway). HDFS is shared-nothing — no special hardware, unlike NAS/SAN shared-disk appliances with Fibre Channel: a daemon on every machine exposes its local disks; a central NameNode tracks which blocks live where; together they form one big filesystem. Blocks are replicated across machines for fault tolerance — plain copies, or erasure coding (Reed–Solomon) for lower storage overhead; RAID across a network, essentially. HDFS deployments have reached tens of thousands of machines and hundreds of petabytes, because commodity hardware plus open source is far cheaper than a storage appliance.

MapReduce Job Execution

mapreduce-job-execution

The pattern is the log-analysis pipeline: (1) read input files and split them into records (one log line each — the input format parser); (2) call the mapper on each record to extract a key and value (awk '{print $7}': key = URL, value empty); (3) sort all key-value pairs by key (the first sort — implicit, you never write it); (4) call the reducer over the sorted pairs, which sees all values for one key adjacent and combines them without much state (uniq -c). You write steps 2 and 4. The mapper is called once per record, may emit zero or many pairs, and keeps no state between records. The reducer gets a key and an iterator over all its values and emits output records. The second sort (ranking) needs a second MapReduce job fed by the first's output — the mapper prepares data for sorting, the reducer processes sorted data.

Distributed execution of MapReduce

The difference from Unix: MapReduce parallelizes across machines without you writing parallel code. Mapper and reducer handle one record at a time and don't know where input comes from or output goes, so the framework moves data between machines (Chapter 2←2 met them as JavaScript functions; in Hadoop they're Java classes). Reduce-Side Joins and Grouping

reduce-side-joins-and-grouping

Chapter 2 discussed joins as a data-model question; here is how they're implemented. A join is needed whenever code must access both sides of an association — a foreign key, a document reference, a graph edge; denormalization reduces but rarely removes the need (Chapter 2←2). A database resolves a small query's joins with index lookups; MapReduce has no indexes and reads its entire input — a full table scan, outrageous for a few records but reasonable for analytic aggregation over everything, especially parallelized. A batch join means resolving all occurrences of the association at once, not looking up one user.

The book's example (Figure 10-2): a log of user activity events (clickstream — the fact table of a star schema, Chapter 3←3) containing user IDs, and a user database with dates of birth (a dimension). To learn which pages are popular with which age groups you must join them. The naive way — query the user database over the network for each event — is slow (round trip per record), cache-dependent, can overwhelm the database, and is nondeterministic because the remote data may change mid-job. Better: ETL a copy of the user database into HDFS beside the events, and let MapReduce bring related records together.

Handling skew

"All records with the same key to one place" breaks on hot keys — a celebrity with millions of followers (linchpin objects). One reducer gets far more work, and since a job finishes only when its slowest reducer does, everything downstream waits (Chapter 6←6). Remedies: Pig's skewed join first samples to find hot keys, then sends a hot key's records to one of several random reducers while replicating the other join input to all of them — more parallelism, at the cost of replication (Crunch's sharded join is the same with hot keys declared explicitly). Hive's skewed join stores hot-key records in separate files and uses a map-side join for them. For grouping by a hot key, aggregate in two stages: random reducers compute partial aggregates, a second job combines them.

Map-Side Joins

map-side-joins

Reduce-side joins assume nothing about the input — the mappers prepare whatever they're given — but the sorting, copying, and merging are expensive and may write data to disk several times. If you can assume things about the input, a map-side join skips reducers and sorting entirely: each mapper reads one input block and writes one output file.

So the physical layout of datasets — number of partitions, partitioning and sort keys — becomes metadata you must know to pick a join strategy; Hadoop keeps it in HCatalog and the Hive metastore.

FEYNMAN · three ways to join two piles of paper You have a crate of receipts (events) and a folder of customer cards (users). Sort-merge (reduce-side): sort both by customer number, then walk through them side by side — works for any two piles, but you have to sort everything first, which is the expensive bit. Broadcast hash: if the customer folder is thin, photocopy it for every clerk; each clerk just flips to the right card for each receipt. Partitioned hash: if receipts and cards were already filed into the same ten drawers by last digit, each clerk takes one drawer of each — smaller stacks, no copying. Merge: if the drawers are already sorted too, each clerk walks both stacks without even needing a table to lay cards out. Each step down needs more to be true about the piles before you start — which is why knowing how a dataset is laid out matters as much as knowing its format.

The Output of Batch Workflows

the-output-of-batch-workflows

What is all this processing for? Not OLTP (few records by key for a user) and not exactly analytics (a report for a manager — Chapter 3←3), though closer to the latter: batch output is usually some other kind of structure.

Building search indexes

Google's original MapReduce use: building the web search index as a workflow of 5–10 jobs (it later moved on, but Hadoop still builds Lucene/Solr indexes well). A full-text index maps each term to its postings list of document IDs (Chapter 3←3); for a fixed document set, mappers partition the documents, each reducer builds the index for its partition, and the immutable index files go to HDFS — a document-partitioned index (Chapter 6←6) that parallelizes beautifully. When documents change, either rerun the whole workflow and swap the index wholesale (expensive if little changed, trivially easy to reason about: documents in, index out) or build incrementally as Lucene does with new segments and background merging — the topic of Chapter 11.

Key-value stores as batch process output

Another common output: databases behind machine-learning systems — classifiers (spam, anomaly, image recognition) and recommenders (people you may know, related products) — queried by user or product ID from the web application, which lives outside Hadoop. How does the output get there? Writing to the production database from inside mappers or reducers, one record at a time, works but is a bad idea: a network request per record is orders of magnitude slower than batch throughput; parallel tasks writing at batch rates can overwhelm the database and degrade its service to real users; and it breaks MapReduce's all-or-nothing guarantee — external side effects from partially completed jobs, retried attempts, and speculative execution become visible. Far better: build a brand-new database inside the job, write it as files to the output directory like a search index, and bulk-load the immutable files into read-only serving nodes. Voldemort, Terrapin, ElephantDB, and HBase bulk loading all support this. It's a natural fit — mapper extracts a key, sort by key, that's most of index building — and because the files are write-once the data structures are simple (no WAL needed). Voldemort keeps serving the old files while the new ones copy to local disk, then atomically switches; if anything goes wrong it switches back, since the old files are still there.

Philosophy of batch process outputs

This is the Unix philosophy applied: explicit dataflow, input unchanged, previous output completely replaced, no other side effects — so you can rerun as often as you like. The payoffs beyond performance: human fault tolerance — buggy code that produced bad output is fixed by rolling back the code and rerunning, or just switching back to the old output directory, whereas a database with read-write transactions keeps the bad data after the rollback; hence faster feature development, since mistakes aren't irreversible (minimizing irreversibility); automatic task retry is safe only because inputs are immutable and failed tasks' outputs are discarded; the same files feed many jobs, including monitoring jobs that check an output's characteristics against the previous run; and logic is separated from wiring (input/output directories), so one team builds a job that does one thing well and others decide where and when to run it. One difference from Unix: instead of untyped text needing {print $7}, Hadoop uses structured, schema-carrying, evolvable formats — Avro and Parquet (Chapter 3←3, Chapter 4←4).

Comparing Hadoop to Distributed Databases

comparing-hadoop-to-distributed-databases

Hadoop is a distributed Unix: HDFS the filesystem, MapReduce a quirky process that always runs sort between map and reduce. None of the join algorithms above were new in 2004 — massively parallel processing (MPP) databases (Gamma, Teradata, Tandem NonStop SQL) had them a decade earlier. The difference: MPP databases parallelize analytic SQL on a cluster; MapReduce plus a distributed filesystem is closer to a general-purpose operating system that runs arbitrary programs.

Designing for frequent faults

Are task failures really that frequent? Hardware failures aren't — most jobs would never see one. The explanation is Google's environment: mixed-use datacenters where online services and batch jobs share machines under container resource limits and priorities; lower-priority tasks are preempted when higher-priority ones need resources, and priority sets the price. That lets non-production resources be overcommitted for better utilization — batch jobs "pick up the scraps under the table." An hour-long MapReduce task at Google had about a 5% chance of preemption, an order of magnitude above hardware failure; with 100 ten-minute tasks, the odds that at least one is killed exceed 50%. MapReduce tolerates frequent termination not because hardware is unreliable but because the freedom to kill processes buys cluster utilization. Open-source schedulers preempt less (YARN's CapacityScheduler for queue balancing; not general priority preemption in YARN, Mesos, or Kubernetes at the time), and where tasks are rarely killed, MapReduce's design choices make less sense — which motivates the next section.

beyond-mapreduce

Beyond MapReduce

MapReduce got the hype of the late 2000s, but it is one of many programming models; the right tool depends on data volume, structure, and processing type. The chapter dwelt on it because it is a clear abstraction over a distributed filesystem — simple to understand, not simple to use: writing a complex job against raw MapReduce APIs is laborious (you'd implement your own joins). Higher-level models — Pig, Hive, Cascading, Crunch — fixed the ergonomics. But the execution model itself has problems no abstraction layer fixes: it is extremely robust (arbitrary data, unreliable multi-tenant clusters, frequent terminations — it gets there, slowly) yet other tools are orders of magnitude faster for some workloads. This section covers those alternatives; Chapter 11's stream processing is another way of speeding batch up.

Materialization of Intermediate State

materialization-of-intermediate-state

Every MapReduce job is independent; its only contact with the world is its input and output directories. Chaining jobs means directory names plus an external scheduler. Fine when a job's output is a dataset you want to publish — named, reused by other teams, loosely coupled. But often an output is consumed by exactly one downstream job maintained by the same team: it is intermediate state, and recommendation workflows of 50–100 jobs have a great deal of it. Writing it to files is materialization (as in materialized views — compute eagerly and store, rather than on demand; Chapter 3←3). Unix pipes don't materialize; they stream through a small buffer. Full materialization has three costs: a job can start only when every task of its predecessors finished, so stragglers (skew, uneven load) stall the whole workflow, whereas piped processes run concurrently; redundant mappers that merely re-read what a reducer just wrote and re-prepare it — logic that could have lived in the previous reducer; and intermediate files are replicated across nodes, overkill for temporary data.

Dataflow engines

Spark, Tez, and Flink were built to fix this. They differ in design but share one idea: handle the entire workflow as one job rather than independent sub-jobs, explicitly modeling how data flows through stages — hence dataflow engines. Like MapReduce they call a user function per record on one thread, parallelize by partitioning, and copy one function's output over the network to another's input. Unlike MapReduce, functions (operators) need not alternate strictly map/reduce, and the engine offers several ways to connect them: repartition-and-sort by key (the shuffle — enabling sort-merge joins and grouping); partition without sorting (enough for partitioned hash joins, since the hash table randomizes order anyway); or broadcast one operator's output to every partition of another (broadcast hash joins). Descended from research systems Dryad and Nephele, they gain: sorting only where needed instead of between every stage; no redundant map tasks (a mapper's work folds into the preceding reducer, since a mapper doesn't change partitioning); locality scheduling, because all dependencies are declared — a consumer can run on the producer's machine and exchange data through shared memory; intermediate state in memory or local disk rather than replicated on HDFS (MapReduce did this only for mapper output); operators that start as soon as input is ready, without waiting for the whole preceding stage; and JVM reuse instead of a new JVM per task. Same computations, significantly faster — and since operators generalize map and reduce, Pig/Hive/Cascading workflows switch from MapReduce to Tez or Spark by configuration. Tez is a thin library over YARN's shuffle service; Spark and Flink are full frameworks with their own networking, scheduler, and APIs.

Graphs and Iterative Processing

graphs-and-iterative-processing

Chapter 2 used graphs for OLTP-style queries — find a few vertices fast (Chapter 2←2). Batch graph processing analyzes a whole graph offline — recommendation engines, ranking; the famous example is PageRank, estimating a page's popularity from who links to it. (Naming trap: dataflow engines arrange operators as a DAG while the data is relational tuples; in graph processing the data itself is a graph.) Many graph algorithms traverse one edge at a time, propagating information from vertex to neighbor, repeating until done — no more edges to follow, or a metric converges (Chapter 2's transitive closure over "located within" edges). Plain MapReduce makes one pass, so the loop must be external: a scheduler runs one step as a batch job, checks the completion condition, and reruns. It works but is wasteful — every iteration reads the entire graph and writes a whole new one even if only a sliver changed.

The Pregel processing model

The bulk synchronous parallel (BSP) model — Apache Giraph, Spark's GraphX, Flink's Gelly — is better known as the Pregel model after Google's paper. Recall that MapReduce mappers conceptually "send a message" to the reducer call for a key. In Pregel, vertices send messages to other vertices, typically along edges. Each iteration calls a function per vertex with all messages sent to it — like a reducer call — but unlike MapReduce, a vertex keeps its state in memory between iterations, so the function processes only new messages, and quiet parts of the graph do no work. It resembles the actor model with a vertex as an actor, except state and messages are fault-tolerant and durable and communication proceeds in fixed rounds: every message sent in iteration n is delivered in iteration n+1.

High-Level APIs and Languages

high-level-apis-and-languages

Batch infrastructure matured to petabytes on 10,000-machine clusters; with physical operation "more or less solved," attention moved to the programming model, efficiency, and breadth of problems. Hive, Pig, Cascading, and Crunch arose because hand-written MapReduce is laborious, and with Tez they could switch execution engines without rewriting jobs; Spark and Flink ship their own high-level dataflow APIs, inspired by FlumeJava. These APIs use relational building blocks — join on a field, group by key, filter, aggregate by count or sum — implemented with the join and grouping algorithms above. Less code, and interactive use: write analysis incrementally in a shell, run it often, see what it does — the Unix spirit of experimentation. And they make the machine more efficient too.

The move toward declarative query languages

Specify a join as a relational operator rather than as code, and the framework can inspect the inputs and pick the join algorithm — Hive, Spark, and Flink have cost-based optimizers that also reorder joins to minimize intermediate state. You needn't remember the algorithms in this chapter; declare the join and let the optimizer choose (the argument of Chapter 2←2). Yet MapReduce and its successors differ from SQL's fully declarative model: they're built on function callbacks — per record or group, a user function runs arbitrary code, drawing on whole library ecosystems for parsing, NLP, image analysis, statistics. That freedom to run arbitrary code (with real package managers — Maven, npm, Rubygems — not databases' clumsy UDFs) is what long separated MapReduce-heritage systems from MPP databases. Dataflow engines found declarative features pay off beyond joins: a callback that merely filters or selects fields costs a function call per record; expressed declaratively, the optimizer can use column-oriented layouts (Chapter 3←3) to read only needed columns and run vectorized, cache-friendly inner loops without function calls — Hive, Spark DataFrames, Impala do this; Spark generates JVM bytecode, Impala uses LLVM for native code. With declarative pieces plus optimizers, batch frameworks start to look like MPP databases and match their performance, while keeping the flexibility of arbitrary code over arbitrary formats.

Specialization for different domains

Arbitrary code is essential, but recurring patterns deserve reusable building blocks. MPP databases served business intelligence; other domains grew: statistical and numerical algorithms for machine learning — Mahout implements ML on MapReduce, Spark, and Flink; MADlib does similar work inside a relational MPP database (Apache HAWQ); spatial algorithms like k-nearest neighbors (similarity search in a multi-dimensional space); approximate string matching for genome analysis. As batch engines gain built-in operators and MPP databases gain programmability, the two converge: in the end they are all just systems for storing and processing data.

FEYNMAN · the two ends met in the middle Start from opposite corners. MPP databases began with a tightly integrated engine and a declarative language — fast, elegant, and only able to do what SQL can say. MapReduce began with a dumb filesystem and "call my function on every record" — able to do anything, slow at everything, and you write your own joins. Ten years on, each borrowed the other's virtue: batch engines grew optimizers, columnar formats, and declarative DataFrames; databases grew UDFs and ML libraries inside the engine. The chapter's quiet conclusion is that the interesting property was never "database vs Hadoop" but the two dials underneath — how much you declare versus code, and how much you materialize versus stream. Chapter 11 turns the second dial all the way toward streaming.

Core takeaways

  • Three kinds of system: services (request/response, response time and availability), batch (large input → job → output, throughput, scheduled, nobody waiting), stream (batch's inputs-and-outputs shape applied to events soon after they happen). Part III's frame: systems of record vs derived data, and being explicit about which derives from which.
  • Unix pipelines are batch processing: awk (map) → sort (bring equal keys together) → uniq -c (reduce) → second sort (another job). GNU sort spills to disk and uses all cores, so the approach scales past memory where an in-memory hash table wouldn't.
  • The Unix philosophy: do one thing well; expect output to feed an unknown program; build to try early and throw away; prefer tools. Enabled by a uniform interface (a file = a byte sequence, newline-separated text by convention), separation of logic from wiring (stdin/stdout, pipes), and transparency (immutable inputs, inspect anywhere, restart from a saved stage). Limit: one machine.
  • MapReduce = distributed Unix: HDFS (shared-nothing daemons + NameNode, replicated or erasure-coded blocks) is the pipe; a job reads input files, maps records to key-value pairs, sorts implicitly, reduces per key. Mappers run near their input block; each partitions its sorted output per reducer; the shuffle copies and merges; reducers write to HDFS. Workflows chain jobs by directory with schedulers (Airflow, Oozie…), since a failed job's partial output is discarded.
  • Joins without indexes: full scans, all associations at once. Reduce-side sort-merge join: mappers from both inputs emit the join key; the shuffle co-locates all records per key; secondary sort puts the dimension record first; the reducer joins with one record in memory. The key is an address — transport is separated from logic. GROUP BY (counts, sums, top-k, sessionization) is the same pattern. Skew from hot keys: sample and randomize (Pig skewed join, Crunch sharded join), separate files + map-side join (Hive), or two-stage aggregation.
  • Map-side joins skip the shuffle when you can assume things about inputs: broadcast hash (small input in every mapper's memory), partitioned hash (both inputs partitioned identically), merge (partitioned and sorted). Output partitioning follows the large input; physical layout metadata (HCatalog/Hive metastore) becomes essential.
  • Batch outputs are structures, not reports: search indexes (document-partitioned, immutable, rebuilt or incrementally merged) and key-value stores for ML/recommendations — built as files inside the job and bulk-loaded into read-only serving nodes with an atomic switch (Voldemort, ElephantDB, HBase bulk load), never written record-by-record into a live database (slow, overwhelming, leaks side effects).
  • Philosophy of outputs: immutable inputs, wholly replaced outputs, no side effects ⇒ human fault tolerance (roll back code and rerun, or switch back to old output), minimized irreversibility, safe automatic retries, reusable inputs, separated logic and wiring. Hadoop improves on Unix text with schema-carrying Avro/Parquet.
  • Hadoop vs MPP databases: MPP = parallel SQL on carefully modeled data, monolithic and fast for its queries, whole-query retry, in-memory. Hadoop = a general-purpose OS over raw files (data lake, schema-on-read, "raw data is better"), arbitrary code and many processing models on one shared cluster (Hive SQL, HBase, Impala), task-level retry and eager disk writes — designed for Google's mixed-use datacenters where low-priority tasks face ~5% preemption per hour for utilization's sake.
  • Materialization of intermediate state (MapReduce's replicated temp files) costs straggler barriers, redundant mappers, and needless replication. Dataflow engines (Spark, Tez, Flink) treat the workflow as one job of operators: sort only where needed, partition-only or broadcast connections, in-memory/local-disk hand-off, pipelined start, locality scheduling, JVM reuse. Fault tolerance by recomputation from lineage (RDDs) or checkpoints — requiring deterministic operators; materialize when recompute is dearer.
  • Graphs: iterative algorithms (PageRank, transitive closure) don't fit single-pass MapReduce. Pregel / BSP: vertices keep state across supersteps, exchange messages delivered exactly once in the next round, do work only when messaged, stop when messages cease; checkpoint at round boundaries. Heavy cross-machine traffic under arbitrary partitioning means single-machine processing often wins if the graph fits.
  • High-level APIs (Hive, Pig, Spark, Flink DataFrames, FlumeJava heritage) offer relational operators, interactive use, and declarative joins/filters that cost-based optimizers turn into the right algorithm, columnar reads, and vectorized or code-generated loops — approaching MPP performance while keeping arbitrary code (Mahout, MADlib, k-NN, genomics). Batch engines and MPP databases converge.
  • 2nd-edition arc (Ch 11): MapReduce explicitly cut to a teaching tool; Spark/Flink default; S3 object storage replaces HDFS (erasure coding, spot instances, cloud schedulers); lakehouse and data mesh; ML training pipelines (embeddings, Ray) as the headline batch workload; derived-data serving stores like Venice. The Unix framing and the join algorithms are unchanged.

Answer key with explanations
Q1 — c. Sorting is a means: adjacency lets uniq -c count with no hash table. Deduplication (b) is what uniq does after sorting; ranking (d) needs the second sort -rn.
Q2 — b. The working set is the number of distinct keys, not log lines (c): a million hits on one URL is one hash entry. Below memory the hash table is fine (so not (a)); above it, sort's sequential mergesort wins — the SSTable principle.
Q3 — d. The book stresses how dumb the interface is — and that its dumbness is why unrelated programs from different decades compose. Typed records (c) are exactly what Unix lacks ($7 vs $request_url); Hadoop adds them via Avro/Parquet.
Q4 — a. "Shuffle" is a misnomer — the book notes there is no randomness (b). Mapper output goes to local disk, not HDFS (c). Reducer count is set by the job author independently of mapper count (d).
Q5 — c. All four reasons are in the text; determinism matters because a batch job should give the same output for the same input. (d) is false — it can, which is why the book has to argue against it.
Q6 — b. The secondary sort orders within a key. (d) describes skewed-join techniques; (c) is a separate job.
Q7 — d. (a) is the map-side merge join; (b) the partitioned hash join. Hot keys (c) call for skewed/sharded joins or Hive's separate-files trick.
Q8 — a. The alternative is to build the database as files inside the job and bulk-load them into read-only serving nodes with an atomic switch (Voldemort, ElephantDB, HBase bulk load).
Q9 — c. Recoverability from buggy code, not from human operators' mistakes at runtime. It follows from immutability and follows the principle of minimizing irreversibility.
Q10 — b. The book explicitly rejects (a): hardware failures are rare enough that most jobs never see one. Batch jobs "pick up the scraps under the table" and get killed when production needs the resources.
Q11 — d. (d) is the cost of not materializing — the dataflow engines' trade-off, handled by recomputation. (a)–(c) are the three downsides the book lists for MapReduce's approach.
Q12 — a. Nondeterminism creeps in through hash-iteration order, random numbers, clocks, and external data; fix seeds and remove it. Recompute isn't always cheapest — small or CPU-heavy intermediate data may be worth materializing.
Q13 — c. Pregel is iterative by design (so not (b)) and message-passing over the network (so not (d)); the actor-model comparison holds except for durability and fixed rounds.
Q14 — b. Optimal partitioning that co-locates chatty vertices is hard, so practice uses arbitrary IDs. Distributed Pregel is unavoidable only when the graph can't fit on one machine.
Q15 — d. The convergence argument: declarative pieces + optimizers make batch engines look like MPP databases (Hive, Spark DataFrames, Impala; Spark generates bytecode, Impala uses LLVM), while callbacks retain the flexibility databases lack.
