Encoding and Evolution

Everything changes and nothing stands still. — Heraclitus of Ephesus, as quoted by Plato in Cratylus (360 BCE)

Applications change: features are added, requirements are understood better, business circumstances shift. Chapter 1←1 named the goal — evolvability — and this chapter is where it gets concrete, because a change to features almost always means a change to the data: a new field, a new record type, an old field presented differently. The data models of Chapter 2←2 cope differently: relational databases enforce exactly one schema at a time (changed by migrations); schema-on-read databases can hold a mixture of old and new formats written at different times.

FEYNMAN · the whole chapter in one idea Two processes that don't share memory can only exchange bytes, so every piece of data that crosses a process boundary — to disk, over the network, into a queue — has to be turned into bytes (encoded) and turned back (decoded). The catch: the encoder and the decoder are rarely the same version of your code. Deployments roll out gradually, users don't update their apps, and data written five years ago is still on disk. So the real question of this chapter is: how do you choose a byte format such that old code and new code can keep talking to each other while everything is mid-change? Colors as always: ember = writing/encoding, cyan = reading/decoding.
compatibility (framing)

Why old and new must coexist

When a data format changes, application code has to change too — but in a large system code changes cannot happen all at once. Server-side, you want a rolling upgrade (staged rollout): deploy the new version to a few nodes, watch it, work through the rest — zero downtime, which encourages frequent small releases. Client-side you're at the mercy of the user, who may not install the update for months. So old and new code, and old and new data formats, coexist — and the system has to stay compatible in both directions:

This chapter examines encoding formats — JSON, XML, Protocol Buffers, Thrift, Avro — through exactly this lens: how do they handle schema change, and how do they let old and new data and code coexist? Then it follows the data as it flows: through databases, through services (REST and RPC), and through message-passing systems.

formats-for-encoding-data

Formats for Encoding Data

Programs hold data in (at least) two representations. In memory: objects, structs, lists, hash tables, trees — optimized for CPU access, full of pointers. On the wire or on disk: a self-contained sequence of bytes, since a pointer means nothing to another process. Translating memory → bytes is encoding (also serialization, marshalling); bytes → memory is decoding (parsing, deserialization, unmarshalling). The book says encoding throughout, because "serialization" also means something entirely different in transactions→7. (And encoding has nothing to do with encryption.)

Language-Specific Formats

language-specific-formats

Every language ships one: Java's java.io.Serializable, Ruby's Marshal, Python's pickle, plus libraries like Kryo. Convenient — objects saved and restored with almost no code — and deeply problematic:

  • Language lock-in. Reading the data from another language is very hard; you've committed your data to your current language for potentially decades and precluded integration with other organizations.
  • Security. Decoding must instantiate arbitrary classes. If an attacker can feed your application a byte sequence to decode, they can instantiate arbitrary classes — which routinely leads to remote code execution.
  • Versioning is an afterthought — forward and backward compatibility are neglected.
  • Efficiency is an afterthought — Java's built-in serialization is notorious for poor performance and bloated output.

Verdict: use them for very transient purposes only.

JSON, XML, and Binary Variants

json-xml-and-binary-variants

The standardized, cross-language options: JSON, XML (widely known, widely supported, almost as widely disliked — XML for verbosity and complexity; JSON popular for browser support and relative simplicity), and CSV (popular, less powerful). All three are textual and roughly human-readable. Beyond syntax debates, the subtle problems:

  • Numbers are ambiguous. XML and CSV can't tell a number from a digit string without an external schema. JSON distinguishes strings from numbers but not integers from floats, and specifies no precision. Integers above 253 can't be represented exactly in an IEEE 754 double, so JavaScript mangles them — which is why Twitter's API returns each 64-bit tweet ID twice, as a number and as a decimal string.
  • No binary strings. Unicode text is fine; raw bytes aren't supported, so people Base64-encode them and use the schema to say so. Hacky, and 33% bigger.
  • Schemas are optional and complicated. XML Schema is widely used; many JSON tools skip JSON Schema entirely — so the interpretation of numbers and binary has to be hardcoded in application logic instead.
  • CSV has no schema at all — meaning of rows and columns is up to the application; a new column is a manual change; and it's vague (commas and newlines in values), with escaping rules that not every parser honors.

Still: good enough for many purposes, and likely to stay popular as interchange formats between organizations — where getting people to agree on anything outweighs prettiness or efficiency.

Binary encoding

For data used only within your organization there's less pressure toward a lowest-common-denominator format; at terabyte scale, compactness and parse speed matter. Hence a profusion of binary encodings for JSON (MessagePack, BSON, BJSON, UBJSON, BISON, Smile…) and XML (WBXML, Fast Infoset). Some extend the datatypes (integers vs floats, binary strings) but keep the data model — and crucially, without a schema they must still embed every field name. The book encodes one record in every format that follows:

{
    "userName": "Martin",
    "favoriteNumber": 1337,
    "interests": ["daydreaming", "hacking"]
}

Thrift and Protocol Buffers

thrift-and-protocol-buffers

Apache Thrift (Facebook) and Protocol Buffers (Google), both open-sourced 2007–08, share a principle: a schema is required for anything encoded, written in an interface definition language —

Thrift IDLProtocol Buffers
struct Person {
  1: required string       userName,
  2: optional i64          favoriteNumber,
  3: optional list<string> interests
}
message Person {
    required string user_name       = 1;
    optional int64  favorite_number = 2;
    repeated string interests       = 3;
}

— and a code generator that turns the schema into classes in many languages; application code calls the generated code to encode and decode. (Thrift, confusingly, has two binary encodings — BinaryProtocol and CompactProtocol — plus a C++-only DenseProtocol and two JSON variants. "What fun!") One detail: required vs optional makes no difference to the bytes. required just enables a runtime check that fails if the field isn't set — useful for catching bugs.

Field tags and schema evolution

An encoded record is the concatenation of its fields; each field is identified by tag number and annotated with a datatype; unset fields are simply omitted. So tags carry the meaning: you can rename a field freely (names are never encoded), but you can never change a tag. Schema evolution follows from there:

Avro

avro

Apache Avro (2009, a Hadoop subproject born because Thrift didn't fit Hadoop's needs) also requires a schema, in two syntaxes — Avro IDL for humans, a JSON form for machines:

Avro IDLJSON schema
record Person {
    string               userName;
    union { null, long } favoriteNumber = null;
    array<string>        interests;
}
{"type": "record", "name": "Person", "fields": [
  {"name": "userName",       "type": "string"},
  {"name": "favoriteNumber", "type": ["null","long"],
                             "default": null},
  {"name": "interests",      "type": {"type":"array",
                             "items":"string"}}
]}

No tag numbers. The encoding (32 bytes, above) is pure values; the reader must walk a schema to interpret them. So how can Avro possibly evolve? With the idea that makes it interesting:

FEYNMAN · tags vs names Thrift and Protobuf label every box in the shipment with a number — compact, but somebody has to keep the master list of numbers forever and never hand out a used one twice. Avro labels nothing in the shipment; instead, sender and receiver each hold a packing list, and the receiver reconciles the two lists by item name: reorder freely, ignore items you didn't order, and for items you expected but didn't get, use your listed default. The cost is that the receiver must somehow obtain the sender's packing list — once per file, once per connection, or via a version stamp and a registry.

The Merits of Schemas

the-merits-of-schemas

Protobuf, Thrift, and Avro schemas are far simpler than XML Schema or JSON Schema (no regex validation, no numeric ranges) — which is why they're simple to implement and support so many languages. The idea is old: ASN.1 (1984) defined network protocols, its DER encoding still encodes X.509 SSL certificates, and it evolves schemas with tag numbers like Protobuf/Thrift — but it's complex and badly documented, so not a choice for new applications. Databases have proprietary binary protocols too, decoded by vendor drivers behind ODBC/JDBC. The case for schema-driven binary encodings:

  • Compactness — far smaller than binary-JSON variants, because field names are omitted.
  • Documentation that can't go stale — the schema is required for decoding, so it's guaranteed up to date, unlike hand-maintained docs.
  • Compatibility checks before deployment — a database of schemas lets you verify forward and backward compatibility ahead of time.
  • Code generation for statically typed languages — compile-time type checking.

Net: schema evolution gives you the flexibility of schema-on-read JSON databases plus better guarantees and tooling.

2ND EDITION · schema registries become infrastructure The 1st edition's "a database of schema versions is a useful thing to have" became a product category: the 2nd edition (Chapter 5 there) covers schema registries (Confluent-style) as standard infrastructure for evolving schemas in event streams — the registry assigns version IDs, stores every schema, and rejects incompatible changes at publish time. The refs suggest Avro and Protobuf dominate the discussion, with Thrift a smaller presence than in 2017 (low-confidence inference).
modes-of-dataflow

Modes of Dataflow

Compatibility is a relationship between the process that encodes and the process that decodes — but who is who? Data flows between processes in three common ways, each with its own compatibility shape:

Dataflow Through Databases

dataflow-through-databases

The writer encodes, the reader decodes. With a single process, the reader is a later version of the same process — storing data is sending a message to your future self, so backward compatibility is obviously required. But usually many processes hit the database concurrently, some on newer code and some on older (mid rolling-upgrade), so a value written by new code may be read by old code: forward compatibility is required too. And there's a snag beyond what the encoding format handles:

Different values written at different times — data outlives code

A database lets any value be updated any time, so it holds values written five milliseconds ago beside values written five years ago. Deploying a new version replaces all the code in minutes; the five-year-old data stays in its original encoding unless you explicitly rewrite it. Rewriting (migrating) a large dataset is expensive, so databases avoid it: most relational systems add a column with a NULL default without touching existing rows (MySQL being the exception that often rewrites the table), filling nulls in at read time. LinkedIn's Espresso stores Avro and leans on its schema-evolution rules. Either way, schema evolution lets the whole database look as if it had one schema even though storage holds records from many eras.

Archival storage

Snapshots for backup or for loading into a data warehouse←3 are the exception: you're copying anyway, so encode the copy consistently in the latest schema. Written once and immutable, dumps suit Avro object container files — or, for analytics, a column-oriented format like Parquet←3. More on archived data in Chapter 10→10.

Dataflow Through Services: REST and RPC

dataflow-through-services-rest-and-rpc

Over a network the usual arrangement is clients and servers: the server exposes an API — a service — and clients call it. The web is the canonical case (browsers making GET/POST requests; standardized HTTP, URLs, TLS, HTML). Clients can also be native apps or in-browser JavaScript (Ajax), receiving data like JSON rather than HTML. And a server is often a client of other services — the pattern of decomposing an application into services by function, called service-oriented architecture and lately rebranded microservices. Services resemble databases (submit and query data) but expose an application-specific API rather than arbitrary queries — an encapsulation that lets them restrict what clients can do. The design goal is independent deployability and evolvability — each service owned by one team releasing on its own schedule — which means old and new servers and clients coexist, and API encodings must be compatible across versions. Exactly this chapter's subject.

Web services: REST vs SOAP

HTTP-based services are called web services (a misnomer — they're used everywhere: user devices calling over the internet; service-to-service within a datacenter, a.k.a. middleware; and cross-organization data exchange like payment processing or OAuth). Two opposed philosophies:

The problems with remote procedure calls

Web services are the latest in a long line of network-API technologies with serious problems: EJB and Java RMI (Java only), DCOM (Microsoft only), CORBA (excessively complex, no compatibility story). All rest on the remote procedure call idea (1970s): make a network request look like a local function call — location transparency. Convenient-seeming and fundamentally flawed, because a network request is a different animal:

Current directions for RPC

RPC isn't going away. Frameworks exist over every encoding here — Thrift and Avro ship RPC; gRPC uses Protocol Buffers; Finagle uses Thrift; Rest.li uses JSON over HTTP — and the new generation is explicit that remote ≠ local: Finagle and Rest.li use futures/promises for asynchronous, failable actions (and for fanning out to several services in parallel and combining results); gRPC supports streams — a series of requests and responses over one call. Some provide service discovery (finding a service's IP and port), revisited under request routing→6. Binary custom RPC beats JSON-over-REST on performance, but REST wins on experimentation and debugging (curl, a browser), universal language support, and a vast tool ecosystem — so REST dominates public APIs, while RPC frameworks focus on service-to-service calls inside one organization's datacenter.

Data encoding and evolution for RPC

Clients and servers must be deployable independently. Versus databases there's a simplifying assumption: servers are updated first, then clients — so you need only backward compatibility on requests and forward compatibility on responses. Compatibility is inherited from the encoding: Thrift, gRPC, and Avro RPC follow their formats' rules; SOAP uses XML schemas (evolvable, with subtle pitfalls); RESTful APIs mostly use schema-less JSON, where adding optional request parameters and new response fields is conventionally compatible. The hard part: RPC often crosses organizational boundaries, so the provider can't force clients to upgrade — compatibility must hold for a very long time, and breaking changes mean maintaining multiple API versions side by side. Versioning has no consensus: a version in the URL or in the Accept header for REST; or, for API-key-identified clients, storing each client's requested version server-side and changing it through an admin interface (Stripe's approach).

Message-Passing Dataflow

message-passing-dataflow

Asynchronous message passing sits between RPC and databases: like RPC, a message is delivered to another process with low latency; like a database, it isn't sent directly but via an intermediary — a message broker (message queue, message-oriented middleware) that stores it temporarily. Versus direct RPC, the broker:

  • acts as a buffer when the recipient is unavailable or overloaded — improving reliability;
  • redelivers to a crashed process, preventing message loss;
  • spares the sender from knowing the recipient's IP and port — valuable in clouds where VMs come and go;
  • lets one message reach several recipients;
  • decouples sender from recipient: publish and forget who consumes.

Unlike RPC, it's usually one-way: the sender doesn't expect a reply (a response, if any, goes over a separate channel), and doesn't wait — it sends and forgets. Asynchronous.

Message brokers

Once the domain of commercial enterprise software (TIBCO, IBM WebSphere, webMethods), now open source: RabbitMQ, ActiveMQ, HornetQ, NATS, Apache Kafka — compared in depth in Chapter 11→11. Delivery semantics vary, but the shape is: a producer sends to a named queue or topic; the broker delivers to one or more consumers/subscribers; many producers and consumers may share a topic. A topic is one-way, but a consumer can publish onward to another topic (chaining, as Chapter 11→11 shows) or to a reply queue the original sender consumes — RPC-like request/response. Brokers impose no data model — a message is bytes plus metadata — so any encoding works, and a backward- and forward-compatible one gives maximum freedom to change publishers and consumers independently and deploy in any order. And if a consumer republishes to another topic, preserve unknown fields — the database hazard from earlier, in a new costume.

Distributed actor frameworks

The actor model is a concurrency model for a single process: instead of threads (races, locks, deadlocks), logic lives in actors — each representing one client or entity, with private local state, communicating only by asynchronous messages that may be lost; each processes one message at a time, so no thread worries. Distributed actor frameworks scale this across nodes with the same message-passing mechanism regardless of whether sender and receiver share a node — messages are transparently encoded, sent, decoded. Location transparency works better here than in RPC, because the model already assumes messages can be lost even locally; the local/remote mismatch is smaller. Essentially a message broker fused with a programming model — and rolling upgrades still demand compatibility, since messages flow between old and new nodes. In practice: Akka defaults to Java serialization (no compatibility) but can swap in Protobuf to enable rolling upgrades; Orleans defaults to a custom encoding without rolling-upgrade support (deploy a new cluster, shift traffic, retire the old — or plug in custom serialization); Erlang OTP, despite its high-availability pedigree, makes record-schema changes surprisingly hard — rolling upgrades are possible but need careful planning, and the newer maps type may help.

FEYNMAN · why the broker is the friendliest place to evolve A database is a message to your future self; RPC is a phone call that demands an answer now; a message broker is a mailbox. Mailboxes tolerate everything this chapter worries about: the recipient can be asleep (buffering), can have moved (no IP needed), can be several people (fan-out), and can read tomorrow (asynchrony). The only thing a mailbox can't fix is the letter's language — which is why the encoding you drop in the mailbox must be compatible both ways, so any consumer of any version can read any producer of any version.

Core takeaways

  • Rolling upgrades (a few nodes at a time, zero downtime, easy rollback) are what make frequent small releases safe — and they guarantee old and new code and data coexist. Client apps and stored data stay old far longer than servers.
  • Two directions of compatibility: backward (new code reads old data — easy, you know the past) and forward (old code reads new data — harder, it must ignore what it doesn't understand). Both are required, for a long time.
  • Encoding = memory → bytes; decoding = bytes → memory. Language-built-in serializers are transient-use only: lock-in, security holes (arbitrary class instantiation → RCE), no versioning, poor efficiency.
  • JSON/XML/CSV: fine for interchange between organizations, where agreement beats efficiency; but vague on numbers (JSON: ints vs floats, precision, the 253 problem), no binary strings (Base64, +33%), optional and heavyweight schemas. Binary-JSON variants save little because they still carry field names.
  • Thrift and Protocol Buffers: schema-required, code-generated; field tags replace names (59 → 33/34 bytes with packed tags and varints). Evolution rules: never change a tag; add fields only with new tags and only as optional/default; remove only optional fields and never reuse the tag; type changes risk truncation; Protobuf's repeated allows optional → list.
  • Avro: no tags, no types in the bytes (32 bytes); the reader reconciles the writer's schema with its own reader's schema by field name — reorder, ignore unknown, default missing. Rule: add/remove only fields with defaults; null only via unions. The writer's schema travels via file header, per-record version + registry, or connection negotiation. No tags ⇒ dynamically generated schemas; code generation optional; files self-describing.
  • Schemas earn their keep: compactness, documentation that can't drift, pre-deployment compatibility checks, code generation for static languages — schema-on-read flexibility with guarantees.
  • Dataflow through databases: a message to your future self; needs backward and forward compatibility; beware old code round-tripping records and dropping unknown fields; data outlives code, so schema evolution makes many eras look like one schema; archive dumps re-encode consistently (Avro container files, Parquet).
  • Dataflow through services: REST (HTTP philosophy, simple, curl-able, dominant for public APIs) vs SOAP (XML protocol, WS-*, WSDL, tooling-dependent). RPC's location transparency is a lie: requests and responses get lost (retries need idempotence), timeouts leave outcomes unknown, latency varies wildly, parameters must be encoded across languages. Modern RPC (gRPC, Finagle, Rest.li) is explicit about it: futures, streams, service discovery. Servers upgrade first ⇒ backward compat on requests, forward on responses; cross-org APIs need long-lived versioning.
  • Dataflow through messages: brokers buffer, redeliver, decouple, fan out, hide addresses — one-way and asynchronous; any encoding, but bidirectional compatibility gives deployment freedom. Actor frameworks fuse a broker with a concurrency model; their default encodings often block rolling upgrades.
  • 2nd-edition arc: schema registries as infrastructure, Stripe-style API versioning and idempotency keys as named practice, event-driven framing, virtual actors, and a new dataflow mode — durable execution/workflow engines (Temporal, Restate).

Answer key with explanations
Q1 — b. Backward = newer code reads older data (easy: you know the old format). Forward = older code reads newer data (harder: old code must gracefully ignore unknown additions). Rolling upgrades and slow client updates make both mandatory.
Q2 — d. Four problems from the text: tied to one language; deserialization instantiates arbitrary classes, a classic RCE vector (CWE-502); compatibility neglected; Java serialization notoriously slow and bloated.
Q3 — a. JSON numbers carry no int/float distinction or precision; IEEE 754 doubles represent integers exactly only up to 253. Twitter's 64-bit IDs overflow that, so JavaScript clients need the string form.
Q4 — c. Binary-JSON variants keep the JSON data model — including embedding userName, favoriteNumber, interests as strings — because there's no schema to make the names implicit. That's why Thrift/Protobuf (tags) and Avro (nothing) win so decisively.
Q5 — d. Encoded data refers to fields only by tag, never by name — so renames are free and tag changes are catastrophic. (b) and (c) are the other fatal moves: adding required fields breaks backward compat; reusing tags corrupts the meaning of old data still on disk.
Q6 — b. Every field carries a type annotation; from it the parser knows the field's length (or how to find it) and skips. This is why "add fields with new tags" preserves forward compatibility.
Q7 — c. Old writers never wrote the new field; if new readers require it, every old record fails the check. So post-deployment additions must be optional or defaulted. (Note required changes nothing on the wire — it's purely a runtime check.)
Q8 — a. Avro's central idea: writer's and reader's schemas need only be compatible; the library resolves them side by side by field name. Evolution rule: add/remove only fields with defaults.
Q9 — d. Embedding the schema per record would dwarf the data. Context decides: file header (Hadoop-style container files), version stamp + schema table (Espresso), or connection negotiation (Avro RPC). A schema registry is useful in every case.
Q10 — b. This was an explicit Avro design goal and not one for Thrift/Protobuf. Name-based matching means regenerated schemas stay compatible with old readers; tag assignment would need careful manual bookkeeping.
Q11 — c. The encodings can carry unknown fields; the loss happens at the application layer when decode → model object → encode drops what the object has no slot for. Awareness is the whole fix.
Q12 — a. Rewriting large datasets is expensive, so databases avoid it (adding a NULL-default column touches no rows); the mixture of eras is hidden by schema evolution — or re-encoded consistently when you archive anyway.
Q13 — d. The book's list: unpredictability and loss, the timeout "fourth outcome," retry duplication needing idempotence, variable latency, encoding parameters instead of passing pointers, and cross-language type translation. Parameter count isn't an issue.
Q14 — b. The simplifying assumption for services (unlike databases, where any version may read any value): servers first, clients second. Cross-organization APIs weaken it — you can't force clients to upgrade, so compatibility must hold long-term and versions pile up.
