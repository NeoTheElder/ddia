Stream Processing

A complex system that works is invariably found to have evolved from a simple system that works. The inverse proposition also appears to be true: A complex system designed from scratch never works and cannot be made to work. — John Gall, Systemantics (1975)

Chapter 10←10 rested on one assumption: the input is bounded. A batch job knows when it has read everything, and that knowledge is load-bearing — MapReduce's central sort cannot emit its first output line until it has seen its last input line, because the last record might have the smallest key. Real data isn't like that. Users produced data yesterday and today and will produce more tomorrow; the dataset is never "complete." Batch processing copes by chopping the unbounded into artificial fixed-size chunks — a day's worth, an hour's worth — at the cost of results that lag the world by a day or an hour. Shrink the chunk to a second, then abandon chunks entirely and process each event as it happens, and you have stream processing.

A "stream" is data made incrementally available over time — Unix stdin/stdout, lazy lists, FileInputStream, TCP connections, audio and video over the internet. This chapter treats event streams as a data-management mechanism: the unbounded, incrementally processed counterpart to batch data. It runs in three movements. How are streams represented, stored, and transmitted (messaging systems, partitioned logs)? What is the relationship between streams and databases (change data capture, event sourcing, the log as the truth)? And what can you do with a stream once you have it (windows, joins, fault tolerance)?

FEYNMAN · the whole chapter in one idea Replace the batch job's input file with an append-only log that never ends, and everything in Chapter 10 comes back, one event at a time. A file is a sequence of records you read from the start; a log is the same sequence with the end still being written. Producers append; consumers read sequentially and remember how far they got (an offset) — the very mechanism a replication follower uses to trail its leader. Once you see that, two things fall out. First, a database's own changelog is a stream, so every other system — cache, search index, warehouse — can be a follower of the database instead of a second write target that drifts (change data capture). Second, the mutable table you query is just a cache of the latest value per key in that log: state is the integral of the stream; the stream is the derivative of the state. The hard parts are the ones batch never had: the input arrives out of order and late, so when did the event happen and when do you know a window is complete become real questions; and the job runs for years, so you can't retry it from the beginning — you checkpoint, or you make your writes idempotent. Colors as always: ember = writes / appends / output, cyan = reads / consumers.
transmitting-event-streams

Transmitting Event Streams

In batch, a job's inputs and outputs are files. Parsing a file yields records; in streaming the record is called an event, but it is the same thing — a small, self-contained, immutable object describing something that happened at some point in time, usually carrying a timestamp from a time-of-day clock (Chapter 8←8). A page view, a purchase, a temperature reading, a CPU metric, one line of a web-server log. Encoded as text, JSON, or a binary format (Chapter 4←4), an event can be appended to a file, inserted into a table, or sent over the network. Where a file is written once and read by many jobs, an event is generated once by a producer (publisher, sender) and processed by any number of consumers (subscribers, recipients); where a filename groups related records, a topic or stream groups related events.

In principle a plain file or database connects producers to consumers: the producer writes, each consumer periodically polls for events since its last run — which is exactly what a daily batch job does. But as the delay you want shrinks, polling becomes expensive: the more often you poll, the smaller the fraction of polls that find anything. Consumers should be notified. Relational databases have triggers, but they are limited and an afterthought in database design, so specialized tools grew up for delivering event notifications.

Messaging Systems

messaging-systems

A messaging system pushes a producer's message to consumers (first met in Chapter 4←4). A Unix pipe or TCP connection is the degenerate case — one sender, one recipient — and most systems generalize it: many producers into one topic, many consumers out of it, the publish/subscribe model. Systems differ enormously within that model, and two questions cut the space cleanly:

  1. What if producers outrun consumers? Three options: drop messages, buffer them in a queue, or apply backpressure (flow control — block the producer). Unix pipes and TCP use backpressure: a small fixed buffer, and the sender blocks when it fills (Chapter 8←8). If the system buffers, what happens as the queue grows — crash when it outgrows memory, or spill to disk, and how does that disk access affect performance?
  2. What if nodes crash or go offline — are messages lost? Durability costs disk writes and/or replication. If you can afford to lose the occasional message you get higher throughput and lower latency on the same hardware. Periodic sensor readings can tolerate a missing point (the next one supersedes it, though mass loss may go unnoticed); event counters cannot — every lost message is a wrong count.

Batch systems gave a strong guarantee for free: failed tasks retry, partial output is discarded, and the result is as if nothing failed. The end of this chapter asks how a stream can offer the same.

Direct messaging from producers to consumers

Some systems skip intermediaries. UDP multicast carries stock-market feeds where latency rules; UDP is unreliable, so application protocols retransmit on request (the producer must remember what it sent). Brokerless libraries — ZeroMQ, nanomsg — do pub/sub over TCP or IP multicast. StatsD and Brubeck collect metrics over unreliable UDP, which makes counters approximate at best. Webhooks register a callback URL so one service makes an HTTP/RPC request to another whenever an event occurs (Chapter 4←4). All of these work in their niche, but the application must be aware that messages can be lost; they assume producers and consumers are constantly online. An offline consumer misses what was sent meanwhile, and a producer that retries may itself crash and lose the buffer it was retrying.

Message brokers

The widely used alternative routes messages through a message broker (message queue): a server — essentially a database optimized for message streams — to which producers and consumers connect as clients. Centralizing the data lets clients come, go, and crash; durability becomes the broker's problem (some keep messages only in memory, others write to disk). Faced with slow consumers, brokers generally choose unbounded queueing over dropping or backpressure. A consequence: consumers are asynchronous. A producer waits only for the broker to confirm it has buffered the message, not for any consumer to process it; delivery happens at some later point — usually within a fraction of a second, sometimes much later if there is a backlog.

Message brokers compared to databases

Some brokers can even join two-phase commit via XA/JTA (Chapter 9←9), which makes them look database-like. The practical differences still matter. Databases keep data until it is explicitly deleted; brokers delete a message once it is delivered, so they are not long-term storage. Brokers assume a small working set — short queues — and slow down when a backlog spills to disk. Databases offer secondary indexes and rich search; brokers offer subscription to topics matching a pattern — different mechanisms, both ways for a client to select the slice of data it cares about. And a database query returns a point-in-time snapshot that goes silently stale, whereas a broker can't answer arbitrary queries but does notify clients when new data arrives. This is the traditional broker, codified in JMS and AMQP and implemented by RabbitMQ, ActiveMQ, HornetQ, Qpid, TIBCO EMS, IBM MQ, Azure Service Bus, and Google Cloud Pub/Sub.

Multiple consumers

When several consumers read the same topic, two patterns appear (Figure 11-1 in the book), and they compose: two consumer groups may each subscribe so that each group sees every message, while within a group each message goes to one node.

Acknowledgments and redelivery

Consumers crash. A broker might deliver a message that is never processed, or only half processed. To avoid losing it, brokers use acknowledgments: the client must explicitly tell the broker it has finished with a message before the broker removes it from the queue. If the connection closes or times out without an ack, the broker assumes the message was not processed and redelivers it to another consumer. (It may in fact have been fully processed and only the ack lost — handling that case properly needs an atomic commit protocol, Chapter 9←9.) Partitioned Logs

partitioned-logs

Sending a packet or making a request is transient: it leaves no permanent trace. Even brokers that durably write messages to disk delete them once delivered, because they are built around a transient-messaging mindset. Databases and filesystems take the opposite stance — what is written stays until someone explicitly deletes it. The difference matters for derived data. A batch process can be rerun repeatedly, experimenting freely, because its input is read-only; AMQP/JMS consumption is destructive — acknowledging deletes — so you cannot rerun a consumer and expect the same result, and a consumer added today sees only messages sent from now on; the past is gone. Why not a hybrid: the durable storage of a database with the low-latency notification of messaging? That is the log-based message broker.

Using logs for message storage

A log is an append-only sequence of records on disk — the same structure as the log-structured storage engines and write-ahead logs of Chapter 3←3 and the replication logs of Chapter 5←5. Used as a broker: a producer appends a message to the end; a consumer reads the log sequentially and, at the end, waits for a notification of a new append — tail -f. To exceed a single disk's throughput the log is partitioned (Chapter 6←6): each partition is an independent log on its own machine, and a topic is a group of partitions carrying the same kind of message. Within a partition the broker assigns each message a monotonically increasing offset; because a partition is append-only, its messages are totally ordered. There is no ordering guarantee across partitions. Apache Kafka, Amazon Kinesis Streams, and Twitter's DistributedLog work this way (Google Cloud Pub/Sub is architecturally similar but exposes a JMS-style API); despite writing everything to disk they reach millions of messages per second by partitioning across machines, and tolerate faults by replicating messages.

Logs compared to traditional messaging

Fan-out is trivial in a log — reading doesn't delete, so consumers don't affect each other. Load balancing assigns partitions rather than messages, which has the downsides shown above: parallelism capped by partition count, and head-of-line blocking within a partition. (You could have two consumers split a partition by even/odd offsets, or spread a partition over a thread pool, but that complicates offset management; more partitions is the sane way to add parallelism.) So the choice is a real one. JMS/AMQP-style brokers win when messages are expensive to process, you want message-by-message parallelism, and ordering doesn't matter much — an asynchronous RPC, a task queue. Log-based brokers win with high throughput, cheap per-message processing, and ordering that matters.

Consumer offsets

Sequential consumption makes progress trivial to describe: everything below the offset is processed, everything above is unseen. The broker need not track acks per message, only periodically record offsets — less bookkeeping, and room for batching and pipelining, which is where log-based systems' throughput comes from. The offset is the log sequence number of single-leader replication (Chapter 5←5): the broker behaves like a leader, the consumer like a follower. If a consumer fails, another node in the group takes its partitions and starts from the last recorded offset — reprocessing whatever the dead consumer had handled but not yet recorded. Dealing with that is deferred to the fault-tolerance section.

Disk space usage

Append forever and you run out of disk, so the log is divided into segments and old segments are deleted or archived. A consumer so slow that its offset points into a deleted segment misses messages: the log is a bounded circular buffer — but a very large one, because it lives on disk. Back of the envelope (2017 numbers): a 6 TB drive at 150 MB/s sequential write fills in about 11 hours, so even at maximum write rate the disk buffers 11 hours of messages, and the ratio holds however many disks and machines you add. Real deployments rarely saturate write bandwidth, so retention of days or weeks is normal. Throughput stays roughly constant regardless of retention, since every message is written to disk anyway — unlike memory-first brokers, which are fast while queues are short and slow down sharply when they start spilling.

When consumers cannot keep up

In the drop/buffer/backpressure taxonomy, the log is buffering with a large fixed-size buffer. A consumer that falls behind retention effectively has old messages dropped — but you can monitor how far each consumer lags the head of the log and alert well before that, and the buffer is large enough that a human can fix the slow consumer in time. Crucially, a lagging consumer hurts only itself: it doesn't disrupt other consumers, which makes it safe to experimentally consume a production log for development or debugging. When it shuts down it consumes no resources — only its offset remains. Traditional brokers, by contrast, need you to remember to delete the queues of dead consumers, or they keep accumulating messages and stealing memory from live ones.

Replaying old messages

In AMQP/JMS, processing-and-acknowledging is destructive. In a log, consuming is like reading a file: read-only, no change to the log, the only side effect being the consumer's own offset — which the consumer controls. Start a copy of a consumer at yesterday's offset with output to a different location and you have reprocessed a day; vary the code and repeat as many times as you want. This is what makes log-based messaging resemble batch processing: derived data cleanly separated from input by a repeatable transformation, so experimentation is cheap and recovery from bugs is easy — "a good tool for integrating dataflows within an organization" (Kreps, "The Log").

FEYNMAN · a queue is a conveyor belt; a log is a bookshelf A traditional broker is a conveyor belt: items ride toward whichever worker is free, and once a worker takes one it's gone from the belt. Great for sharing out expensive, unrelated jobs; terrible if you later want to know what went past, or if item 3 must be handled before item 4 and a worker drops one. A log is a bookshelf that only ever grows on the right. Readers don't take books off — each keeps a bookmark (the offset) and reads left to right. Any number of readers can browse the same shelf without interfering; a new reader can start at the far left and catch up on everything; a reader who loses their bookmark just reopens at the last page they wrote down (rereading a few pages — the duplicate). To handle more readers you build more shelves (partitions) and give each reader whole shelves, so books on one shelf are always read in order. The one thing the bookshelf can't do is fan out a single shelf's books to many readers in parallel — that's the belt's job.

databases-and-streams

Databases and Streams

Log-based brokers took ideas from databases and applied them to messaging. Now run it in reverse. An event is a record of something that happened — a user typing a search, a sensor reading — and a write to a database is also something that happened. It can be captured, stored, and processed. The connection runs deeper than logs on disk: a replication log is a stream of database write events, produced by the leader as it commits transactions and applied by followers to arrive at the same data (Chapter 5←5). State machine replication (Chapter 9←9) says: if every event is a write and every replica processes the same events in the same order, the replicas end in the same state. That is just another event stream. This section starts from a problem in heterogeneous systems and solves it with streams.

Keeping Systems in Sync

keeping-systems-in-sync

No single system satisfies every storage, query, and processing need, so real applications combine several: an OLTP database serving users, a cache for hot requests, a full-text index for search, a data warehouse for analytics — each holding its own copy of the data in its own optimized representation. Those copies must stay in sync. Warehouses get it by ETL (Chapter 3←3) — a full dump, transformed and bulk-loaded, i.e. a batch process — and search indexes and recommenders were built the same way in Chapter 10←10. When periodic full dumps are too slow, the tempting alternative is dual writes: the application writes to each system itself — database, then search index, then cache invalidation. It has two serious problems.

Change Data Capture

change-data-capture

The obstacle: a database's replication log has long been treated as an internal implementation detail, not a public API. Clients were supposed to go through the data model and query language, and for decades most databases had no documented way to get the log of changes — so replicating those changes into a search index, cache, or warehouse was hard. Change data capture (CDC) is the process of observing all data changes written to a database and extracting them in a form that can be replicated elsewhere — most interesting when the changes come out as a stream, immediately as they are written. Capture the changes, apply them in the same order to a search index, and the index matches the database. The index and every other derived system become consumers of the change stream.

Implementing change data capture

The log consumers are derived data systems: the search index and warehouse are just other views onto the system of record, and CDC guarantees that every change to the record reaches them. Two implementation routes. Database triggers that observe every table and append to a changelog table (trigger-based replication, Chapter 5←5) — fragile, with significant overhead. Parsing the replication log — more robust, though schema changes are a challenge. LinkedIn's Databus, Facebook's Wormhole, and Yahoo!'s Sherpa did this at scale; Bottled Water decodes PostgreSQL's WAL, Maxwell and Debezium parse MySQL's binlog, Mongoriver reads MongoDB's oplog, GoldenGate does it for Oracle. Like brokers, CDC is usually asynchronous: the system of record commits without waiting for consumers. Operationally that is a feature — a slow consumer doesn't hurt the source — but it means every replication-lag issue applies (Chapter 5←5).

Initial snapshot

With the log of all changes ever made you could rebuild the database by replay, but keeping everything forever is usually too much disk and too slow to replay, so the log gets truncated. Building a new full-text index needs a full copy — recent changes alone miss items that weren't recently touched. So without full history you start from a consistent snapshot that corresponds to a known offset in the change log (Chapter 5←5), so you know where to resume applying changes once the snapshot is loaded. Some CDC tools integrate the snapshot; others leave it manual.

Log compaction

If you can keep only limited history you must snapshot every time you add a derived system. Log compaction is the alternative, borrowed from log-structured storage engines (Chapter 3←3): in the background, look for records with the same key, discard duplicates, keep only the most recent update per key; a tombstone (null value) marks a deletion and is removed by compaction. The compacted log's size depends only on the database's current contents, not on how many writes ever happened. The same works for a CDC topic if every change carries a primary key and every update replaces the previous value for that key. Then rebuilding any derived system means: start a consumer at offset 0 of the compacted topic and scan — the log is guaranteed to hold the latest value of every key (plus maybe some older ones), so you get a full copy without ever snapshotting the source again. Kafka supports this, and it is what lets a broker be durable storage, not just transient messaging.

API support for change streams

Increasingly databases expose change streams as a first-class interface rather than a reverse-engineered afterthought: RethinkDB lets queries subscribe to notifications when their results change; Firebase and CouchDB build synchronization on a change feed also exposed to applications; Meteor uses MongoDB's oplog to push data changes into the UI; VoltDB lets transactions continuously export data as a stream — modeled as a relational table that transactions insert into but nobody can query, whose committed tuples form the stream in commit order. Kafka Connect integrates CDC tools for many databases with Kafka; once changes are in Kafka they can update derived systems and feed stream processors.

2ND EDITION · "CDC is having a moment": Debezium, DBLog, and the outbox pattern CDC went from a niche of reverse-engineered binlog parsers to mainstream infrastructure, and the 2nd edition treats it that way. Debezium (mentioned in 2017 at version 0.2) is now the default open-source CDC platform across PostgreSQL, MySQL, MongoDB, SQL Server, and Oracle, riding on Kafka Connect. Event Sourcing

event-sourcing

Event sourcing, from the domain-driven design community, also stores all changes to application state as a log of change events — but at a different level of abstraction. In CDC the application uses the database mutably, updating and deleting at will; the change log is extracted underneath it (by parsing the replication log), which guarantees the extracted order matches the real write order (avoiding the dual-write race), and the application need not know CDC is happening. In event sourcing the application logic is explicitly built on immutable events written to an append-only event store; updates and deletes are discouraged or prohibited, and events describe what happened at the application level rather than low-level state changes. "Student cancelled their course enrollment" expresses one action in a neutral way; "one row deleted from enrollments, one row added to student_feedback" bakes in assumptions about how the data will be used. When a new feature arrives — "offer the place to the next person on the waiting list" — the new side effect chains off the existing event. Event sourcing makes applications easier to evolve, easier to debug after the fact (you can see why something happened), and more robust to application bugs. It resembles the chronicle data model, and an event log resembles a star schema's fact table (Chapter 3←3). Specialized stores exist (Event Store), but any database or log-based broker will do.

Deriving current state from the event log

Users want the current state, not the history: the contents of the cart, not every change ever made to it. So an event-sourced application transforms the log (the data as written) into state suitable for display (the data as read) with arbitrary but deterministic logic, so the same state can be re-derived by replaying. Replay works as it does for CDC, but compaction does not. A CDC event carries the whole new record, so the latest event per key determines the current value and older events can be discarded. An event-sourced event expresses intent — later events don't override earlier ones — so you need the full history to reconstruct state, and log compaction isn't possible in the same way. Event-sourced systems therefore store snapshots of derived state so they need not replay from the beginning every time — purely a performance optimization for reads and crash recovery; the intent is still to keep every raw event forever and be able to reprocess the whole log whenever required.

Commands and events

The philosophy separates commands from events. A user's request arrives as a command, which may still fail — an integrity condition might be violated — so the application first validates it. If accepted, it becomes an event: durable and immutable. Registering a username or reserving a seat (Chapter 9←9) needs a check that it isn't already taken; once the check passes, the application emits "username X registered by user Y" or "seat S reserved for customer C." At that moment it is a fact: even if the customer later cancels, it remains true that they once held the reservation — the cancellation is a separate later event. Consumers of the stream may not reject an event: by the time they see it, it is an immutable part of the log that others may already have seen. So validation must happen synchronously before the event exists — for example a serializable transaction that validates the command and publishes the event atomically. Or split the request into two events: a tentative reservation, then a separate confirmation once validated (the total-order-broadcast trick of Chapter 9←9), which lets validation run asynchronously.

FEYNMAN · CDC is a court stenographer; event sourcing is a diary Both produce a written record of everything that happened, and both let you reconstruct "where things stand." The stenographer (CDC) sits underneath a proceeding that goes on as it always has — the application updates rows and deletes them, oblivious — and transcribes every change verbatim, in the order it actually occurred. Because each line is the full new value ("row 42 now reads …"), the latest line about any row is all you ever need, so old lines can be shredded (compaction). The diarist (event sourcing) writes deliberately, in their own words, about what they did and meant: "cancelled my enrollment." That is richer — you can later derive things the stenographer's transcript can't tell you (why?) and reinterpret old entries for new purposes — but no entry replaces an earlier one, so you can never shred; you can only keep a bookmark summary (snapshot) so you don't reread from page one. And a diarist writes a decision only after making it: the doubt ("should I?") is a command; the ink is an event.

State, Streams, and Immutability

state-streams-and-immutability

Batch processing drew its power from immutable input files. The same principle powers event sourcing and CDC. But databases store current state, optimized for reads — and the nature of state is that it changes, so databases update and delete. How does that fit with immutability? Whenever state changes, it is the result of the events that mutated it: available seats are the result of processed reservations, an account balance the result of its credits and debits, a response-time graph the aggregate of individual requests. However state changes, some sequence of events caused it — and even as things are done and undone, the fact that the events occurred remains true. Mutable state and an append-only log of immutable events are two sides of the same coin. The log of all changes — the changelog — is the evolution of state over time.

Advantages of immutable events

Immutability is an old idea. Accountants have kept append-only ledgers for centuries: every transaction is a log entry describing money, goods, or services changing hands; the accounts — profit and loss, balance sheet — are derived by adding them up. A mistake is never erased; a compensating transaction is added (a refund), the wrong entry stays forever for auditing, and already-published figures get a correction in the next period. That auditability matters outside finance too. If buggy code writes bad data, recovery is far harder when the code could destructively overwrite (Chapter 10←10); with an append-only log you can diagnose and recover. And immutable events hold more information than the state: a customer adds an item to the cart, then removes it — for fulfillment the events cancel, but for analytics "considered it, then decided against it" is valuable, and a database that deletes on removal has lost it.

Deriving several views from the same event log

Separating the immutable log from mutable state lets you derive several read-oriented representations from one log — exactly the multiple-consumers pattern of the CDC figure. Druid ingests directly from Kafka; Pistachio uses Kafka as its commit log; Kafka Connect sinks export to many databases and indexes. An explicit translation step from log to database makes evolution easy: to present existing data in a new way, build a new read-optimized view from the log and run it alongside the old one, no migration of the existing system required; shut the old one down when nobody needs it. Storing data is straightforward when you don't have to worry about how it will be queried — most of the complexity of schema design, indexing, and storage engines comes from supporting particular access patterns (Chapter 3←3). So separating the write form from the read form, with several read views, buys enormous flexibility — command query responsibility segregation (CQRS). The traditional assumption that data must be written in the form it will be queried is a fallacy; normalization-versus-denormalization debates (Chapter 2←2) mostly dissolve when a translation process keeps denormalized read views consistent with the log. Twitter's home timelines (Chapter 1←1) are read-optimized state of exactly this kind: massively denormalized, kept consistent by the fan-out service.

Concurrency control

The biggest downside of event sourcing and CDC: consumers are usually asynchronous, so a user may write to the log and then read a derived view that doesn't yet reflect it — the read-your-own-writes problem (Chapter 5←5). You can update the read view synchronously with the append, but that needs a transaction spanning both — so log and view in one storage system, or a distributed transaction — or the total-order-broadcast approach. On the other hand, deriving state from a log simplifies concurrency control. Much of the need for multi-object transactions (Chapter 7←7) comes from one user action changing data in several places; an event can be a self-contained description of the action, so the action is one write — an append — which is easy to make atomic. And if log and state are partitioned alike (a customer's event in partition 3 touches only partition 3 of the state), a single-threaded log consumer needs no write concurrency control at all: it processes one event at a time, like actual serial execution (Chapter 7←7). The log removes nondeterminism by fixing a serial order per partition. Events touching several partitions need more work — Chapter 12→12.

Limitations of immutability

Many non-event-sourced systems already lean on immutability: MVCC snapshots inside databases (Chapter 7←7), and Git, Mercurial, and Fossil for version history. Can you keep an immutable history of everything forever? It depends on churn. Mostly-append workloads are easy. High rates of update and delete on a small dataset make the history grow prohibitively, cause fragmentation, and make compaction and garbage-collection performance critical to operational health. And sometimes data must be deleted, immutability notwithstanding: privacy regulation after an account closes, data-protection law for erroneous information, containing an accidental leak. Appending "consider this deleted" isn't enough; you need to rewrite history and pretend the data was never written — Datomic calls it excision, Fossil shunning. Truly deleting is surprisingly hard: copies live in storage engines, filesystems, and SSDs that write to new locations rather than overwriting, and in deliberately immutable backups. Deletion is more "making it harder to retrieve" than "making it impossible" — but sometimes you have to try (Chapter 12→12).

2ND EDITION · crypto-shredding, and the log-as-truth idea becoming a product category Two threads from this section grew up. GDPR-era deletion in immutable systems now has a standard technique: crypto-shredding — encrypt each user's data under a per-user key and, on a deletion request, destroy the key, so every copy in every log, backup, and SSD becomes unreadable at once; excision in Datomic-style systems is the other pattern. Processing Streams

Where streams come from (user activity, sensors, database writes) and how they travel (direct messaging, brokers, logs) are settled. What can you do with one? Three things. Write it to storage — a database, cache, or search index — for others to query: the streaming equivalent of a batch job's output (Chapter 10←10), and the CDC picture above. Push it to people — emails, push notifications, a live dashboard; a human is the final consumer. Or process one or more input streams into one or more output streams, possibly through a pipeline of stages before ending in option 1 or 2. The rest of the chapter is option 3. The code that does it is an operator or job, a close relative of a Unix process or MapReduce job: it consumes inputs read-only and appends output somewhere else. Partitioning and parallelization patterns carry over from MapReduce and dataflow engines; so do basic map operations (transform, filter). The one crucial difference: a stream never ends. Sorting an unbounded input is meaningless, so sort-merge joins (Chapter 10←10) are out. And fault tolerance must change: a failed batch task that ran for minutes simply restarts from the beginning; a stream job that has run for years cannot.

Uses of Stream Processing

uses-of-stream-processing

Stream processing began as monitoring: fraud detection watching a card's usage pattern change; trading systems executing rules on price ticks; factory systems spotting a malfunctioning machine; military and intelligence systems watching for signs of attack. These need sophisticated pattern matching and correlation. Other uses emerged, and they differ in what they keep and for how long.

Complex event processing

CEP (1990s) searches an event stream for patterns of events, the way a regular expression searches a string for patterns of characters. Rules are written in a high-level declarative language (often SQL-like) or a GUI and submitted to an engine that consumes the inputs, maintains an internal state machine doing the matching, and emits a complex event when a pattern completes. The relationship between queries and data is reversed: a normal database stores data persistently and treats queries as transient; a CEP engine stores queries long-term and lets events flow past them looking for a match. Esper, IBM InfoSphere Streams, Apama, TIBCO StreamBase, SQLstream; Samza and others gained streaming SQL.

Stream analytics

Blurry boundary with CEP, but analytics cares less about specific sequences and more about aggregates and statistics over many events: the rate of some event; a rolling average; comparing now to the same interval last week to detect trends or anomalies. Statistics are computed over fixed intervals — average QPS and p99 over the last 5 minutes — which smooths second-to-second noise while staying timely. That interval is a window. Analytics often uses probabilistic algorithms — Bloom filters for set membership (Chapter 3←3), HyperLogLog for cardinality, percentile estimators (Chapter 1←1) — because they use far less memory. That leads some to believe stream processing is inherently lossy and approximate. It isn't: approximation is merely an optimization. Frameworks built with analytics in mind: Storm, Spark Streaming, Flink, Concord, Samza, Kafka Streams; hosted, Google Cloud Dataflow and Azure Stream Analytics.

Maintaining materialized views

Keeping caches, indexes, and warehouses in sync with a source database via its change stream is a special case of materialized view maintenance (Chapter 3←3): an alternative view over a dataset, updated whenever the data changes. Event-sourced application state is a materialized view too. Unlike analytics, a window isn't enough — the view depends on all events over an arbitrary period (minus what compaction discards): a window stretching back to the beginning of time. That runs against the assumptions of analytics-oriented frameworks built for bounded windows; Samza and Kafka Streams support it, building on Kafka's log compaction.

Search on streams

Besides multi-event patterns there is a need to search for individual events by complex criteria — full-text queries. Media monitoring matches a stream of news items against standing queries about companies or topics; real-estate sites notify users when a new listing matches their saved search. Elasticsearch's percolator does this. Again processing is turned on its head: conventional search indexes documents and runs queries over the index; stream search stores the queries and runs documents past them. Naively test every document against every query; with many queries, index the queries too, to narrow which could match.

Message passing and RPC

Message-passing systems as an alternative to RPC — the actor model (Chapter 4←4) — also move messages, but aren't usually thought of as stream processing. Actor frameworks manage concurrency and distributed execution of communicating modules; stream processing is a data-management technique. Actor communication is often ephemeral and one-to-one; event logs are durable and multi-subscriber. Actors communicate arbitrarily, including cyclic request/response; stream processors form acyclic pipelines where every stream is the output of one job derived from well-defined inputs. There is crossover — Storm's distributed RPC farms user queries out to nodes that also process event streams, interleaving them and aggregating the results (see Chapter 12→12) — and you can process streams with actors, but many actor frameworks don't guarantee delivery across crashes, so it isn't fault-tolerant without extra retry logic.

Reasoning About Time

reasoning-about-time

"The average over the last five minutes" sounds unambiguous. It isn't. A batch job crunching a year of history in minutes obviously uses the timestamp in each event, never the machine's clock — the processing run has nothing to do with when things happened — and doing so makes the job deterministic: rerun it and get the same answer. Many stream frameworks instead use the processing time — the local clock of the processing machine — to define windows. Simple, and fine if the lag between an event happening and being processed is negligible. It breaks as soon as there is significant delay.

Event time versus processing time

Processing can be delayed by queueing, network faults (Chapter 8←8), contention in the broker or processor, a consumer restart, or deliberate reprocessing of old events after a bug fix. Delays also reorder: a user's first request is handled by server A, the second by server B, and B's event reaches the broker before A's — the processor sees them backwards. The Star Wars analogy: Episodes IV, V, VI were released in 1977–83, then I, II, III in 1999–2005, then VII in 2015. Watch them in release order and your processing order disagrees with the narrative order — the episode number is the event timestamp, the viewing date is the processing time. Humans cope; algorithms must be written to. Confusing the two produces bad data:

Knowing when you're ready

Event-time windows have a tricky property: you never know whether all events for a window have arrived or some are still coming. Counting requests per minute, you've seen events for minute 37 and now most arrivals fall in minutes 38 and 39 — when do you declare minute 37 finished and emit its count? You can time out after seeing no new events for a while, but some could still be buffered on a machine somewhere behind a network interruption. These late arrivals are stragglers, and there are two ways to handle them: ignore them (normally a small fraction; track the dropped count as a metric and alert if it grows), or publish a correction — an updated value for the window, possibly retracting the earlier output. Some systems use a special message saying "from now on there will be no more messages with timestamp earlier than t" to trigger windows; with several producers each having its own minimum-timestamp threshold, the consumer must track them individually, and adding or removing producers gets trickier.

Whose clock are you using, anyway?

Timestamps get harder when events are buffered at several points. A mobile app reporting usage metrics is used offline, buffers events on the device, and uploads them hours or days later — extreme stragglers to any consumer. The meaningful timestamp is when the interaction occurred by the device's clock — but user-controlled clocks can't be trusted; they may be wrong by accident or design (Chapter 8←8). The server's receipt time is trustworthy but meaningless as a description of the interaction. The fix is to log three timestamps: when the event occurred (device clock), when it was sent to the server (device clock), and when the server received it (server clock). Received minus sent estimates the device's clock offset (assuming network delay is negligible relative to the accuracy you need); apply that offset to the occurrence time to estimate when the event truly happened (assuming the device offset didn't drift between occurrence and sending). None of this is unique to streams — batch has exactly the same problem; streaming just makes the passage of time harder to ignore.

Types of windows

Once each event's timestamp is settled, decide how windows are defined; the window is then the unit of aggregation (count, average). Four are common. A tumbling window has a fixed length and every event belongs to exactly one: with 1-minute tumbling windows, 10:03:00–10:03:59 is one window, 10:04:00–10:04:59 the next — round each timestamp down to the minute. A hopping window also has a fixed length but overlaps for smoothing: a 5-minute window hopping by 1 minute covers 10:03:00–10:07:59, then 10:04:00–10:08:59 — compute 1-minute tumbling windows and aggregate adjacent ones. A sliding window contains all events within some interval of each other: a 5-minute sliding window groups 10:03:39 and 10:08:12 because they're less than 5 minutes apart, which no fixed-boundary window would — implement with a time-sorted buffer, evicting expired events. A session window has no fixed duration: it groups a user's events that occur close together and ends after inactivity (say 30 minutes) — sessionization, a staple of web analytics (compare the batch version in Chapter 10←10).

Stream Joins

stream-joins

Batch pipelines join datasets by key (Chapter 10←10); stream processing generalizes pipelines to unbounded data, so it needs joins too — harder, because new events can appear on any stream at any time. Three kinds: stream-stream, stream-table, and table-table.

Stream-stream join (window join)

Your site has search; you want click-through rates per URL. Each search logs an event with the query and results; each click on a result logs another. Both carry the session ID, and the CTR needs them joined. The click may never come (the user gave up), and the gap between search and click ranges from seconds to weeks (a forgotten tab), and thanks to network delay the click event may even arrive before the search event. So you choose a join window — say, match a click to a search if they're at most an hour apart. Note that embedding the search details in the click event is not a join: it tells you only about searches that were clicked, nothing about the ones that weren't, and search quality needs both. The processor must maintain state: all events of the last hour, indexed by session ID, on both sides.

Stream-table join (stream enrichment)

The batch job of Chapter 10←10 joined activity events to a user-profile database. Treat the activity events as a stream and do the same continuously: input is events with a user ID, output is events enriched with profile fields. Per event, look up the user ID and attach the profile. Querying a remote database per event is slow and risks overloading it; instead load a copy of the database into the processor and query locally — the hash join of Chapter 10←10, in memory or on local disk. The difference from batch: a batch job uses a point-in-time snapshot, but a stream processor runs forever while the database changes, so the local copy must be kept current — by change data capture. The processor subscribes to the profile table's changelog as well as the activity stream, and updates its copy as profiles change. So a stream-table join is really a join of two streams — activity and profile updates — where the table side's window reaches back to the beginning of time (newer versions overwrite older) and the stream side may keep no window at all.

Table-table join (materialized view maintenance)

Twitter's home timeline (Chapter 1←1): merging every followee's recent tweets at read time is too slow, so maintain a per-user timeline cache — an inbox tweets are written into as they're sent. Keeping it requires: when u tweets, add it to every follower's timeline; when a tweet is deleted, remove it from all timelines; when u₁ follows u₂, add u₂'s recent tweets to u₁'s timeline; when u₁ unfollows, remove them. The processor needs streams of tweet events (send, delete) and follow events (follow, unfollow), and must maintain a database of each user's followers to know which timelines to touch. Another way to see it: the processor maintains a materialized view of a query joining two tables —

SELECT follows.follower_id AS timeline_id,
       array_agg(tweets.* ORDER BY tweets.timestamp DESC)
FROM tweets
JOIN follows ON follows.followee_id = tweets.sender_id
GROUP BY follows.follower_id

The join of the two streams corresponds directly to the join of the two tables; the timelines are a cache of the query result, updated whenever either table changes. (Footnote worth savoring: if a stream is a table's derivative and a join is a product u·v, the change stream of the joined view follows the product rule (u·v)′ = u′v + uv′ — any change in tweets joined with the current followers, plus any change in followers joined with the current tweets.)

Time-dependence of joins

All three joins maintain state from one input (search and click events, profiles, follower sets) and query it on messages from the other. The order of the state-maintaining events matters (follow-then-unfollow ≠ unfollow-then-follow); within a partition order is preserved, but across streams or partitions there is typically no guarantee. So when events on different streams happen at about the same time, which is processed first? If a user updates their profile, which activity events join with the old profile and which with the new? Put generally: if state changes over time and you join against it, which point in time do you use? Tax rates change; when joining sales to a rates table you want the rate at the time of sale, not today's — especially when reprocessing history. If cross-stream order is undetermined the join is nondeterministic: rerun the job on the same input and the interleaving — and the result — may differ. Data warehouses call this a slowly changing dimension (SCD) and solve it with a unique identifier per version of the joined record — each new tax rate gets a new ID, and the invoice records which one applied. The join becomes deterministic, at a cost: every version must be retained, so log compaction is off the table.

Fault Tolerance

fault-tolerance

Batch got fault tolerance cheaply: a failed MapReduce task restarts elsewhere and its output is discarded, safe because inputs are immutable, each task writes its own HDFS file, and output becomes visible only on success. The result is as if nothing had failed — every input record appears to have been processed exactly once, even though retries mean some records really were processed more than once. The book prefers the term effectively-once. Streams face the same problem with one option removed: you can't wait until the task finishes to make its output visible, because the stream never finishes.

Microbatching and checkpointing

Break the stream into small blocks and treat each as a miniature batch job — microbatching, used by Spark Streaming with batches of about a second: smaller means more scheduling and coordination overhead, larger means longer delay before results appear. Microbatching also implies a tumbling window equal to the batch size, by processing time; larger windows must carry state across microbatches explicitly. Apache Flink's variant: periodically write rolling checkpoints of operator state to durable storage; on a crash, restart from the latest checkpoint and discard the output produced since. Checkpoints are triggered by barriers injected into the stream — like microbatch boundaries but without forcing a window size. Within the framework, both provide batch-grade exactly-once semantics. But once output leaves the processor — a database write, a message to an external broker, an email — the framework can no longer discard it. Restarting then makes the external side effect happen twice; microbatching and checkpointing alone don't prevent that.

Atomic commit revisited

For exactly-once appearance under faults, all outputs and side effects of processing an event must take effect if and only if processing succeeds: messages to downstream operators or external brokers (including emails and push notifications), database writes, operator state changes, and the acknowledgment of the input — moving the consumer offset forward. All or none, never out of sync. That is exactly-once message processing (Chapter 9←9) — distributed transactions and 2PC, whose traditional XA implementations have well-known problems. In a more restricted environment, though, atomic commit can be efficient: Google Cloud Dataflow and VoltDB do it, and Kafka planned to. Unlike XA, they don't span heterogeneous technologies; they keep state changes and messaging inside the framework, and amortize the protocol's overhead by processing several input messages per transaction.

Idempotence

The other route to discarding partial output safely: idempotence. An idempotent operation has the same effect whether performed once or many times — setting a key to a fixed value is idempotent; incrementing a counter is not. Non-idempotent operations can often be made idempotent with a little metadata: when consuming from Kafka, every message has a persistent, monotonically increasing offset; store the offset of the message that caused the last write alongside the value in the external database, and on retry you can see that an update was already applied and skip it (Storm's Trident uses the same idea). Idempotence rests on assumptions: restarting a failed task must replay the same messages in the same order (a log-based broker does that), processing must be deterministic, and no other node may concurrently update the same value. Failing over between nodes may require fencing (Chapter 8←8) so a node wrongly presumed dead can't interfere. With those caveats, idempotent writes deliver exactly-once semantics at small cost.

Rebuilding state after a failure

Any stateful stream process — windowed aggregations (counters, averages, histograms), join tables and indexes — must recover that state after a failure. Keep it in a remote, replicated datastore? Querying it per message is slow (as with stream-table joins). Keep it local to the processor and replicate it periodically, so a recovering task reads the replica and resumes without loss: Flink snapshots operator state to HDFS; Samza and Kafka Streams send state changes to a dedicated log-compacted Kafka topic — CDC on the processor's own state; VoltDB replicates by redundantly processing every input on several nodes (Chapter 7←7). Sometimes no replication is needed because the state can be rebuilt from the input: a short window's aggregates by replaying that window; a CDC-maintained local table from the compacted change stream. Which trade-off wins depends on the infrastructure — in some systems network latency beats disk latency and network bandwidth rivals disk bandwidth — so there is no universal answer, and the balance between local and remote state shifts as storage and networking evolve.

FEYNMAN · exactly-once is a bookkeeping trick, not a delivery guarantee Nothing can promise a message is delivered exactly once — networks lose acks, and then you must resend and risk a duplicate. What you can promise is that the duplicate has no visible effect. There are exactly two ways to make a duplicate harmless. Make the effect and the acknowledgment one indivisible thing, so a retry that already happened has nothing left to do (atomic commit — cheap when everything lives inside one framework, painful across systems). Or make the effect one that doesn't care about being repeated — "set X to 7" rather than "add 1 to X" — and carry a note of how far you got (the offset), so a repeated write recognizes itself and does nothing (idempotence). Microbatches and checkpoints are the internal version of the first trick; the moment output crosses to a database or an email server, you need one of the two tricks at that boundary too.

Flink's asynchronous barrier snapshots (Carbone et al.) are described as the mature form of the checkpointing above, with two-phase-commit sinks extending the guarantee to external systems that support transactions. Core takeaways

  • Streams are unbounded batch: the same inputs-and-outputs shape as Chapter 10, run continuously on data that never finishes arriving. An event is an immutable record of something that happened, with a timestamp; producers generate, consumers process, topics group. Polling doesn't scale down to low latency — consumers must be notified.
  • Two questions classify messaging systems: what happens when producers outrun consumers (drop / buffer / backpressure — Unix pipes and TCP backpressure), and what is lost when a node crashes (durability costs disk and replication). Direct messaging (UDP multicast, ZeroMQ, StatsD, webhooks) is fast but assumes everyone is online; a broker centralizes durability and lets clients come and go, making consumers asynchronous.
  • AMQP/JMS brokers (RabbitMQ, ActiveMQ, IBM MQ…) assign individual messages, delete on acknowledgment, and assume short queues. Load balancing shares a topic's work; fan-out gives every consumer everything; they compose. Acknowledgment plus redelivery under load balancing reorders messages — harmless for independent messages, not for causally related ones.
  • Log-based brokers (Kafka, Kinesis, DistributedLog) treat the topic as partitioned append-only files with per-partition offsets: total order within a partition, none across. Partitions, not messages, are assigned to consumer-group nodes (parallelism ≤ partitions; head-of-line blocking). Offsets replace acks — the replication log sequence number in disguise: broker = leader, consumer = follower; failover resumes at the last recorded offset and reprocesses a few messages.
  • The log is a large circular buffer on disk (segments age out; hours to weeks of retention; throughput independent of retention). A slow consumer hurts only itself, and reading is non-destructive — so you can replay: rerun yesterday with new code, add a consumer that starts in the past. That is what makes log messaging feel like batch and suits it to integrating dataflows.
  • Databases are streams: a replication log is a stream of write events; state machine replication is stream consumption. Dual writes to keep heterogeneous systems in sync race (no single leader → permanent silent inconsistency) and half-fail. Change data capture makes the database the leader and every other system a follower of its ordered changelog, transported by a log-based broker; implemented by triggers (fragile) or log parsing (Databus, Wormhole, Bottled Water, Maxwell, Debezium, GoldenGate); asynchronous, so replication lag applies; bootstrapped from a snapshot pinned to a log offset — or, with log compaction (latest event per key, tombstones dropped), by scanning the compacted topic from offset 0 with no snapshot at all, which makes the broker durable storage.
  • Event sourcing applies the same idea at the application level: immutable events expressing user intent, written to an append-only store by explicit design (DDD). Richer and more evolvable than CDC's low-level row changes, but later events don't supersede earlier ones, so no compaction — snapshots of derived state instead. Commands may fail validation; once accepted they become events that consumers cannot reject, so validate synchronously (or split into tentative + confirmed events).
  • State and stream are two sides of one coin: state = ∫ stream, stream = d(state)/dt; "the truth is the log, the database is a cache." Immutable events give auditability (the accountant's ledger), recoverability from bad deploys, more information than state (the removed cart item), and many read views from one log (CQRS) — evolve by building a new view beside the old. Costs: asynchronous views break read-your-writes; high-churn histories bloat; and privacy law sometimes demands real deletion (excision, shunning), which immutable systems find genuinely hard.
  • Uses of stream processing: CEP (stored queries, flowing events — the database inside out), stream analytics (windowed aggregates; probabilistic structures as an optimization, not a necessity), materialized-view maintenance (a window back to the beginning of time), search on streams (percolator), and the crossover with actor/RPC systems. Processing options: write to a store, push to humans, or derive new streams via operators in acyclic pipelines.
  • Time is hard: processing time (the machine's clock) is simple but produces artifacts under lag — a redeploy's backlog looks like a spike; event time (the timestamp in the event) is truthful and deterministic but raises "when is the window complete?" Handle stragglers by dropping-and-counting or emitting corrections; untrusted device clocks need three timestamps (occurred, sent, received) to estimate offset. Windows: tumbling, hopping, sliding, session.
  • Stream joins all maintain state from one input and probe it on the other: stream-stream (windowed indexes on both sides; search/click; emits negatives too), stream-table (a CDC-maintained local copy, infinite window — the hash join, kept fresh), table-table (two changelogs; the output is the changing materialized join — Twitter timelines; the product rule). Cross-stream order is undefined, so joins against changing state are nondeterministic unless you version the dimension (SCD), which forbids compaction.
  • Fault tolerance: batch's restart-and-discard doesn't fit a never-ending job. Microbatching (Spark Streaming) and checkpointing with barriers (Flink) give exactly-once — better, effectively-once — inside the framework; once output crosses to a database or an email, you need atomic commit within a restricted environment (Dataflow, VoltDB, Kafka) or idempotent writes tagged with the input offset (given ordered replay, determinism, and fencing). State is rebuilt from local replicas (Flink snapshots, Samza/Kafka Streams changelog topics, VoltDB redundant execution) or from the input itself.
  • 2nd-edition arc (Ch 12): the log model dominates but queues get vocabulary (dead-letter queues, KIP-932 share groups, Postgres-as-queue); CDC "has a moment" (Debezium, DBLog, the outbox pattern); Dataflow-Model terms — watermarks, allowed lateness, triggers — become standard; exactly-once matures (Kafka transactions/KIP-98 verified in TLA+, Flink async snapshots); crypto-shredding answers GDPR deletion; and "the database is a cache of the log" becomes a product category — incremental view maintenance in streaming databases (Materialize, RisingWave, DBSP, differential dataflow).

Q7 — d. Compaction keeps the latest event per key, which is only a complete picture if each event is the full row. Sorting (a) and replication (b) are irrelevant to compaction. (c) is exactly the property that prevents compaction, in event sourcing.
Q8 — a. "Enrollment cancelled" doesn't replace "enrolled"; you need both to know the state. Snapshots are the workaround — a performance optimization only. (b), (c), (d) are not the reason.
Q9 — c. Once in the log, an event is a fact other consumers may already have seen, so it cannot be rejected downstream (a). Immutability doesn't prevent two people wanting the same seat (b). Batch cleanup (d) would leave consumers having acted on an invalid event.
Q10 — b. Multiple views and side-by-side evolution are the CQRS payoff. (a) is the opposite of the truth — asynchronous views break read-your-writes. (c) is backwards: the log holds more than current state. (d) is backwards too: immutability makes deletion hard.
Q11 — d. Figure 11-7 exactly. The real rate was flat; the artifact is caused by measuring against the processor's clock. (a), (b), (c) invent causes that aren't in the scenario.
Q12 — a. The book gives precisely these two: ignore-and-alert, or correct-and-retract. Re-timestamping (b) corrupts event time; blocking (c) is impossible since you never know if more are coming; (d) misattributes the events.
Q13 — c. The book's own example. Tumbling (a) and hopping (b) windows have fixed boundaries — 10:05 splits the pair. A session window (d) is per-user and gap-based, not a fixed 5-minute span.
Q14 — b. Remote lookups (a) are slow and can overload the database; snapshots (c) are the batch approach that a long-running processor can't rely on; (d) is the bug. CDC keeps the local copy current, which is why the book says a stream-table join is really a stream-stream join with an infinite window.
Q15 — d. Versioned dimension records make the join deterministic (the invoice names the rate version that applied). The cost is that no version may be compacted away. (a), (b), (c) don't address which point in time the join uses.
Q16 — a. The framework can roll back what it controls; external side effects are the boundary. Atomic commit (Dataflow, VoltDB, Kafka transactions) or idempotence (offset-tagged writes, Trident) extend the guarantee across it. (b), (c), (d) are false — checkpointing is precisely for stateful operators on unbounded input.
