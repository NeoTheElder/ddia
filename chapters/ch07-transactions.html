Transactions

Some authors have claimed that general two-phase commit is too expensive to support, because of the performance or availability problems that it brings. We believe it is better to have application programmers deal with performance problems due to overuse of transactions as bottlenecks arise, rather than always coding around the lack of transactions. — James Corbett et al., Spanner: Google's Globally-Distributed Database (2012)

Things go wrong. The database process dies mid-write; the application crashes halfway through a sequence of operations; the network drops the connection; two clients overwrite each other; a third client reads something that is only half updated. A reliable system (Chapter 1←1) has to survive all of that, and hand-rolling fault tolerance for every code path is exhausting and error-prone. For forty years the standard shortcut has been the transaction: a way for an application to group several reads and writes into one logical unit that either wholly succeeds (commit) or wholly fails (abort, rollback) — and if it fails, can simply be retried.

Transactions are not a law of nature. They were invented (IBM System R, 1975) to simplify the programming model: the database takes on certain error and concurrency scenarios so the application can ignore them. Those are the safety guarantees. Not every application needs them, and giving them up can buy performance or availability — but you cannot make that trade sensibly without knowing exactly what you are giving up. That is this chapter's job. It applies to single-node and distributed databases alike; the distributed-only troubles wait for Chapter 8→8.

The chapter has three movements: first, what a transaction promises (ACID, and why the acronym is slipperier than it looks); second, the weak isolation levels that most real databases actually run at, each defined by the race conditions it does and doesn't prevent; third, serializability — the strong guarantee — and the three ways to implement it.

FEYNMAN · the whole chapter in one idea A transaction is a promise the database makes so you don't have to think. The promise has two halves. Atomicity: "if I can't do all of it, I'll do none of it, and you can just try again." Isolation: "while you work, pretend nobody else is here." The whole chapter is about the second half being a lie of varying sizes. Read committed only hides other people's unfinished work. Snapshot isolation freezes the world at the moment you walk in — but two people can each make a decision that's fine alone and disastrous together (write skew). Only serializable isolation actually delivers "nobody else is here," and it costs something: run one at a time (serial execution), make everyone queue for locks (2PL), or let everyone run and cancel whoever turns out to have been wrong (SSI). Colors as always: ember = writes, cyan = reads. Every race condition in this chapter is a cyan arrow that read something an ember arrow was about to change.

The Slippery Concept of a Transaction

Almost every relational database and some nonrelational ones support transactions, and nearly all of them follow the style System R introduced in 1975 — MySQL, PostgreSQL, Oracle, and SQL Server are, in the book's phrase, "uncannily similar" to it. Then the late-2000s NoSQL wave arrived with new data models (Chapter 2←2), replication and partitioning by default (Chapters 5←5 and 6←6) — and transactions were the main casualty: dropped entirely, or redefined to mean something far weaker.

Two slogans grew up around this and the book dismisses both as hyperbole. One: transactions are the enemy of scalability, so any serious large-scale system must abandon them. The other (from vendors): transactions are the non-negotiable mark of "serious applications with valuable data." The truth is that transactions are a design trade-off like any other, and to weigh it you need the fine print.

The Meaning of ACID

the-meaning-of-acid

ACID — Atomicity, Consistency, Isolation, Durability — was coined by Härder and Reuter in 1983 to give fault-tolerance in databases precise vocabulary. In practice one database's ACID is not another's; the meaning of isolation in particular is ambiguous, and "ACID compliant" has drifted into a marketing term. (Its foil, BASE — Basically Available, Soft state, Eventual consistency — is even vaguer; its only sensible definition is "not ACID.") So take the four letters one at a time.

Atomicity

Atomic means "cannot be split into smaller parts," but the word means different things in different corners of computing. In multi-threaded programming an atomic operation is one no other thread can observe half-done — that's about concurrency. ACID atomicity is not about concurrency at all (that's the I). It is about faults: a client wants to make several writes, and partway through the process crashes, the network drops, the disk fills, or a constraint fails. If the writes are in one atomic transaction and it cannot be committed, the database aborts it and discards or undoes everything it has written so far. Without this, the application can't tell which of its changes took effect, and retrying risks doing some of them twice. With it, "aborted" means "nothing happened" and a retry is always safe. The book suggests abortability would have been the more honest name.

Consistency

The most overloaded word in the book. It has meant replica consistency and eventual consistency (Chapter 5←5); consistent hashing as a rebalancing scheme (Chapter 6←6); and in the CAP theorem it means linearizability (Chapter 9→9). In ACID it means something else again: an application-specific notion of the data being in a good state — invariants that must always hold, like "credits and debits across all accounts balance." If every transaction starts from a valid state and preserves validity, the invariants stay true. But the database cannot know your invariants; it can check a few simple ones (foreign keys, uniqueness) and otherwise stores whatever you give it. Atomicity, isolation, and durability are properties of the database; consistency in this sense is a property of the application, which merely leans on A and I to achieve it. Hence the book's verdict: the C doesn't really belong in ACID. (Joe Hellerstein's remark: it was "tossed in to make the acronym work.")

Isolation

Several clients hit the same records at once and you get race conditions. The book's Figure 7-1 is the canonical one — two clients each read a counter, add one, and write it back, and 42 becomes 43 instead of 44 — and it is redrawn as the first stepper below. Isolation means concurrent transactions can't step on each other's toes. The textbook formalization is serializability: every transaction may pretend it is the only one running, and the database guarantees the committed result equals some serial order of the transactions even though they actually overlapped. In practice serializable isolation is rarely used because it costs performance; Oracle 11g doesn't even offer it — its level named "serializable" is actually snapshot isolation, a weaker thing. That gap between the name and the guarantee is the heart of the Weak Isolation Levels section.

Durability

The point of a database is a safe place for data. Durability is the promise that once a transaction has committed, its writes will not be forgotten — even through hardware faults and crashes. On a single node that means written to nonvolatile storage (disk or SSD), usually together with a write-ahead log so the on-disk structures can be repaired after a crash (Chapter 3←3). In a replicated database it may mean copied to some number of nodes. Either way the database must wait for that to finish before it reports the commit. And perfect durability does not exist: if every disk and every backup is destroyed at once, nothing saves you.

FEYNMAN · replication and durability — nothing is perfect Durability has meant "on tape," then "on disk," and now often "on several machines." The book's sidebar refuses to crown a winner. Disk survives a crash but the data is unreachable until the machine is fixed; replicas stay available. Replicas can all die of the same correlated fault — a power cut, a bug that crashes every node on the same input — so an in-memory database still wants a disk. Asynchronous replication can lose recent writes on failover (Chapter 5←5). SSDs have been caught violating their guarantees on sudden power loss, even fsync isn't always honest, firmware has bugs, filesystem–storage-engine interactions corrupt files after crashes, bits rot silently (and if they rot for long enough, so do your replicas and recent backups), 30–80% of SSDs grow a bad block within four years, and an unpowered SSD can start losing data within weeks depending on temperature. The only sane stance: disk + remote replicas + backups, together, and a grain of salt for every "guarantee."

Single-Object and Multi-Object Operations

single-object-and-multi-object-operations

Recap the two guarantees that matter when a client makes several writes in one transaction. Atomicity: if an error hits halfway, abort and discard the writes so far — all or nothing. Isolation: another transaction sees either all of those writes or none, never a subset. Both assume you want to modify several objects (rows, documents, records) at once, and that need is everywhere: the book's example is an email client that keeps an unread counter as a denormalized shortcut to SELECT COUNT(*) … WHERE unread_flag = true. Every new message must insert the email and bump the counter. Its Figures 7-2 and 7-3 show what goes wrong without I and without A:

Single-object writes

Atomicity and isolation matter even for one object. Write a 20 KB JSON document and ask: if the network dies after 10 KB, does the database store the unparseable fragment? If power fails mid-overwrite, do old and new bytes end up spliced? Does a concurrent reader see a half-written value? Those would be intolerable, so storage engines almost universally give single-object atomicity and isolation on one node — atomicity via a log for crash recovery, isolation via a lock per object. Some go further with atomic operations: an increment (which removes the read-modify-write cycle of the stepper above) and compare-and-set (write only if the value hasn't changed since you read it). Useful, and they prevent lost updates on a single object — but they are not transactions. Marketing has called them "lightweight transactions" or even "ACID"; a transaction, properly, groups multiple operations on multiple objects into one unit.

The need for multi-object transactions

Many distributed datastores dropped multi-object transactions because they are hard across partitions and get in the way of extreme availability or performance goals — though nothing fundamentally prevents them, as Chapter 9→9 shows. Could you live on single-object operations alone? Sometimes. But three patterns keep demanding coordinated writes: foreign keys in relational data (and edges in graphs) that must stay valid when inserting several mutually referring records; denormalized data in document stores — a single document is one object and needs no transaction, but lacking joins pushes people to duplicate data across documents (Chapter 2←2), and the unread-counter example is exactly that; and secondary indexes, which are separate objects from the transaction's point of view — without isolation a record can appear in one index and not yet in another. You can build without transactions; error handling just gets much harder and concurrency bugs creep in.

Handling errors and aborts

The defining feature is that a transaction can be aborted and safely retried. ACID databases would rather throw away a transaction than leave it half-finished. Not everyone thinks that way: leaderless stores (Chapter 5←5) are "best effort" — they won't undo what they already did, and recovery is the application's problem. And even with abort-and-retry available, developers squander it: Rails's ActiveRecord and Django don't retry aborted transactions; the exception bubbles up and the user's input is thrown away. Retrying is simple and effective, but it has sharp edges:

  • If the transaction actually committed but the acknowledgment was lost, a retry performs it twice — unless the application deduplicates.
  • If the abort was caused by overload, retrying pours fuel on the fire; cap retries, back off exponentially, and treat overload errors differently.
  • Retry only transient errors (deadlock, isolation violation, network blip, failover); retrying a constraint violation is pointless.
  • Side effects outside the database — an email — happen even when the transaction aborts, and again on every retry. Making several systems commit or abort together is what two-phase commit is for (Chapter 9→9).
  • If the client dies while retrying, whatever it was trying to write is gone.
FEYNMAN · "abort" is a feature, not an error Think of a transaction as a draft in a word processor with one very good Undo. Atomicity is the promise that if the power dies, you get back either the fully saved document or the version before you started — never a file with half a paragraph. That's only useful if you actually press Undo and try again. An ORM that turns every abort into a 500 page is like a word processor that has Undo but deletes the document whenever it's pressed. The five bullets are the small print on Undo: sometimes the save did go through and you're saving twice; sometimes you're retrying because the disk is on fire, and retrying faster doesn't put it out.
weak-isolation-levels

Weak Isolation Levels

Two transactions that touch different data can run in parallel with no risk. Trouble starts only when one reads data another is concurrently modifying, or two try to modify the same data. Such bugs are nasty in every way: they need unlucky timing, so tests rarely trigger them and production rarely reproduces them; and in a large application you don't even know which other code touches the same rows. Databases have therefore long offered transaction isolation so you can pretend there is no concurrency. In theory, serializable isolation does exactly that. In practice it costs performance, so most databases run weaker levels that stop some race conditions and let others through — and those levels are hard to understand and easy to be bitten by.

This isn't academic. Weak isolation has lost real money, drawn financial auditors, and corrupted customer data. The reflex "use an ACID database for financial data!" misses the point: the popular relational databases everyone calls ACID also default to weak isolation, so they would not have prevented those bugs. The way out is to understand the anomalies, level by level. Four levels appear in this section — read uncommitted (a footnote), read committed, snapshot isolation, and, as the destination, serializable. The book's approach is informal, by example; the rigorous definitions live in Berenson et al.'s A Critique of ANSI SQL Isolation Levels, Adya's thesis, and Bailis's Highly Available Transactions.

FEYNMAN · a ladder of lies Each isolation level is a specific list of things you're allowed to see that aren't true yet, or aren't true anymore. Picture four people editing a shared spreadsheet. Read committed: you never see a cell someone is still typing into — only saved values. Snapshot isolation: you get a photocopy taken the instant you sat down; other people's saves don't show up until you fetch a new copy. That sounds like enough — until you and a colleague each look at your own photocopy, each see "two doctors on call," and each cross yourself off. Serializable: it is as if only one of you were ever in the room at a time. Every level below the top is a set of race conditions with names, and the rest of this section is a bestiary: dirty read, dirty write, read skew, lost update, write skew, phantom.

Read Committed

read-committed

The most basic level makes two promises. No dirty reads: you only see data that has been committed. No dirty writes: you only overwrite data that has been committed. (An even weaker level, read uncommitted, keeps only the second promise.)

No dirty reads

A transaction has written something but not yet committed or aborted. Can another transaction see it? If so, that is a dirty read. Read committed forbids it: a transaction's writes become visible to others only at commit, and then all at once. Two reasons to want this. First, partial state confuses: the unread-counter figure above was a dirty read of the email. Second, an uncommitted write may later be rolled back — a dirty reader has then seen data that never existed, and reasoning about the consequences "quickly becomes mind-bending."

No dirty writes

Two transactions update the same object; normally the later write wins. But what if the earlier write belongs to a transaction that hasn't committed, and the later write overwrites that uncommitted value? That's a dirty write. Read committed prevents it, usually by making the second writer wait until the first transaction commits or aborts. The book's used-car example (Figure 7-5) shows the damage: Alice and Bob both buy the same car; a purchase updates the listings row (new owner) and the invoices row (who pays). With dirty writes, Bob's update to listings wins but Alice's update to invoices wins — Bob gets the car, Alice gets the bill. Note what read committed does not fix: the counter race of the first stepper. There the second write happens after the first transaction committed, so it isn't dirty. It's still wrong — a lost update — for a different reason, handled in Preventing Lost Updates.

Implementing read committed

Read committed is the default in Oracle 11g, PostgreSQL, SQL Server 2012, MemSQL, and many others. Dirty writes are prevented with row-level locks: to modify an object a transaction must acquire its lock and hold it until commit or abort; a second writer blocks until then. This happens automatically at read committed and above. For dirty reads you could make readers briefly take the same lock — but then one long write transaction stalls every reader of that object, wrecking read latency and letting a slowdown in one part of the app ripple into unrelated parts. So almost every database instead remembers two values per object being written — the old committed value and the new uncommitted one held by the lock owner — and serves the old value to readers until the commit switches them over. (The only mainstream hold-outs using read locks: IBM DB2, and SQL Server with read_committed_snapshot=off.)

Snapshot Isolation and Repeatable Read

snapshot-isolation-and-repeatable-read

Read committed looks like everything you need: aborts work, you never see half-finished transactions, concurrent writes don't get tangled. Yet bugs remain. The book's Figure 7-6: Alice has $1,000 split $500/$500 across two accounts. A transfer moves $100 from account 2 to account 1. If Alice lists her balances at just the wrong moment, she reads account 1 before the deposit ($500) and account 2 after the withdrawal ($400) — and $100 has apparently vanished. Both values were committed when she read them, so read committed is satisfied. This is a nonrepeatable read or read skew: run the first query again at the end and you get a different answer ($600). (Careful — skew here means a timing anomaly, unrelated to the hot-spot skew of Chapter 6←6.)

For Alice it's a refresh away from fixed. Two situations can't shrug it off. Backups copy a whole database over hours while writes continue; parts of the backup end up older than others, and a restore makes the vanished money permanent. Analytic queries and integrity checks scan large parts of the database (Chapter 3←3) and return nonsense if they see different parts at different times.

The standard answer is snapshot isolation: each transaction reads from a consistent snapshot — the database exactly as it was, all committed data, at the moment the transaction began. Later changes by others are invisible for the transaction's whole life. It is a boon for long read-only queries, and it is widely available: PostgreSQL, MySQL/InnoDB, Oracle, SQL Server.

Implementing snapshot isolation

Like read committed, writes take write locks to prevent dirty writes; but reads take no locks at all. The performance mantra: readers never block writers, and writers never block readers. The mechanism generalizes the two-value trick: the database keeps several committed versions of each object side by side, because different in-progress transactions need to see the database at different moments. This is multi-version concurrency control (MVCC). Read committed alone would only need two versions; engines that support snapshot isolation typically use MVCC for read committed too — a fresh snapshot per query for read committed, one snapshot per transaction for snapshot isolation.

PostgreSQL's version (Figure 7-7): every transaction gets a unique, always-increasing transaction ID (txid). Every row carries created_by (the txid that inserted it) and deleted_by (initially empty; set to the txid that deleted it — the row is not physically removed). An update is a delete plus a create: transaction 13 taking $100 from account 2 leaves two rows for account 2 — $500 marked deleted_by = 13, and $400 marked created_by = 13. A garbage collector later removes rows no live transaction can still see.

Visibility rules for observing a consistent snapshot

Which versions can a transaction see? At its start the database lists every other transaction then in progress. Then: (1) writes by any of those transactions are ignored even if they later commit; (2) writes by aborted transactions are ignored; (3) writes by transactions with a later txid are ignored, committed or not; (4) everything else is visible. Equivalently, an object is visible iff its creator had committed before the reader started, and it is not deleted — or its deleter had not committed before the reader started. Because nothing is ever updated in place, a long transaction can keep reading its snapshot for as long as it likes at small cost.

Indexes and snapshot isolation

How does an index work when an object has many versions? One approach: the index points at all versions and the query filters out those invisible to its snapshot; when GC drops old versions the index entries go too (PostgreSQL avoids some index updates when versions of an object fit on one page). CouchDB, Datomic, and LMDB take a different route: an append-only, copy-on-write B-tree (Chapter 3←3). Modified pages are copied, and so are their parents up to the root; untouched pages are shared. Every write (or batch) produces a new root, and each root is a consistent snapshot — no txid filtering needed, since old trees are immutable. The price is a background compaction/GC process.

Repeatable read and naming confusion

Snapshot isolation goes by different names: serializable in Oracle, repeatable read in PostgreSQL and MySQL. The cause is the SQL standard, which is based on System R's 1975 isolation levels — before snapshot isolation existed — and defines repeatable read, which looks superficially similar. Databases call their snapshot isolation "repeatable read" to claim compliance. Worse, the standard's definitions are ambiguous and imprecise, real "repeatable read" implementations differ widely, most don't meet the formal definition in the research literature, and IBM DB2 uses "repeatable read" to mean serializability. The book's conclusion: nobody really knows what repeatable read means.

Preventing Lost Updates

preventing-lost-updates

Read committed and snapshot isolation have so far been about what a reader sees among concurrent writers; the only write-write conflict covered was the dirty write. The best-known of the others is the lost update — the counter race of the first stepper. It happens whenever an application reads a value, modifies it, and writes back the result (a read-modify-write cycle) and two transactions do so concurrently: the second write doesn't include the first modification and clobbers it. It shows up as incrementing counters and account balances, editing part of a JSON document (parse, change, write back), and two people saving a whole wiki page over each other. Because it is so common there are many defenses.

Atomic write operations

Let the database do the read-modify-write: UPDATE counters SET value = value + 1 WHERE key = 'foo' is concurrency-safe in most relational databases; MongoDB has atomic operators for parts of a document, Redis for its data structures. Usually implemented with an exclusive lock taken on the object at read time (cursor stability) or by funnelling all atomic operations through one thread. The best choice whenever your change can be expressed this way — but not everything can (arbitrary text edits to a wiki page), and ORMs make it easy to write an unsafe read-modify-write cycle by accident.

Explicit locking

When the built-in atomics don't fit — say a multiplayer game where a move must also be checked against the rules, logic you can't express as an UPDATE — the application can lock the rows itself: SELECT … FOR UPDATE makes the database lock every row the query returns, so a concurrent read-modify-write on the same figure waits. It works, but you must remember to add the lock everywhere; a single forgotten one is a race.

Automatically detecting lost updates

Atomics and locks prevent the race by serializing the cycles. The alternative is to let them run in parallel and have the transaction manager detect a lost update, abort the loser, and make it retry. This pairs naturally with snapshot isolation, and PostgreSQL's repeatable read, Oracle's serializable, and SQL Server's snapshot isolation all do it. MySQL/InnoDB's repeatable read does not — which is why some authors say MySQL doesn't really provide snapshot isolation. Detection is attractive precisely because it requires no discipline from application code.

Compare-and-set

Databases without transactions often offer an atomic compare-and-set: update only if the value is still what you last read. UPDATE wiki_pages SET content = 'new' WHERE id = 1234 AND content = 'old content' — if it affected zero rows, retry. But if the database evaluates the WHERE against an old snapshot, the condition can hold even while another write is in flight, and the guard fails. Check how your database implements it before relying on it.

Conflict resolution and replication

Locks and compare-and-set assume a single up-to-date copy. Multi-leader and leaderless replication (Chapter 5←5) deliberately have none, so those techniques don't apply; the topic returns under linearizability→9. The usual approach there is to let concurrent writes produce siblings and merge them afterwards (Chapter 5←5). Commutative atomic operations — increments, set-adds — work well across replicas since order doesn't matter; that's the idea behind Riak 2.0 datatypes, which merge concurrent updates losslessly. Last write wins, the default in many replicated stores, is by construction prone to lost updates.

FEYNMAN · four ways to keep two editors from overwriting each other Two people want to update the same whiteboard. Atomic op: don't hand them the eraser — tell the whiteboard "add one" and let it do the arithmetic. Explicit lock: one marker in the room; you hold it from reading to writing. Detect: let both scribble, and have a referee who notices the second person overwrote something they never saw and sends them back to redo it. Compare-and-set: write "change 42 to 43" — if the board no longer says 42, the write bounces. All four assume there is one whiteboard. With replicas there are several, and you're left with merging (or with last-writer-wins, i.e. shrugging).

Write Skew and Phantoms

write-skew-and-phantoms

Dirty writes and lost updates are both about two transactions writing the same object. There are subtler conflicts. The book's example: a hospital on-call rota. There must always be at least one doctor on call; a doctor may drop a shift only if a colleague remains. Alice and Bob are both on call, both feel ill, both click "go off call" at nearly the same moment. Each transaction checks currently_on_call >= 2 — under snapshot isolation both see 2 — and each updates its own record. Both commit. Nobody is on call.

Characterizing write skew

This anomaly is write skew. It is a generalization of the lost update: two transactions read the same objects and then update some of them — if they update the same object you get a dirty write or lost update; if different objects, write skew. The defenses shrink. Single-object atomic operations don't help (several objects). Automatic lost-update detection doesn't help — none of PostgreSQL's repeatable read, MySQL's repeatable read, Oracle's serializable, or SQL Server's snapshot isolation catch it. Database constraints mostly can't express "at least one doctor on call," a multi-object condition, though triggers or materialized views sometimes can. Short of serializable isolation, the second-best option is explicit locking of the rows the decision depends on: SELECT * FROM doctors WHERE on_call = true AND shift_id = 1234 FOR UPDATE, then the update.

More examples of write skew

Once you see the pattern it is everywhere. Meeting-room booking: check for overlapping bookings, insert if none — two users can each find no conflict and both insert. Multiplayer game: the lock from Example 7-1 stops two players moving the same piece, but not moving two different pieces onto the same square. Claiming a username: check it's free, then create — two users can both pass the check (here a unique constraint saves you). Preventing double-spending: insert a tentative charge, sum the account, check it's positive — two concurrent charges can each see a positive balance and together drive it negative.

Phantoms causing write skew

All the examples share a shape: (1) a SELECT checks a requirement by searching for rows matching a condition; (2) application code decides what to do based on the result; (3) it makes a write and commits. The write in step 3 changes the precondition of step 2 — re-run the SELECT afterwards and it would answer differently. In the doctors case the rows updated were among those returned by the query, so FOR UPDATE can lock them. But the other four examples check for the absence of rows, and the write adds a matching row. There is nothing for SELECT FOR UPDATE to lock. A write in one transaction that changes the result of a search in another is a phantom. Snapshot isolation hides phantoms from read-only queries; in read-write transactions they cause the trickiest write skew.

Materializing conflicts

If the problem is that there's no object to lock, invent one. For the booking system, pre-create a table of (room, 15-minute slot) rows for the next six months; a booking transaction first SELECT … FOR UPDATEs the slots it wants, then checks for overlaps and inserts. The slot table stores no booking data — it is purely a set of locks. This is materializing conflicts: turning a phantom into a lock conflict on concrete rows. It is hard to get right and it leaks concurrency control into the data model; treat it as a last resort. Serializable isolation is almost always preferable — which is the cue for the next section.

FEYNMAN · the phantom is the row that isn't there yet A lock is a sticky note on a thing. Write skew with phantoms is the case where the thing you need to protect doesn't exist yet: "no booking for room 123 at noon" is a fact about an empty space, and you can't put a sticky note on an empty space. Materializing conflicts is the janitor's fix — pre-print a sticky note for every room and every quarter-hour so there is always a physical place to stick your claim. It works, and it's ugly, because now your schema contains furniture that exists only to be locked. Predicate locks and index-range locks (next section) are the database doing the same thing for you, more cleverly.
serializability

Serializability

The situation so far is grim. Isolation levels are hard to understand and inconsistently implemented ("repeatable read" means three different things). Looking at application code, you can't tell whether it is safe at a given level — especially in a large application where you don't know what else runs concurrently. And there is no good tooling: static analysis exists in research but not in practice, and concurrency bugs are nondeterministic, so tests miss them. This has been true since weak isolation was introduced in the 1970s, and the researchers' answer has always been the same: use serializable isolation.

Serializable isolation guarantees that although transactions run in parallel, the end result is as if they had run one at a time. If each transaction is correct on its own, they stay correct together — every race condition in this chapter is prevented. So why doesn't everyone use it? The answer is in how it is implemented. Almost every serializable database uses one of three techniques: literally executing transactions serially, two-phase locking (for decades the only viable option), or optimistic concurrency control, notably serializable snapshot isolation. This section treats them on a single node; Chapter 9→9 stretches them across nodes.

FEYNMAN · three ways to make a crowd behave like a queue You want many people to use one bathroom as if they were taking turns. Serial execution: actually make them take turns — fine if everyone is quick and the line is short. Two-phase locking: hand out keys for every fixture; you take the keys you need as you go and return them all when you leave; anyone who needs a key you hold waits — safe, but a slow person blocks everyone and two people can end up each holding the key the other needs (deadlock). SSI: let everyone in, keep a list of who looked at what, and at the door check whether anything someone relied on was changed behind their back — if so, send that person back to redo it. Pessimists wait; optimists apologize.

Actual Serial Execution

actual-serial-execution

The simplest way to avoid concurrency problems is to have no concurrency: one transaction at a time, on a single thread. The result is serializable by definition. Obvious as it sounds, database designers only concluded around 2007 that this was feasible. Two things changed. RAM got cheap enough to hold the entire active dataset in memory (Chapter 3←3), so transactions never wait for disk. And designers noticed that OLTP transactions are short — a few reads and writes — while the long analytic queries are read-only and can run on a consistent snapshot outside the serial loop. VoltDB/H-Store, Redis, and Datomic execute this way, and by dodging locking overhead can outperform concurrent systems — within the ceiling of one CPU core. Living inside that ceiling requires restructuring transactions.

Encapsulating transactions in stored procedures

Early database designers imagined a transaction spanning a whole user flow — searching flights, choosing, booking seats, paying. Humans are slow, so a database would have to juggle huge numbers of idle open transactions; instead every OLTP application keeps transactions short and never waits for a user inside one (on the web, one HTTP request = at most one transaction). But even without the human, transactions stayed interactive: the application sends a query, reads the result, sends the next query, and so on, with a network round trip each time. A single-threaded database running transactions like that would spend most of its time waiting for the application — throughput would be dreadful. So serial-execution systems forbid interactive multi-statement transactions: the application submits the whole transaction in advance as a stored procedure, which runs to completion in memory without any network or disk waits.

Pros and cons of stored procedures

Stored procedures have a poor reputation, for reasons that are real but not fatal. Each vendor has its own archaic language (PL/SQL, T-SQL, PL/pgSQL) lacking libraries and modern ergonomics. Code inside the database is hard to debug, version, deploy, test, and monitor. And a database is shared by many application servers, so one badly written procedure hogging CPU or memory hurts far more than the same code in an app server. Modern serial-execution systems sidestep the first problem with general-purpose languages: VoltDB uses Java or Groovy, Datomic Java or Clojure, Redis Lua. With in-memory data and stored procedures, one thread achieves good throughput. VoltDB also replicates by re-executing the same stored procedure on every replica, which requires procedures to be deterministic — the current time, for instance, must come from a special deterministic API (compare statement-based replication's problems in Chapter 5←5).

Partitioning

One thread means one core's worth of write throughput. Read-only transactions can run elsewhere on snapshots, but a write-heavy application hits the wall. The way out is to partition the data (Chapter 6←6) so each transaction reads and writes within one partition; each partition then gets its own serial thread, and throughput scales linearly with cores. But any cross-partition transaction must be coordinated in lock-step across every partition it touches, and that is vastly slower — VoltDB quotes ~1,000 cross-partition writes per second, orders of magnitude below single-partition rates and not improvable by adding machines. Whether your transactions can stay single-partition depends on your data: simple key-value data partitions easily; anything with several secondary indexes tends to need cross-partition coordination (Chapter 6←6).

Summary of serial execution

Serial execution delivers serializability under constraints: every transaction must be small and fast (one slow one stalls everyone); the active dataset must fit in memory (a transaction that touches disk can be aborted, the data fetched asynchronously, and the transaction restarted — anti-caching); write throughput must fit one core, or the data must partition without cross-partition transactions; and cross-partition transactions, while possible, have a hard ceiling.

Two-Phase Locking (2PL)

two-phase-locking-2pl

For about thirty years there was one widely used algorithm for serializability: two-phase locking (strictly, strong strict 2PL). It is not two-phase commit — 2PC is an atomic-commit protocol across nodes (Chapter 9→9); the similar names are an accident. We've already met locks that stop dirty writes: a second writer waits for the first transaction to finish. 2PL makes the requirement much stronger. Many transactions may read an object concurrently, but the moment anyone wants to write it, exclusive access is required: if A has read x and B wants to write x, B waits until A commits or aborts (so nothing changes behind A's back); if A has written x and B wants to read x, B waits too (reading an old version, MVCC-style, is not acceptable). Writers block readers and readers block writers — the exact opposite of snapshot isolation's mantra — and that's precisely why 2PL prevents lost updates and write skew.

Implementation of two-phase locking

Used by MySQL/InnoDB's and SQL Server's serializable level and DB2's repeatable read. Every object has a lock with two modes. To read, acquire it in shared mode — many can hold shared simultaneously, but not if someone holds exclusive. To write, acquire it in exclusive mode — nobody else may hold it in any mode. Read-then-write may upgrade shared to exclusive, with the same waiting rules. And every lock, once acquired, is held until the end of the transaction. That is the "two phases": phase one, while executing, only acquires locks; phase two, at commit or abort, releases them all. With so many locks held so long, deadlock — A waits for B's lock while B waits for A's — is routine; the database detects it, aborts one transaction, and the application retries.

Performance of two-phase locking

The reason 2PL didn't sweep the world in the 1970s is performance: throughput and response times are much worse than under weak isolation. Partly the overhead of the locks themselves, but mostly reduced concurrency — by design, whenever two transactions could possibly race, one waits. Traditional databases don't bound transaction duration (they were built for interactive human-paced sessions), so a wait can be arbitrarily long, and a queue can form behind a hot object even when every transaction is short. The result is unstable latency with terrible high percentiles under contention (Chapter 1←1): one slow transaction, or one that grabs many locks, can grind the system to a halt. Frequent deadlocks add retries on top.

Predicate locks

Something was glossed over: phantoms. A serializable database must stop one transaction changing another's search results — if a transaction has searched for bookings of room 123 from noon to 1 pm, nobody may concurrently insert or update a booking for that room and window (other rooms and other times are fine). Conceptually this needs a predicate lock: a shared/exclusive lock that belongs not to one object but to all objects matching a search condition. To read matching objects, take a shared predicate lock on the condition — wait if anyone holds an exclusive lock on any matching object. To insert, update, or delete anything, first check whether the old or new value matches any existing predicate lock — wait if so. The key: a predicate lock covers objects that don't exist yet. 2PL plus predicate locks prevents every form of write skew and makes isolation truly serializable.

Index-range locks

Predicate locks perform badly — checking every write against many active predicates is slow. So most 2PL databases use index-range locking (next-key locking), a coarser approximation. It is always safe to lock more than the predicate: "room 123 at any time," or "every room from noon to 1 pm," both contain the original condition. The database picks whichever index it used for the search — room_id, or a time index — and attaches a shared lock to that index entry or range of entries. Any writer of a booking for that room or that window must update the same part of the index, hits the lock, and waits. Less precise than predicate locks, far cheaper, and effective against phantoms. With no suitable index, the fallback is a shared lock on the whole table — safe, and disastrous for concurrent writes.

Serializable Snapshot Isolation (SSI)

serializable-snapshot-isolation-ssi

The picture so far: serializable implementations that don't perform (2PL) or don't scale (serial execution), versus weak levels that perform but leak races. Are serializability and performance fundamentally at odds? Perhaps not. Serializable snapshot isolation provides full serializability at only a small cost over snapshot isolation. It is young — first described in 2008, the subject of Michael Cahill's PhD thesis — and used by PostgreSQL's serializable level since 9.1 and, in distributed form, by FoundationDB. It is still proving itself, but it may become the default of the future.

Pessimistic versus optimistic concurrency control

2PL is pessimistic: if anything might go wrong (someone else holds a lock), wait until it's safe — mutual exclusion, as in multi-threaded programming. Serial execution is pessimism taken to the limit: effectively an exclusive lock on the entire database (or partition) per transaction, made bearable by making each transaction very fast. SSI is optimistic: don't block, carry on and hope; at commit time check whether isolation was violated, and if so abort and retry. Optimistic control is an old idea with a known weakness — under high contention many transactions abort, and if the system is already near capacity the retries make things worse. With spare capacity and modest contention it tends to beat pessimism, and contention can be reduced with commutative atomic operations (concurrent increments of a counter needn't conflict, as long as the counter isn't also read in the same transaction). What distinguishes SSI from earlier optimistic schemes: it is built on snapshot isolation — all reads come from a consistent snapshot — and adds an algorithm for detecting serialization conflicts and choosing which transactions to abort.

Decisions based on an outdated premise

Recall the write-skew pattern: read something, decide, write. Under snapshot isolation the query result may be stale by commit time. The transaction acted on a premise — "two doctors are on call" — that may no longer be true. The database can't know how the application used a query result, so it must assume any change to the result might invalidate the transaction's writes (a causal dependency from reads to writes). To be serializable it must detect that a transaction may have acted on an outdated premise and abort it. How can a query's result have changed? Two cases: a stale MVCC read (an uncommitted write existed before the read and was hidden by the snapshot), and a write that affects a prior read (the write came after the read).

Detecting stale MVCC reads

The snapshot ignores writes from transactions uncommitted at snapshot time. In the book's Figure 7-10, transaction 43 reads Alice as on call because transaction 42's change to her row is uncommitted; by the time 43 wants to commit, 42 has committed — the ignored write took effect and 43's premise is false. So the database tracks when a transaction ignored another's write under the visibility rules, and at commit checks whether any of those ignored writes have since committed; if so, abort. Why wait until commit rather than abort at the read? Because 43 might be read-only (no write skew possible), or 42 might still abort, or still be uncommitted when 43 commits. Avoiding premature aborts is what preserves snapshot isolation's gift of long-running consistent reads.

Detecting writes that affect prior reads

The mirror case: a transaction modifies data after another has read it. Reuse the index-range-lock idea, but without blocking. When 42 and 43 both search for on-call doctors in shift 1234, the database records on the index entry for 1234 (or at table level if no index) that these two transactions read it — kept only until they and all concurrent transactions finish. When a transaction writes, it looks in the indexes for other transactions that recently read the affected data and notifies them that what they read may be stale. It's like a write lock on the key range that acts as a tripwire instead of a barrier. In Figure 7-11 each of 42 and 43 trips the other; 42 commits first and succeeds (43's conflicting write hasn't committed, so it hasn't taken effect); when 43 tries to commit, 42's write has committed, so 43 must abort.

Performance of serializable snapshot isolation

Engineering details decide how well SSI does. One trade-off is the granularity of tracking reads and writes: fine-grained tracking aborts only what must abort but costs bookkeeping; coarse tracking is cheap but aborts bystanders. Sometimes a transaction can be proven serializable even though it read data later overwritten; PostgreSQL uses that theory to avoid unnecessary aborts. Against 2PL, SSI's big win is no blocking: writers don't block readers or vice versa, so latency is predictable and read-only queries run lock-free on a snapshot — very appealing for read-heavy workloads. Against serial execution, SSI is not bound to one core: FoundationDB distributes conflict detection across machines and lets transactions span partitions while staying serializable. The abort rate is what matters most: a transaction that reads and writes for a long time will likely conflict and abort, so read-write transactions should be short (long read-only ones are fine) — though SSI is probably less sensitive to slow transactions than either alternative.

FEYNMAN · what SSI actually checks Every transaction under snapshot isolation is a little argument: "I saw X, therefore I wrote Y." Snapshot isolation guarantees X was true when you looked. Serializability demands X still be true when you commit — otherwise your argument's premise expired while you were writing. SSI doesn't try to stop premises from expiring (that's 2PL, and it means everyone waits). It just keeps two lists — "what did you look at" and "what did you change" — and, at the commit door, asks one question: did anything you looked at get changed by someone who has already committed? If yes, your argument is void; go back and argue again from the current facts. Optimism with a receipt check.

Core takeaways

  • A transaction groups reads and writes into one unit that commits or aborts as a whole; it exists to simplify the programming model — the database absorbs partial-failure and concurrency scenarios so the application can ignore them. Neither "transactions don't scale" nor "serious data needs transactions" is true; it is a trade-off.
  • ACID: Atomicity = abortability under faults (not concurrency). Consistency = application invariants, a property of the application, not the database — it doesn't belong in the acronym. Isolation = concurrent transactions don't interfere; formally serializability, in practice usually something weaker. Durability = committed data survives crashes, via WAL + disk and/or replication; no technique is perfect, so combine disk, replicas, and backups.
  • Single-object atomicity/isolation is near-universal (log + per-object lock), and atomic increment / compare-and-set help — but they aren't transactions. Multi-object transactions are needed for foreign keys, denormalized data, and secondary indexes. Aborts exist to enable retries; retry only transient errors, beware duplicates, overload, and side effects.
  • Read committed (default in PostgreSQL, Oracle, SQL Server): no dirty reads (see only committed data — implemented by keeping old + new value, not read locks) and no dirty writes (row-level write locks held to commit). Still allows read skew and lost updates.
  • Snapshot isolation (PostgreSQL/MySQL "repeatable read", Oracle "serializable"): each transaction reads a consistent snapshot as of its start, via MVCC — rows stamped created_by/deleted_by txid, updates = delete + create, visibility rules ignore in-progress, aborted, and later transactions; GC removes dead versions. Readers never block writers and writers never block readers. Alternative: copy-on-write B-trees where every root is a snapshot. "Repeatable read" is so inconsistently defined that nobody knows what it means.
  • Lost updates (concurrent read-modify-write) are prevented by atomic write operations, explicit SELECT … FOR UPDATE, automatic detection (PostgreSQL, Oracle, SQL Server — not MySQL), or compare-and-set; all assume one up-to-date copy. Across replicas: commutative operations and merging siblings; LWW loses updates.
  • Write skew: two transactions read the same objects and write different ones, jointly breaking an invariant (doctors on call, room bookings, usernames, double-spend). Not caught by snapshot isolation or lost-update detection. Phantoms — a write changing another transaction's search result — make it worse because there's no row to lock; materializing conflicts (a table of lock rows) is the ugly last resort.
  • Serializability prevents every race condition and comes three ways. Actual serial execution (VoltDB/H-Store, Redis, Datomic): one thread, in-memory data, stored procedures (no interactive round trips), deterministic; scales by partitioning only if transactions stay single-partition.
  • Two-phase locking (MySQL/SQL Server serializable, DB2 repeatable read): shared/exclusive locks held until commit — readers block writers and vice versa; deadlocks detected and aborted; poor, unstable latency under contention. Predicate locks cover rows that don't exist yet; index-range locks approximate them cheaply with a superset.
  • Serializable snapshot isolation (PostgreSQL ≥ 9.1, FoundationDB): optimistic — run on a snapshot, track stale MVCC reads and writes that affect prior reads (non-blocking tripwires on index entries), abort at commit if a premise was invalidated by a committed transaction. No blocking, predictable latency, scales across machines; needs short read-write transactions and low contention.
  • 2nd-edition arc (Ch 8): same structure, more real-world stakes (Horizon scandal, ACIDRain, exchange races), harder-nosed durability (fsyncgate, crash consistency, SSD power faults), MVCC internals and newer isolation checkers (Elle, client-centric specs), isolation clearly separated from consistency levels, and CockroachDB/TiDB/Spanner/FoundationDB as the proof that serializable transactions and distribution are not enemies.
